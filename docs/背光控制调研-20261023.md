## 0. TL;DR

| 问题 | 结论 | 硬证据 |
|---|---|---|
| **谁在驱动面板？** | **DECON 是 mainline 在驱动**（i80 命令模式）；**DSIM 和面板是 S-Boot 留下的"孤儿"**，mainline 从头到尾没有绑定过 DSIM | 见 §1（`card0-VGA-1` 名字 + i80 判定 + DT 无 dsi 节点 + samsung-dsim 无 7420 compatible） |
| 为什么根本没有 `/sys/class/backlight/`？ | 整条链路上**没有任何 backlight 注册点**：DTS 里没有 panel/backlight 节点，`panel-samsung-s6e3ha2.ko` 虽然编了但没有 mipi_dsi 宿主，永远不会 probe | §1.5、§3.1 |
| 为什么 DPMS Off 只省 6mA？ | DPMS Off 只走到 `decon_atomic_disable()`：关 window + `pm_runtime_put`。**面板还在按最后一帧发光**，因为没人给它发 0x28 | §2 |
| DSIM 能不能发 DCS 命令？ | **能，而且只碰 SFR FIFO 时风险很低**：pclk 门控带 `CLK_IGNORE_UNUSED`、DCS 与 i80 帧数据走两条独立 FIFO、不需要改 PLL/PHY/lane | §5 |
| 亮度命令到底是什么？ | vendor 用 **0xCA gamma 表（35B）+ 0xF4 VINT + 0xB6 ELVSS + 0xF7 update**；MIPI 标准的 **0x51(DBV) vendor 一次都没用过** → 0x51 属"待设备验证" | §4.2 |
| 主线 s6e3ha2 驱动用的是 0x51 吗？ | **不是**（任务描述里这点要更正）。0x51 在主线驱动里一次都没出现；`0x53` 只用于 HBM off（`0x53 0x00`） | §3.2、§3.3 |
| `gpio_pcd` 是面板控制脚吗？ | **不是**。PCD = **P**anel **C**ondition **D**etect，是 ESD 检测中断（`pcd-irq`），跟亮度/供电无关 | §6.4 |
| 面板供电在哪？ | MAX77838（i2c **0x60**）LDO1=`VCC_DISPLAY_1.8V`、LDO3=`VCC_3.0V_LCD`，vendor 里是 `regulator-boot-on`，**mainline 没有 max77838 驱动** | §6 |
| 0x60 能写吗？ | **存疑**。项目自己的 DTS 注释写着"mainline 实测只有 0x59 稳定 ACK" → 方案 C 的第一步是 `i2cdetect` 验证 0x60 | §6.2 |

**一句话**：面板在发光，但主线里没有任何人能命令它 —— DECON 是我们的人，DSIM 是敌人的（S-Boot 的）通讯兵，而我们要发的命令（0x28/0x51）必须经过那条 DSIM。所以方案 A = 绕过"编制"，直接往 DSIM 的 SFR FIFO 塞包（不接管、不初始化、不改配置）。

## 1. 当前显示链路：到底谁在驱动面板

### 1.1 链路图

```
            mainline 6.6 拥有 ─┐        ┌─ S-Boot 遗留，mainline 无人驱动 ─┐
                               ↓        ↓                                  ↓
  GPU/CPU ──► framebuffer ──► DECON ──i80──► DSIM0 ──4 lane DSI──► S6E3HF2
               (DMA-BUF)      0x13930000    0x13900000   (command)    (1440×2560)
              exynos7_drm_decon.c          无 DT 节点，无驱动          S-Boot 初始化
              i80_if=true, TRIGCON 每帧触发  PLL/PHY/lane 保持 S-Boot 状态   (0xF0/0xF2/0xC8 MTP…)
```

**结论：mainline 驱动 DECON；DSIM 和面板完全是 S-Boot 初始化好之后被"继承"下来的静态状态。**
这正是 `card0-VGA-1` 能工作、而亮度/熄屏完全失控的原因。

### 1.2 证据 1：connector 叫 `VGA-1` 说明走的是 DPI 编码器，**不是 DSI**

设备上 `card0-VGA-1` 的 `VGA` 不是笔误，是 `exynos_drm_dpi.c` 里写死的连接器类型：

```c
/* drivers/gpu/drm/exynos/exynos_drm_dpi.c:102-104 */
ret = drm_connector_init(encoder->dev, connector,
                         &exynos_dpi_connector_funcs,
                         DRM_MODE_CONNECTOR_VGA);      /* → 名字就是 "VGA-1" */
```

也就是说：**DRM 管线里根本没有 DSI 编码器**，DSI 桥不在 encoder chain 上。
`exynos_drm_dpi.c:117-147` 的 `exynos_dpi_enable/disable` 只会 `drm_panel_prepare/enable`
（而 `ctx->panel == NULL`，见 `:233-237`），所以它本质是个**空壳 encoder**，只负责
"让 DRM 有个 connector 可用"，扫描输出其实是 DECON 在 i80 模式下自己推的。

顺带说明 `zenlte` 主线移植也是同一套（`HANDOVER-DISPLAY-GPU-TOUCH.md` §1.2 里
`monitors.xml` 用的就是 `VGA-1`），所以这不是我们移植的问题，是**这条路线本身的选择**。

### 1.3 证据 2：DECON 走的是 i80（命令）模式，而不是 RGB 视频模式

```c
/* drivers/gpu/drm/exynos/exynos7_drm_decon.c:945-947 */
i80_if_timings = of_get_child_by_name(dev->of_node, "i80-if-timings");
if (i80_if_timings)
        ctx->i80_if = true;
```

板级 DTS `exynos7420-zeroflte.dts:533-535` 故意留了个空的 `i80-if-timings {}` 子节点，
DTS 注释里写明了原因：没有 DSI/panel 节点 → DPI 模式找不到 port → 不创建 connector → 黑屏；
加上它就切到 i80 命令模式，"直接按 display-timings 驱动 S-Boot 已初始化的面板"。

i80 模式下每帧要靠 `TRIGCON` 软件触发 + `DECON_UPDATE` 提交：

```c
/* exynos7_drm_decon.c:618-641（decon_atomic_flush，我们自己加的） */
if (ctx->i80_if) {
        val = readl(ctx->regs + TRIGCON);
        ...
        val |= TRIGCON_SWTRIGEN_I80_RGB | TRIGCON_SWTRIGCMD_I80_RGB |
               TRIGCON_HWTRIGEN_I80_RGB | TRIGCON_HWTRIGMASK_DISPIF0 |
               TRIGCON_HWTRIGMASK_DISPIF1 | TRIGCON_HWTRIG_AUTO_MASK;
        writel(val, ctx->regs + TRIGCON);
        writel(upd | DECON_UPDATE_STANDALONE_F, ctx->regs + DECON_UPDATE);
        writel(readl(ctx->regs + TRIGCON) | TRIGCON_SWTRIGCMD_I80_RGB,
               ctx->regs + TRIGCON);
}
```

⇒ **帧数据是 mainline 主动推进 DSIM 的**（i80 通路），DSIM 只是被动转发。

### 1.4 证据 3：DT 里**没有** dsi 节点，也没有 panel/backlight 节点

```sh
$ grep -c "mipi-dsi\|dsi@" arch/arm64/boot/dts/exynos/exynos7.dtsi
0
$ grep -n "panel\|backlight" arch/arm64/boot/dts/exynos/exynos7420-zeroflte.dts
514: *   S-Boot 已经初始化好 DSI + panel 并持续扫描帧缓冲；Linux **不碰 DSI/panel**，
529: *   而本板没有 DSI/panel 节点 → "no port node found" → 不创建 connector
```

整个 mainline DT（SoC + 板级）里：
- `decon: decon@13930000`（`exynos7.dtsi:830`）—— 有。
- `dsim0 / mipi-dsi` —— **没有**（vendor 在 `exynos7420.dtsi:2812` 有 `dsim_0: dsim@0x13900000`）。
- `panel@…` / `backlight` / `pwm-backlight` —— **没有**。

### 1.5 证据 4：`samsung-dsim` 从来没有 probe 过（不是"挂了不用"，是"没挂上"）

```c
/* drivers/gpu/drm/exynos/exynos_drm_dsi.c:157-180 */
static const struct of_device_id exynos_dsi_of_match[] = {
    3250 / 4210 / 5410 / 5422 / 5433 …      /* 没有 7420，也（暂时）不需要 */
};
/* :182-190 */
struct platform_driver dsi_driver = {
    .probe = samsung_dsim_probe,
    .driver = { .name = "exynos-dsi", .of_match_table = exynos_dsi_of_match },
};
```

平台驱动只能靠 DT 节点匹配才 probe；**没有节点 = 没有 `struct samsung_dsim` 实例 = 没有
`mipi_dsi_host` = `panel-samsung-s6e3ha2.ko` 永远等不到宿主**。这就是 `/sys/class/backlight`
完全不存在的最直接原因（`CONFIG_DRM_PANEL_SAMSUNG_S6E3HA2=m` 编了 .ko，但没人能 probe 它）。

### 1.6 各硬件块的归属（这张表决定了后面所有方案的边界）

| 硬件 | 地址 | mainline 状态 | 谁在配置它 |
|---|---|---|---|

## 2. DPMS Off 为什么只省 6mA

### 2.1 代码路径（熄屏时真正发生了什么）

```
GNOME 空闲 → mutter DPMS off → drmModeSetCrtc(NULL)
  → exynos_drm_crtc.c:37-54  exynos_drm_crtc_atomic_disable()   （这里有 DSH-DPMS 调试打印）
  → exynos7_drm_decon.c:754    decon_atomic_disable()
        ├─ decon_disable_plane() ×2   → 清 WINCONx_ENWIN（:583-601）
        └─ pm_runtime_put_sync()      → 关 DECON 的 pclk/aclk/eclk/vclk
```

**没有任何一行代码碰 DSIM 或面板。** 于是：

- DECON 停止扫描 → 不再有新帧推向 DSIM；
- DSIM 保持空闲（它的 pclk 门控是 `CLK_IGNORE_UNUSED`，不会被关）；
- 面板 DDI 的 GRAM 里还留着最后一帧 → **继续按那一帧发光**；
- 电流只掉了 6mA（= DECON/DSIM 的逻辑电流），面板那 300+ mA 一分没省。

实测数据（用户提供）：亮屏 `-346mA`，DPMS off `-340mA`。这个差值就是"只停了扫描"的典型值。

### 2.2 零成本验证这个归因（上机第一步就能做，不需要任何代码）

在 GNOME 里放一张**全屏纯黑**图（或 `feh -F black.png` / `mpv --fs` 一张黑图），等 5 秒后看电流：

- 如果电流掉到 ≈ `-100mA` 以下 ⇒ **归因成立**：这 300mA 就是面板发光，DCS 0x28 会得到同样的收益；
- 如果电流几乎不变 ⇒ 我们的模型错了（可能是别的东西在耗电），先别写内核代码。

这是本任务里**唯一可以零风险先做的实验**，强烈建议上机第一件事就做（步骤见实现方案 §5.1）。

## 3. mainline `panel-samsung-s6e3ha2.c` 解剖（同系列参考驱动）

### 3.1 backlight 怎么注册

```c
/* drivers/gpu/drm/panel/panel-samsung-s6e3ha2.c:723-732 */
ctx->bl_dev = backlight_device_register("s6e3ha2", dev, ctx, &s6e3ha2_bl_ops, NULL);
...
ctx->bl_dev->props.max_brightness = S6E3HA2_MAX_BRIGHTNESS;   /* 100 */
ctx->bl_dev->props.brightness     = S6E3HA2_DEFAULT_BRIGHTNESS; /* 80 */
ctx->bl_dev->props.power          = FB_BLANK_POWERDOWN;

/* :473-476 */
static const struct backlight_ops s6e3ha2_bl_ops = {
    .get_brightness = s6e3ha2_get_brightness,
    .update_status  = s6e3ha2_set_brightness,
};
```

要点：
- 用 `backlight_device_register()`（老 API，非 devm），名字就是 sysfs 节点名；
- **它必须寄生在 `mipi_dsi_device` 上**（`probe(struct mipi_dsi_device *dsi)`，`:678`），
  所以没有 DSIM 宿主 = 这个驱动一行都跑不到 → 我们拿不到它现成的 backlight；
- `props.power` 在 `prepare()` 里置 `FB_BLANK_NORMAL`（`:557`）、`enable()` 里置
  `FB_BLANK_UNBLANK`（`:604`）——**用 backlight 的 power 字段当面板开关**，这是三星驱动的惯例。

### 3.2 亮度到底怎么下发（**不是 0x51**，任务描述需更正）

```c
/* :449-471 s6e3ha2_set_brightness() */
if (bl_dev->props.power > FB_BLANK_NORMAL) return -EPERM;   /* 熄屏时禁止改亮度 */
s6e3ha2_test_key_on_f0(ctx);        /* 0xF0 0x5A 0x5A  解锁 MIPI 厂商命令 */
s6e3ha2_update_gamma(ctx, brightness);   /* ★ 亮度本体 */
s6e3ha2_aor_control(ctx);           /* 0xB2 0x03 0x10  AOR */
s6e3ha2_set_vint(ctx);              /* 0xF4 0x8B <vint>  */
s6e3ha2_test_key_off_f0(ctx);       /* 0xF0 0xA5 0xA5  锁回 */
```

```c
/* :432-447 s6e3ha2_update_gamma() */
unsigned int index = brightness * (46 - 1) / 100;           /* 46 档 gamma 表 */
u8 data[36] = { 0xca, };                                    /* ★ 0xCA 长包 + 35 字节 */
memcpy(data + 1, gamma_tbl + index, 35);
s6e3ha2_dcs_write(ctx, data, 36);
s6e3ha2_gamma_update(ctx);        /* 0xF7 0x03 → ndelay(100) → 0xF7 0x00 */
```

**全文里 `0x51`（`MIPI_DCS_SET_DISPLAY_BRIGHTNESS`）一次都没有出现。**
亮度完全靠"写 gamma 表 + 触发 gamma 更新"。`vint_table[]`（`:217-220`，10 个值）
决定低亮度下的 VINT 电压；`gamma_tbl[46][35]`（`:30-215`）是整张亮度-灰阶映射表。

> **对任务的更正**：任务描述里"DSI DCS 命令：`0x51`、`0x53`"这句，
> 实际是 `0xCA`(gamma) + `0xF7`(gamma update) + `0xF4`(VINT) + `0xB2`(AOR) + `0x53`(仅 HBM off)。

### 3.3 `0x53` 的真实用途：HBM，不是亮度控制

```c
/* :390-394 */
static int s6e3ha2_hbm_off(struct s6e3ha2 *ctx)
{
    s6e3ha2_dcs_write_seq_static(ctx, 0x53, 0x00);   /* WRITE_CONTROL_DISPLAY，bit7:6 = HBM */
    return 0;
}
```

`0x53` 在 MIPI 里是 `WRITE_CONTROL_DISPLAY`：bit5 = BCTRL（亮度控制使能）、
bit3 = BL_DIMMING、bit2 = DISPLAY_DIMMING、bit7:6 = HBM。
主线驱动只用了"HBM off"（`0x53 0x00` = BCTRL 关闭），所以它的亮度完全来自 gamma 表。

⇒ **推论**：如果我们要走 MIPI 标准亮度（0x51），必须先 `0x53 0x20`（BCTRL=1）。
**这颗 DDI 支不支持 BCTRL 没有任何现成证据**（vendor 也从未写过 bit5），
所以实现方案把它列为"待设备验证"，并准备好了 gamma 路径作为阶段 2。

### 3.4 gamma 表结构

```c
#define S6E3HA2_NUM_GAMMA_STEPS   46    /* 亮度档位 */
#define S6E3HA2_GAMMA_CMD_CNT     35    /* 每档 35 字节：3 组 V255/V3/V11 参考 + 24 个灰阶点 */
static const u8 gamma_tbl[46][35] = { ... };      /* :30-215 */
static const unsigned char vint_table[10] = { 0x18, …, 0x21 };  /* :217-220 */
```

`0xCA` 长包 = `1 字节命令 + 35 字节参数 = 36`，正好 `S6E3HA2_GAMMA_CMD_CNT + 1`。

### 3.5 为什么不能直接把 HF2 descriptor 拿来用

主线驱动**已经带了** `s6e3hf2` 的兼容字符串和描述符：

```c
/* :762-766 */
{ .compatible = "samsung,s6e3hf2", .data = &samsung_s6e3hf2 },

/* :627-643 */
static const struct drm_display_mode s6e3hf2_mode = {
    .clock = 247856, .hdisplay = 1600, ...       /* ★ 1600×2560 */
};
```

但是：
1. **分辨率不对**：主线 HF2 是 **1600×2560**（面板 s6e3hf2 的另一版本/WQXGA 变体），
   我们的是 **1440×2560**（vendor DTS `resolution = <1440 2560>`，`zeroflte_chn_00.dts:927`）。
2. **gamma 表是 ha2 的**：`gamma_tbl`、`vint_table` 只有 HA2 一套，HF2 分支只在
   `freq_calibration()` 里差别（`:299-300`、`:310-312`）——即主线对 HF2 的 gamma 支持是"借用 HA2 表"。
3. 对我们的面板（1440×2560）直接套 HA2 的 gamma 表 → 亮度能变，但**颜色/白点会偏**（可用作实验，不宜当成品）。

### 3.6 电源/复位序列（方案 B 的风险就在这）

```c
/* :523-543 s6e3ha2_power_on() */
regulator_bulk_enable(2, ctx->supplies);   /* "vdd3" + "vci" */
msleep(120);
gpiod_set_value(ctx->enable_gpio, 0); usleep_range(5000, 6000);
gpiod_set_value(ctx->enable_gpio, 1);
gpiod_set_value(ctx->reset_gpio, 1);  usleep_range(5000, 6000);
gpiod_set_value(ctx->reset_gpio, 0);  usleep_range(5000, 6000);

/* :478-494 s6e3ha2_panel_init()：极短的初始化序列 */
0x11(exit sleep) → 5ms → 0xF0 5A5A → 0xF2 0x67 → 0xF9 0x09 → 0xFC 5A5A
→ 0xFD 0x1C → 0xFE 0x20 0x39 → 0xFE 0xA0 → 0xFE 0x20 → 0xCE ... → 0xFC A5A5 → 0xF0 A5A5
```

对比 vendor `s6e3hf2_wqhd_lcd_ctrl.c:1451 s6e3hf2_wqhd_init()`（**180 行**：TE、pentile、
POC、PCD、ERR_FG、TSET、ELVSS、gamma、MCD/ACL、HBM 表…）：**主线这套序列对 S6E3HF2 明显不够**。
方案 B 若照搬，黑屏概率很高（面板已经在跑，一复位就要重建全部状态，错一步就得 TWRP 救砖）。

## 4. vendor `s6e3hf2` 的亮度真相（真正的参考实现）

### 4.1 面板参数（`panels/s6e3hf2_wqhd_param.h`）

| 宏 | 值 | 位置 | 说明 |
|---|---|---|---|
| `UI_MAX_BRIGHTNESS` | 255 | `:24` | UI 亮度上限（1 字节） |
| `EXTEND_BRIGHTNESS` | 439 | `:23` | HBM 档（`LEVEL_IS_HBM()`，`:15`） |
| `UI_DEFAULT_BRIGHTNESS` | 134 | `:26` | 默认亮度 |
| `GAMMA_CMD_CNT` | 36 | `:50` | 0xCA + 35 字节 |
| `ELVSS_LEN` / `ELVSS_REG` | 23 / **0xB6** | `:45-46` | ELVSS 长包 |
| `VINT_REG` / `VINT_LEN` | **0xF4** / 3 | `:47-48` | VINT |
| `AID_CMD_CNT` | 3 | `:51` | AID（Auto Impedance/亮度补偿） |

`MAX_BR_INFO = 73`（`panels/s6e3hf2_wqhd_dimming.h:72`）—— 即 **73 档**亮度（不是 256/255 档）。

### 4.2 一次亮度调整 = 5 条 DCS 命令

`panels/dsim_backlight.c`：

```c
/* :107-118 */ dsim_panel_gamma_ctrl()  → dsim_write_hl_data(gamma, 36)    /* 0xCA + 35B */
/* :136-146 */ dsim_panel_aid_ctrl()    → dsim_write_hl_data(aid,   3)     /* AID 补偿 */
/* :148-166 */ dsim_panel_set_elvss()   → 0xB6 + 22B（含温度补偿 HBM_INTER_22TH_OFFSET） */
/* :169-200 */ dsim_panel_set_acl()     → 0x55 (ACL cutoff) + 0xB5 (ACL OPR) */
```

其上层（`dsim_backlight.c` 的 `dsim_panel_set_brightness()`）还会写
`0xF4 VINT`（`s6e3hf2_wqhd_param.h:47`）和 `0xF7`：

```c
/* panels/s6e3hf2_wqhd_param.h */
static const unsigned char SEQ_GAMMA_CONDITION_SET[] = { 0xCA, 0x01,0x00, …, 0x00 };  /* :156 */
static const unsigned char SEQ_GAMMA_UPDATE[]        = { 0xF7, 0x03 };                /* :182 */
static const unsigned char SEQ_GAMMA_UPDATE_L[]      = { 0xF7, 0x00 };                /* :187 */
static const unsigned char SEQ_HBM_OFF[]             = { 0x53, 0x00 };                /* :244 */
static const unsigned char SEQ_HBM_ON[]              = { 0x53, 0xC0 };                /* :249 */
static const unsigned char SEQ_DISPLAY_ON[]          = { 0x29 };                      /* :138 */
static const unsigned char SEQ_DISPLAY_OFF[]         = { 0x28 };                      /* :142 */
```

**结论**：
1. **熄屏只需要 1 个字节 `0x28`**（`SEQ_DISPLAY_OFF`），点亮是 `0x29`。这就是我们最需要的那条命令。
2. 亮度是"gamma 表 + ELVSS + AID + VINT"的组合拳，**不是单个 0x51**。
3. vendor 全库搜索不到以 `0x51` 为**命令**的调用：`grep -rn "0x51" panels/*.c panels/*.h`
   只命中 gamma/mdnie 表里的**数据字节**，没有一行是 DCS 命令；
   ⇒ MIPI 标准亮度在这颗 DDI 上**未经证实**（实现方案把它列为"待设备验证 + 有退化路径"）。

### 4.3 Smart Dimming 为什么不能一次搬过来（阶段 2 的工作量）

`panels/s6e3hf2_wqhd_lcd_ctrl.c:638 init_dimming()` 在初始化时要：

1. 读面板 ID（`panel->id[]`）—— **需要 DSI 读**（`dsim_read_hl_data` → `MIPI_DSI_DCS_READ`，
   需要 BTA/LP turnaround）；
2. 依 `panelline/paneltype/panelrev` 在 **4 套表**里选一套
   （`a3_daisy_dimming_info` / `daisy_dimming_info_RC` / `_RD` / `tulip_dimming_info`，`:663-687`）；
3. 读 MTP（`S6E3HF2_MTP_ADDR = 0xC8`，`:39`）+ HBM gamma（`0xB4`，`:41`），
   逐色算 `t_gamma[][]`、`look_volt[][]`（`:690-750`）；
4. 再跑 `set_gamma_to_center()` / `interpolation_gamma_to_hbm()` 生成每档 36 字节 gamma。

⇒ 这是 **读 + 写 + 大量浮点/查表** 的活，`dimming.h` 光表就 727 行。**和"发一个 0x28"完全不是一个量级**，
所以放到阶段 2（且只有 0x51 验证失败才值得做）。

### 4.4 vendor 的 DCS 发送路径 —— 证明"发命令不影响 i80 帧"

```c
/* dsim_drv.c:387-410 dsim_write_hl_data() */
if (cmdSize == 1)      dsim_write_data(dsim, MIPI_DSI_DCS_SHORT_WRITE, cmd[0], 0);
else if (cmdSize == 2) dsim_write_data(dsim, MIPI_DSI_DCS_SHORT_WRITE_PARAM, cmd[0], cmd[1]);
else                   dsim_write_data(dsim, MIPI_DSI_DCS_LONG_WRITE, cmd, cmdSize);

/* dsim_drv.c:187-… dsim_write_data()：把包塞进 SFR FIFO */
dsim_reg_clear_int(DSIM_INTSRC_SFR_PH_FIFO_EMPTY);
dsim_reg_wr_tx_header(id, data_id, data0, data1);    /* 写 DSIM_PKTHDR */
/* dsim_drv.c:151-186 dsim_wait_for_cmd_fifo_empty(id)：
   id=0 → SFR_PH_FIFO(header)，id=1 → SFR_PL_FIFO(payload) */
```

**关键结论（方案 A 的立论基础）**：vendor 用的是 **SFR header/payload FIFO**，
而 DECON 的 i80 帧数据走 **i80 header/payload FIFO**，两者是 DSIM 里**独立的 FIFO**：

| FIFO | header full/empty | payload full/empty | 谁用 |
|---|---|---|---|
| SFR（普通命令） | `BIT(23)` / `BIT(22)` | `BIT(21)` / `BIT(20)` | **CPU 发 DCS** |
| i80（DECON 帧） | `BIT(19)` / `BIT(18)` | `BIT(17)` / `BIT(16)` | DECON |

（主线的 `samsung-dsim.c:157-168` 把这两组位都定义了，和 vendor
`regs-dsim.h:155-158` 的 `FULL_PH_SFR/FULL_PL_SFR` 位号一致。）

⇒ 我们只往 SFR FIFO 写包时，**物理上不会踩到 i80 的数据通路**。
唯一残余风险是 DSI 协议层面的"包间插队"（面板在收 1440×2560 长包的间隙收到一个
DCS 短包），vendor 靠 `decon_lpd_block_exit()`（`dsim_drv.c:239`）做协调；
我们的实现先不协调，实测有花屏再补（见实现方案 §6.3）。

## 5. DSIM 现状核查（方案 A 的前提：能不能安全地发命令）

### 5.1 DSIM 的"身份"

| 项 | 值 | 来源 |
|---|---|---|
| 基址 | **`0x13900000`**（4 KiB） | vendor `exynos7420.dtsi:2812` `dsim_0: dsim@0x13900000` |
| 中断 | SPI **196** | 同上 `interrupts = <0 196 0>` |
| 电源域 | `pd_disp` | 同上 `samsung,power-domain = <&pd_disp>` |
| 时钟 | `pclk_dsim0` / `mipi0_rx` / `mipi0_bit` / `rgb_vclk0` / `pclk_disp` | 同上 `:2822-2826` |
| mainline DT | **无节点** | `grep -c dsi@ exynos7.dtsi` = 0 |
| mainline 驱动 | `exynos_drm_dsi.c` 无 7420 compatible，且无节点 → **未 probe** | `:157-180` |

### 5.2 寄存器可访问性（为什么不会像 TOP0 那样一读就挂）

三条独立保证：

1. **APB 时钟门控显式豁免**：
   ```c
   /* drivers/clk/samsung/clk-exynos7.c:1564-1565 */
   GATE(CLK_PCLK_DSIM0, "pclk_dsim0", "dout_pclk_disp",
        ENABLE_PCLK_DISP, 29, CLK_IGNORE_UNUSED, 0),
   ```
   `CLK_IGNORE_UNUSED` ⇒ `clk_disable_unused()` 不会关它。
   （同文件 `:1560-1563` 的 `pclk_disp` 桥门控 bit31 也是 `CLK_IGNORE_UNUSED`。）
2. **bootargs 兜底**：`exynos7420-zeroflte.dts:199`
   `bootargs = "... clk_ignore_unused pd_ignore_unused ..."`。
3. **DISP 电源域是活的**：DECON 正在 i80 扫描（屏幕内容会变），同域内的 DSIM 必然上电。

⇒ 结论：**读 `DSIM_STATUS` 不会挂总线**，最坏情况读到 `0xffffffff`（IP 状态不对），
实现里已加这个判定作为硬门禁（见补丁 `dsh_bl_register()`）。

### 5.3 发一条 DCS 短包需要的最小寄存器集（offset 已核对）

| offset | 名字 | 用途 | vendor 定义 |
|---|---|---|---|
| `0x004` | `DSIM_STATUS` | `PLL_STABLE`(b31) / `TX_READY_HS_CLK`(b10) | `regs-dsim.h:21-28` |
| `0x03c` | `DSIM_PKTHDR` | `ID(b5:0) | DATA0(b15:8) | DATA1(b23:16)` | `:137-140` |
| `0x040` | `DSIM_PAYLOAD` | 长包 payload（32bit/word） | `:143` |
| `0x04c` | `DSIM_FIFOCTRL` | 状态位（见 §4.4 表）/ 低 5 位是 FIFO reset | `:155-158` |

**只写 PKTHDR/PAYLOAD，只读 STATUS/FIFOCTRL**。绝不写 `FIFOCTRL`（低 5 位会复位 FIFO）、
`DSIM_CONFIG`、`PLLCTRL`、PHY 寄存器 —— S-Boot 配好的 PLL/PHY/lane 一改就得重跑初始化（_我们没有_）。

对比一下主线 6.6 的同名驱动（`drivers/gpu/drm/bridge/samsung-dsim.c`）：
它的 `samsung_dsim_init_link()`（`:835-921`）会 `FIFOCTRL &= ~0x1f` 复位 FIFO、重写 CONFIG/PLL/PHY。
**这正是方案 B 才敢做的事** —— 方案 A 一行都不能碰。

### 5.4 失败模式（诚实清单）

| 可能失败 | 表现 | 后果 |
|---|---|---|
| DSIM 的 SFR FIFO 被 S-Boot 关在某种低功耗状态 | `wait_empty` 超时 2ms | 返回 `-ETIME`，dmesg 有打印，屏幕不受影响 |
| 包发出去了但面板 DDI 不认 0x28 | 电流不掉 | 亮度/熄屏无效，无副作用 |
| DCS 短包插在 i80 长包中间 | 一帧花屏/闪一下 | 下一帧自愈 |
| DSIM 内部状态被写坏 | 屏幕冻住/花屏 | **需要重启（S-Boot 重新初始化）**，不涉及刷机 |
| 面板进 ULPS/stop state 后包发不出去 | `FIFOCTRL` 一直不 empty | 超时返回，无害 |

**方案 A 的"最坏后果"= 重启一次**（因为 S-Boot 每次冷启动都会重建 DSIM+面板状态），
这也是它比方案 B 低风险的根本原因。

## 6. 面板供电与"关背光"的物理边界

### 6.1 MAX77838：面板两路电源

```dts
/* vendor exynos7420-zero_common.dtsi:692-731 */
hsi2c@13670000 {
	max77838@60 {
		compatible = "maxim,max77838";
		reg = <0x60>;
		regulators {
			__ldo1_reg: LDO1 { regulator-name = "VCC_DISPLAY_1.8V"; regulator-boot-on; };
			__ldo2_reg: LDO2 { regulator-name = "tsp_io";           };   /* 触摸屏 */
			__ldo3_reg: LDO3 { regulator-name = "VCC_3.0V_LCD";  regulator-boot-on; };
			__ldo4_reg: LDO4 { regulator-name = "tsp_avdd";         };   /* 触摸屏 */
		};
	};
};
```

寄存器（vendor `drivers/regulator/max77838-regulator.c`）：
- `0x03 REG_REG_EN`：bit0=`LDO1_EN`、bit1=`LDO2_EN`、bit2=`LDO3_EN`、bit3=`LDO4_EN`（`:51-57`）
- `0x02 REG_REG_STAT`：POK 回读，bit0=LDO1、bit2=LDO3（`:41-49`）
- `0x00 REG_DEVICE_ID`（`:33`）

⇒ 关面板 = 写 `0x60 reg0x03` 清 bit0|bit2（掩码 `0x05`），**保留 bit1|bit3**（触摸屏别断）。
`rootfs/display/g9209-panel-power.sh` 就是干这个的（照 `rootfs/touch-power/g9209-touch-power.sh` 的写法）。

### 6.2 0x60 到底能不能写？**存疑，必须先验证**

板级 DTS 自己的注释（`exynos7420-zeroflte.dts:952-953`）：

> 这条总线上还能摸到（在某些 boot 状态下）MAX77838 的 0x60，
> 但 mainline 实测只有 0x59 稳定 ACK。

原因链（同文件 `:886-950` 的注释）：vendor 把 MAX77838 挂在 `hsi2c@13670000`，
但那条总线的 pinctrl 在 `pinctrl@14CE0000` 死区，且 S-Boot 没 mux 这组引脚；
我们现在是通过 `gpg3-2/3` 的 **i2c-gpio** 去摸它（和 S2MPB02 0x59 同一条物理线）。
**0x59 稳定、0x60 时有时无** ⇒ 方案 C 的第一步永远应该是 `g9209-panel-power.sh probe`。

### 6.3 掉电 = 画面回不来（方案 C 的硬限制）

拉掉 `VCC_3.0V_LCD` ⇒ 面板 DDI 掉电复位（POR）。恢复供电后需要重跑初始化序列
（`0x11` + `0xF0 5A5A` + `0xF2/0xF9/0xFD/0xFE/0xCE` + MTP + gamma …），
而**唯一会跑这套序列的人是 S-Boot**。mainline 手里没有它（方案 B 才去补）。

⇒ 方案 C 只适合：①测面板真实功耗；②屏幕长期不用；③方案 A 失败时的应急。
**不适合日常熄屏/唤醒**（每次唤醒都要重启手机）。

### 6.4 更正：`gpio_pcd` 不是"面板控制脚"

vendor 板级 DT 里的 `decon_0 { gpio_pcd = <&gpa1 2 0>; }`（`zeroflte_chn_00.dts:915`）
是给 **ESD 检测**用的：

```c
/* vendor decon_core.c:5907-5911 */
gpio = of_get_named_gpio(dev->of_node, "gpio_pcd", 0);
if (gpio_is_valid(gpio)) {
	decon_info("esd : found gpio_pcd success\n");
	esd->pcd_irq = gpio_to_irq(gpio);       /* → 注册成中断 */
```
```c
/* vendor decon_core.c:5939-5941 */
devm_request_irq(dev, esd->pcd_irq, decon_esd_pcd_handler,
		 IRQF_TRIGGER_HIGH | IRQF_ONESHOT, "pcd-irq", decon);
```

`PCD = Panel Condition Detect`（面板状态检测/ESD），handler 是 `decon_esd_pcd_handler`
（`decon_core.c:5811`）。它**不是** panel enable/reset 脚，跟亮度、供电都无关 —— 不要在这上面浪费实验。

## 7. 三方案评估（详细代码见实现方案文档）

| | **A：DSIM 直发 DCS（不接管）** | **B：移植 DSI + 面板驱动** | **C：关面板供电（兜底）** |
|---|---|---|---|
| 能调亮度 | 能（0x51 待验证；不行则退化到"只有开关"） | 能（可完整复刻 vendor 73 档） | 不能 |
| 熄屏真关发光 | **能**（0x28，1 字节） | 能 | 能 |
| 改动面 | 1 个驱动文件 + 1 个 DTS 属性（≈250 行） | 新增 DSIM 节点 + 面板驱动 + 对 DSIM 的完全接管（数百行，且要重跑初始化） | 用户态脚本（无内核改动） |
| 挂死风险 | 低（最坏重启） | **高**（面板初始化错 → 黑屏 → TWRP） | 低（但 0x60 未必 ACK） |
| 能否唤醒恢复 | **能**（0x29 + 重设亮度） | 能 | **不能**（需重启） |
| 依赖未知项 | 0x51/BCTRL 是否支持 | 7420 DSIM 的 PLL/PHY 参数、面板完整 init 序列 | 0x60 可达性 |
| 省电收益 | 熄屏 ≈ 面板全暗（目标 -340→<100mA） | 同 A，且亮度可调范围完整 | 同 A（但回不来） |
| 结论 | **先做** | 长期（且只在 A 的亮度不够时） | 测量/应急 |

**推荐：A →（若 0x51 无效）A+gamma 简表 →（若仍不满意）B。C 只当测量工具。**
