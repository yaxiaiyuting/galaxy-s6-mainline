## 0. 结论（TL;DR）

**根因：Exynos7420 的启动链（S-Boot / secure monitor → uniLoader → Linux）把内核放在
EL1 启动，且从不初始化 `CNTVOFF_EL2`。而 mainline arm64 在 "从 EL1 进入" 时的既定策略是
使用虚拟计数器 `CNTVCT`（`arch_counter_register()`），于是每个 CPU 读到的 CNTVCT 各自带一个
互不相同的、可达数千秒量级的随机偏移。`CNTVOFF_EL2` 只有 EL2 能写，EL1 下的内核无法自救。**

这一个缺陷同时解释了全部异常：

| 实测症状 | 机制 | 详见 |
|---|---|---|
| printk 时间戳在几千秒范围乱跳、非单调（同核内单调） | `sched_clock()` = 全局 epoch + **本核 CNTVCT**，每核偏移不同 | §2 |
| 8 核/2 核必须 `nohz=off` 才能启动 | `tick_nohz_next_event()` 用 **tick_do_timer_cpu 域的全局 `last_jiffies_update`** 算 next_tick，从核用**本核 ktime** 编程 clockevent → delta 差上千秒，CPU 被 "睡" 到 `max_delta`（MCT 约 179 s）或 min-delta 反复触发 | §3 |
| `clock_settime`/`date -s` 后任何 sleep/sync 永久挂死 | `timekeeping_forward_now()` 在本核读 CNTVCT 并把**全局** `cycle_last` 更新到"本核计数器域"；其它核 `clocksource_delta()` 无符号运算得到 `2^56−Δ` ⇒ 时间前跳 **≈95 年**，hrtimer 永不触发 | §4 |
| RCU stall、`sched: RT throttling activated` | 次生现象：stall/RT 带宽/调度时钟同样基于被污染的 ktime / `sched_clock_cpu()` | §5 |
| 同一 Image 在 QEMU virt 完全正常 | QEMU 正确实现 CNTVOFF=0；且本属性是 DT 驱动，VM 的 DTB 没有该属性 ⇒ 行为不变 | §6 |
| **原厂 DTB 自身的写法** | `/timer` 节点写着 `use-clocksource-only; use-physical-timer;`，MCT 节点写着 `use-clockevent-only;` —— **三星自己就是用物理计数器 CNTPCT 做 clocksource、MCT 做 clockevent**，因为他们的内核同样在 EL1 且不碰 CNTVOFF | §1.4 |

**修复（p204，已编译）**：让 arm64 的 arch timer 在 DT 属性 `arm,cpu-registers-not-fw-configured`
（本板 uniLoader 已自动注入，板级 DTS 也已补写）存在时，把 counter 读取从 CNTVCT 重定向到
全局的 `CNTPCT`。实现借用内核现成的 OOL erratum 框架，只有 4 行核心代码 + 注释；
框架会自动关闭 arm64 vDSO 的 archtimer fast path，无需改 vDSO。**不改 bootloader、不改 .config。**

## 1. 根因：CNTVOFF_EL2 未被固件初始化

### 1.1 架构规定与 arm64 启动协议

ARMv8 通用定时器中：

- `CNTPCT_EL0`（物理计数器）由 SoC 的 **System Counter** 驱动，**全 SoC 一个计数器**，所有 CPU 读到的值相同。
- `CNTVCT_EL0`（虚拟计数器）= `CNTPCT − CNTVOFF_EL2`，`CNTVOFF_EL2` 是 **per-CPU** 的 64 位寄存器，
  **只有 EL2 及以上可以写**。

`Documentation/arch/arm64/booting.rst:190-196`（"Architected timers"）规定：

```
- Architected timers

  CNTFRQ must be programmed with the timer frequency and CNTVOFF must
  be programmed with a consistent value on all CPUs.  If entering the
  kernel at EL1, CNTHCTL_EL2 must have EL1PCTEN (bit 0) set where
  available.
```

即：**只要内核（任一 CPU）从 EL1 进入，固件就必须把所有 CPU 的 CNTVOFF_EL2 设成同一个值**
（通常是 0），或者干脆让内核从 EL2 进入、由内核自己清零。

### 1.2 Linux 自己只在"EL2 入口"时清 CNTVOFF

- `arch/arm64/kernel/head.S:610-624` `init_kernel_el()`：从 EL2 进入 → `init_el2`；
  从 EL1 进入 → `init_el1` 直接 `eret` 回 EL1 继续。
- `arch/arm64/include/asm/el2_setup.h:51-58` `__init_el2_timers`（只在 `init_el2` 路径执行）：

  ```asm
  .macro __init_el2_timers
      mov x0, #3                  // Enable EL1 physical timers
      ...
      msr cnthctl_el2, x0
      msr cntvoff_el2, xzr        // Clear virtual offset   ← 第 57 行
  .endm
  ```

- `arch/arm64/kernel/smp.c:411-424` `hyp_mode_check()`：本板日志出现的是
  `CPU: All CPU(s) started at EL1` → `is_hyp_mode_available()==false`
  （`arch/arm64/include/asm/virt.h:86-97`）。
- 从核同样从 EL1 进入（`arch/arm64/kernel/head.S:698-701 secondary_entry` → `init_kernel_el`）。

**⇒ 本板没有任何一次 `msr cntvoff_el2, xzr` 的机会。** 而 host 侧的 arch timer 驱动
**完全不会去读/校验/修正 CNTVOFF**（全树只有 KVM 会写它：`arch/arm64/kvm/arch_timer.c:487`；
本内核 `CONFIG_KVM` 未开）。mainline 的做法是"无条件信任固件"。

### 1.3 mainline 6.6 为什么恰好选了虚拟计数器

`drivers/clocksource/arm_arch_timer.c:1100-1150`（HEAD 原始行号）：

```c
static void __init arch_counter_register(unsigned type)
{
	u64 (*scr)(void);
	...
	if (type & ARCH_TIMER_TYPE_CP15) {
		if ((IS_ENABLED(CONFIG_ARM64) && !is_hyp_mode_available()) ||
		    arch_timer_uses_ppi == ARCH_TIMER_VIRT_PPI) {
			/* ★ 本板走这里：arm64 且从 EL1 启动 → 用 CNTVCT */
			rd  = arch_counter_get_cntvct;      /* clocksource / cyclecounter */
			scr = arch_counter_get_cntvct;      /* sched_clock */
		} else {
			rd  = arch_counter_get_cntpct;      /* 只有 EL2 入口 / 32 位 ARM 才用物理计数器 */
			scr = arch_counter_get_cntpct;
		}
		arch_timer_read_counter = rd;
		clocksource_counter.vdso_clock_mode = vdso_default;   /* = VDSO_CLOCKMODE_ARCHTIMER */
	}
	...
	sched_clock_register(scr, width, arch_timer_rate);        /* 第 1149 行 */
}
```

`arch_timer_read_counter` 的默认值也是 CNTVCT（`arm_arch_timer.c:238`）。

注意 PPI 选择与 counter 选择是**两件独立的事**：本板 DT 只声明了物理 PPI
（13/14/10，没有 `virt` PPI），所以 `arch_timer_select_ppi()` 返回 `PHYS_NONSECURE_PPI`
（于是 banner 打印 `(phys)`），**但这只决定"事件中断用哪个 timer"，不决定"读哪个计数器"**。
CLOCK_EVT/PPI 是物理的、clocksource/sched_clock 却是虚拟的 —— 这正是本板"看起来像物理模式、
实际却读 CNTVCT"的迷惑点。

### 1.4 原厂 DTB 的铁证（三星自己不用 CNTVCT）

原厂 zeroflte DTB 反编译（`<HOME>/deepseek/G9209-fix/dtbwork/chn.dts`）：

```dts
/* dtbwork/chn.dts:4205-4211 */
timer {
    compatible = "arm,armv8-timer";
    interrupts = <0x01 0x0d 0xff01 ...>,   /* PPI 13 sec-phys */
                 <0x01 0x0e 0xff01 ...>,   /* PPI 14 phys     */
                 <0x01 0x0b 0xff01 ...>,   /* PPI 11 virt     */
                 <0x01 0x0a 0xff01 ...>;   /* PPI 10 hyp      */
    clock-frequency = <0x16e3600>;         /* 24 MHz */
    use-clocksource-only;                  /* ★ 只做 clocksource，不做 clockevent */
    use-physical-timer;                    /* ★ 用物理计数器/定时器（CNTPCT），不是 CNTVCT！ */
};

/* dtbwork/chn.dts:4221-4231 */
mct@101C0000 {
    compatible = "samsung,exynos4210-mct";
    ...
    use-clockevent-only;                   /* ★ MCT 只做 clockevent */
};
```

- `use-physical-timer`：三星原厂内核的 arm_arch_timer 私有属性，含义就是 **arch_timer_use_virtual = false**
  （counter 读 CNTPCT，event 用物理 timer）。
- `use-clocksource-only` / `use-clockevent-only`：把两套硬件固定成一个供 clocksource、一个供 clockevent。

**三星给 Exynos7420 写 `use-physical-timer`，等价于承认：本 SoC 的启动固件不保证 CNTVOFF 一致，
虚拟计数器不可用。** 这也解释了为什么原厂 Android 能正常跑 —— 它根本不看 CNTVCT。

我们的板级 DTS 忠实地还原了原厂"arch timer 只做 clocksource、MCT 只做 clockevent"的结构
（靠 `MCT_CLKEVENTS_RATING` 在 zeroflte 上提到 500 盖过 arch timer 的 450），**却漏掉了
`use-physical-timer` 这个最关键的 counter 选择**，因为 mainline 6.6 不认识它。

### 1.5 主线历史先例（说明这不是我们的臆测）

1. **2014 年 Rockchip/Chromebook 的同一问题**（Doug Anderson，exynos5420/rk3288）：
   > "The initial problem is that the virtual offset is not initialized by anyone and is per core
   > (each core gets a different, random offset). That makes the virtual counter useless."
   >
   > —— https://lkml.iu.edu/hypermail/linux/kernel/1409.1/02531.html

   结论同样落在"直接用物理计数器"（Sonny Rao 的 patch + 新属性），最终在 **ARM32** 上以
   `arm,cpu-registers-not-fw-configured` 的形式合入。

2. **2018 年三星 Marek Szyprowski 给 Exynos5433 TM2 的 arm64 补丁**（与本板同族问题）：
   > "This enables to run Linux kernel on ARM64 boards using physical architected timers instead of
   > the virtual ones. Examples of such system with broken firmware are Samsung Exynos5433 SoC
   > based TM2(e) boards, which is already deployed for years and updating firmware is not possible."
   >
   > 实现方式：在 `ool_workarounds[]` 里加一条 `ate_match_dt` 条目，
   > `.read_cntvct_el0 = arch_counter_get_cntpct`
   >
   > —— https://marc.info/?l=linux-arm-kernel&m=153900346906095

   该补丁被 Marc Zyngier 以"arm64 启动协议不允许迁就坏固件"为由拒绝（arm32 才允许），
   所以 mainline 至今没有 arm64 的开关。**但它的实现方式与 6.6 的 OOL
   workaround 框架完全兼容 —— 这也是本次 p204 采用的方案（§7.2）。**

### 1.6 为什么 EL1 下的内核无法自救

- 写 `CNTVOFF_EL2`：需要 EL2；本板内核在 EL1（`CurrentEL == EL1`），执行该 MSR 会 UNDEF。
- 让内核改从 EL2 启动：需要 S-Boot/uniLoader 把内核入口放到 EL2。uniLoader 自己也在 EL1
  （`uniLoader/main/boot.c:119` `dsh_arm_probe` 明确要求 EL1），没有 EL2 代码可执行，做不到。
- 读 CNTPCT：**可行**。CNTHCTL_EL2.EL1PCTEN（bit0）已被固件置位：
  - uniLoader 在 EL1 读 CNTPCT 做过实测（p67 `timer status`：`CNTFRQ=0 CNTPCT=2403240663->2405325353`）；
  - 内核在 EL1 也读过 CNTPCT（p68 诊断 `counter_delta=11514`）。
  ⇒ **"改用物理计数器"是本板唯一低成本可救的路**，且已被 loader/内核实测证明可行。

### 1.7 附：CNTFRQ=0 的小坑（不是本次根因）

硬件 `CNTFRQ_EL0` 读出来是 0（S-Boot 没配）；uniLoader 往 DT `/timer` 里补
`clock-frequency = <24000000>`（`uniLoader/main/diag.c:207-217`），所以内核
`arch_timer_of_configure_rate()` 用 DT 频率 24 MHz。这与 CNTVOFF 无关，不影响本次修复。

## 2. 症状 1：sched_clock/printk 时间戳乱跳的确切机制

### 2.1 printk 时间戳的完整链路

```
printk() → kernel/printk/printk.c:2180  ts_nsec = local_clock()
        → include/linux/sched/clock.h:62-65  local_clock() = sched_clock()
        → kernel/time/sched_clock.c:101-109 sched_clock() → sched_clock_noinstr()
        → kernel/time/sched_clock.c:83-98   res = epoch_ns + cyc_to_ns(read())
        → read() = arch_timer_read_counter = arch_counter_get_cntvct (CNTVCT)
```

- 本内核 `CONFIG_HAVE_UNSTABLE_SCHED_CLOCK` **未设置**（只有 ia64/x86/parisc select 它），
  所以 `local_clock()` 就是全局 `sched_clock()`，**没有 per-CPU 校正数据**；
  `kernel/sched/clock.c:484-490` 里 `sched_clock_cpu(cpu)` 在无该配置时也直接返回 `sched_clock()`。
- 这意味着时间戳 = **全局 epoch + 本 CPU 的 CNTVCT 换算值**。每个 CPU 的 CNTVCT 各带
  自己的 `−CNTVOFF_i` 偏移，于是**每个 CPU 打印出来的时间戳都带一个自己的常数偏移**。

### 2.2 MCT 先注册 32 位 sched_clock、arch timer 后覆盖（不是 bug）

`drivers/clocksource/exynos_mct.c:222-259`（HEAD 行号）：

```c
static u64 notrace exynos4_read_sched_clock(void) { return exynos4_read_count_32(); }
...
if (clocksource_register_hz(&mct_frc, clk_rate)) panic(...);     /* "clocksource: mct-frc" */
sched_clock_register(exynos4_read_sched_clock, 32, clk_rate);    /* "sched_clock: 32 bits at 24MHz" */
```

随后 arm timer 注册（`arm_arch_timer.c:1149`）：

```c
sched_clock_register(scr, width, arch_timer_rate);               /* "sched_clock: 56 bits at 24MHz" */
```

`kernel/time/sched_clock.c:164-205` 的替换逻辑：

```c
void __init sched_clock_register(u64 (*read)(void), int bits, unsigned long rate)
{
	if (cd.rate > rate)
		return;                       /* 第 172 行：只拒绝"更慢"的时钟 */
	...
	new_epoch = read();               /* 第 191 行：新计数器当前值 */
	cyc = cd.actual_read_sched_clock();                     /* 旧计数器当前值 */
	ns  = rd.epoch_ns + cyc_to_ns((cyc - rd.epoch_cyc) & rd.sched_clock_mask, ...);
	rd.epoch_cyc = new_epoch;
	rd.epoch_ns  = ns;                /* 保证切换瞬间时间连续 */
```

- MCT 和 arch timer 都是 **24 MHz**，`cd.rate > rate` 为 false ⇒ arch timer 成功替换。
- 替换时 `epoch` 连续，所以 **CPU0（注册时所在 CPU）时间从 ~0 开始是"正常"的**；
  问题全部出在**其它 CPU 之后各自读自己 CNTVCT** 时叠加上去的偏移。
- 日志顺序 `clocksource: mct-frc` → `sched_clock: 32 bits` → `arch_sys_counter` →
  `sched_clock: 56 bits` 与上述代码完全对应，属正常注册顺序，**不是故障**。

### 2.3 对账实测时间戳

sched_clock 按 24 MHz 换算：`1 s = 24,000,000 ticks`。

| 实测时间戳 | 换算 ticks（= CNTVCT−CNTVCT_boot 的隐含值） | 说明 |
|---|---|---|
| `[ 4954.820514] EXT4-fs (sda20) mounted` | 118,915,692,336 ≈ 0x1B AFED7730 | 打印该行的 CPU 的 `−CNTVOFF` 约 −4954 s |
| `[ 2030.025320] systemd: ... advancing clock` | 48,720,607,680 | 另一个 CPU |
| `[ 2024.393637] rcu: INFO: ... stall` | 48,585,447,288 | 再一个 CPU |
| `[ 2020.728719] CPU features` / `[ 2020.728806] CPU1: Booted` | 48,497,491,344 / 48,497,513,424 | **同一 CPU、+87 µs 单调** ⇒ 偏移是"每核常数"的特征 |

特征判别：**同 CPU 相邻打印单调且差值合理（µs 级），跨 CPU 时间戳可以任意前后跳**。
这正是"per-CPU 常数 offset"的表现；如果是计数器本身故障（掉电/复位），同 CPU 也会跳。

> 为什么启动最初的一小段（单核阶段）时间戳看起来正常（`[0.003341]`）？
> 因为 `sched_clock_register()` 的 epoch 是在 **boot CPU** 上注册时按 boot CPU 的 CNTVCT
> 归零的（§2.2），boot CPU 自己的偏移被"吸收"进 epoch；等第二个 CPU 上线开始打印，
> 它读的是**同一 epoch + 自己 CNTVCT**，偏移立刻暴露。所以"启动开头几毫秒正常"
> 并不说明 boot CPU 的 CNTVOFF=0。

### 2.4 为什么不是 MCT 造成的（逐条排除）

1. `sched_clock` 最终是 arch timer（56 bits），MCT 的 32 位 FRC 已被覆盖（§2.2），
   MCT 的 32 位回绕（2³²/24 MHz = 178.96 s）不会进入时间戳。
2. 即使退一步用 MCT FRC 做 sched_clock，它是 **MCT 块里唯一的全局计数器**，所有 CPU
   MMIO 读同一个值，**不可能产生 per-CPU 偏移**。
3. `clocksource` 最终选的是 `arch_sys_counter`（rating 400）而不是 `mct-frc`（arm64 下
   `MCT_CLKSOURCE_RATING=350`，`exynos_mct.c:55-61`），且 bootargs 里还有
   `clocksource=arch_sys_counter`。
4. 因此 p203 的经验性猜测（"MCT 32 位会回绕 → 禁用 MCT"）**方向错误**：禁用 MCT 不会改变
   counter 读取路径，时间戳乱跳会原样保留；反而去掉 MCT clockevent 后会引入
   "arch timer 物理 PPI clockevent 未验证"的新风险（§7.5）。

### 2.5 vDSO 的隐患（即使内核修好了也要处理）

arm64 vDSO 的 `__arch_get_hw_counter()` 固定读 `CNTVCT_EL0`
（`arch/arm64/include/asm/vdso/gettimeofday.h:89`），是否启用由
`clocksource->vdso_clock_mode` 决定（`kernel/time/vsyscall.c:80-84`）。

- 现状（未修）：内核时间戳乱、用户态 vDSO `clock_gettime` 也会按 CPU 跳。
- 本修复：workaround 框架在 `arch_timer_enable_workaround()` 里检测到
  `wa->read_cntvct_el0 != NULL` 时会自动执行
  `clocksource_counter.vdso_clock_mode = VDSO_CLOCKMODE_NONE; vdso_default = VDSO_CLOCKMODE_NONE;`
  （HEAD `arm_arch_timer.c:588-608` 附近）⇒ **用户态自动回退到 syscall，时间正确**。
  这是选择 OOL workaround 方案而不是"裸改 arch_counter_register"的额外好处。

## 3. 症状 3：为什么 8 核必须 `nohz=off`

### 3.1 全局 jiffies 时间基只在一个 CPU 域里更新

`kernel/time/tick-sched.c:52` `static ktime_t last_jiffies_update;`（**全局**），
由 `tick_do_timer_cpu`（= 第一个运行 scheduler tick 的 CPU；本板为 boot CPU，即 A53 簇那个核，
逻辑编号见日志）在 `tick_do_update_jiffies64()` 中更新（`tick-sched.c:57-143`）：

```c
delta = ktime_sub(now, tick_next_period);      /* now 来自本 CPU 的 ktime_get() */
...
last_jiffies_update = ktime_add_ns(last_jiffies_update, TICK_NSEC);
...
update_wall_time();                            /* timekeeping 也只在这一个 CPU 推进 */
```

`now` 是在 **do_timer CPU 的 ktime 域**里取的；`last_jiffies_update` 也就落在这个域里。

### 3.2 NOHZ 停 tick 时，跨核把两种域混用

`kernel/time/tick-sched.c:801-882` `tick_nohz_next_event()`：

```c
do {
	seq = read_seqcount_begin(&jiffies_seq);
	basemono = last_jiffies_update;        /* ← 全局，但属于 do_timer CPU 的 ktime 域 */
	basejiff = jiffies;
} while (...);
...
next_tick = get_next_timer_interrupt(basejiff, basemono);   /* 同样是 do_timer 域 */
...
ts->timer_expires = min_t(u64, expires, next_tick);
```

然后 `tick_nohz_stop_tick()`（`tick-sched.c:884-980`）把这个**绝对 ktime** 用在本 CPU 上：
HIGHRES 模式下 `hrtimer_start(&ts->sched_timer, tick, HRTIMER_MODE_ABS_PINNED_HARD)`，
编程时 `kernel/time/clockevents.c:303-338`：

```c
delta = ktime_to_ns(ktime_sub(expires, ktime_get()));
if (delta <= 0)
	return force ? clockevents_program_min_delta(dev) : -ETIME;
delta = min(delta, dev->max_delta_ns);
...
rc = dev->set_next_event((unsigned long)clc, dev);
```

对偏移为 Δ 的从核（本地 ktime = 全局 ± Δ）：

- Δ 为正（本地 ktime 比 do_timer 域"快"）→ delta 为大负数 → `force=true` ⇒ 编 **min delta**
  → 立即触发 → 反复如此（中断风暴 + tick 逻辑空转）。
- Δ 为负（本地 ktime "慢"）→ delta 大正数 → 被 clamp 到 `dev->max_delta_ns`。
  本板 tick device 是 MCT local timer，`clockevents_config_and_register(evt, clk_rate/2, 0xf, 0x7fffffff)`
  （`exynos_mct.c:487`）⇒ `max_delta = 0x7fffffff cycles @12 MHz = 178.96 s`
  → **该 CPU 一次睡 ~179 秒，反复如此 ≈ 永久静默**。

这与实测完全吻合：`maxcpus=2` 时第一个从核（A57）上线后进入 idle，整机静默；
`nohz=off` 下 `tick_nohz_activate()` 因 `!tick_nohz_enabled` 直接返回
（`tick-sched.c:1392-1398`），`ts->nohz_mode = NOHZ_MODE_INACTIVE` ⇒
`can_stop_idle_tick()` 永远返回 false（`tick-sched.c:1052` 附近）⇒ **根本不走停 tick 路径**，
于是 8 核正常。

> 补充：`nohz=off` 并不能让 `clock_settime` 正常工作（§4 是独立路径，且 timekeeping
> 本身已经被污染），它只是把"从核从 idle 起就睡死"这个更早的故障点绕开。

## 4. 症状 4：`clock_settime` 之后永久挂死

### 4.1 `do_settimeofday64()` 在本 CPU 的计数器域里更新全局 timekeeper

`kernel/time/timekeeping.c:1312-1355`：

```c
int do_settimeofday64(const struct timespec64 *ts)
{
	raw_spin_lock_irqsave(&timekeeper_lock, flags);
	write_seqcount_begin(&tk_core.seq);

	timekeeping_forward_now(tk);          /* ← 关键：在【调用者 CPU】上读 clocksource */
	xt = tk_xtime(tk);
	ts_delta = timespec64_sub(*ts, xt);
	...
	tk_set_wall_to_mono(tk, timespec64_sub(tk->wall_to_monotonic, ts_delta));

	timekeeping_update(tk, TK_CLEAR_NTP | TK_MIRROR | TK_CLOCK_WAS_SET);
	...
	clock_was_set(CLOCK_SET_WALL);        /* → 给相关 CPU 发 IPI 重新编程 hrtimer */
```

`timekeeping_forward_now()`（`timekeeping.c:794-810`）：

```c
static void timekeeping_forward_now(struct timekeeper *tk)
{
	cycle_now = tk_clock_read(&tk->tkr_mono);       /* 本核 CNTVCT */
	delta = clocksource_delta(cycle_now, tk->tkr_mono.cycle_last, ...);
	tk->tkr_mono.cycle_last = cycle_now;            /* ★ 全局 cycle_last 被搬到本核的计数器域 */
	tk->tkr_mono.xtime_nsec += delta * tk->tkr_mono.mult;   /* xtime 被错误推进 Δ */
	...
}
```

`cycle_last` 是**全局**的（上一次在 do_timer CPU 上推进时的值）。若调用 `settimeofday`
的进程跑在偏移为 Δ 的 CPU 上，`delta` 就多算了 Δ，`xtime` 前跳 Δ，并把全局
`cycle_last` 改成"该 CPU 的计数器值"。

### 4.2 其它 CPU 立刻看到 2^56 级时间跳变

`cycle_last` 被改成 CPU_X 的值后，CPU_Y 再读 timekeeper
（`timekeeping_get_delta()` → `timekeeping_get_ns()`，`timekeeping.c:240-275/384`）：

```c
delta = clocksource_delta(now, last, mask);   /* = (now - last) & mask，见下 */
```

`kernel/time/timekeeping_internal.h:19-33`：

```c
static inline u64 clocksource_delta(u64 now, u64 last, u64 mask)
{
	u64 ret = (now - last) & mask;
	/* Prevent time going backwards by checking the MSB of mask in the result.
	 * If set, return 0. */
	return ret & ~(mask >> 1) ? 0 : ret;
}
```

- `CONFIG_CLOCKSOURCE_VALIDATE_LAST_CYCLE` **未开** ⇒ 走简单版 `(now - last) & mask`。
- 56 位 mask 下，负差（now 比 last 小 Δ）会变成 `2^56 − Δ` ⇒ 时间**向前跳 ≈ 95 年**
  （2^56 cycles / 24 MHz = 3.002e9 s ≈ 95.1 年）。
- 于是所有 hrtimer 的到期时间都落在"95 年后"的绝对值上，编程时 `clockevents_program_event()`
  又把 delta clamp 到 `max_delta_ns`（MCT 178.96 s）……**任何 `sleep()`、`sync`、看门狗、
  systemd 事件循环都永远等不到**。

### 4.3 `clock_was_set()` 的 IPI 还会再污染一次

`kernel/time/hrtimer.c:947-990`：

```c

```

`retrigger_next_event()`（`hrtimer.c:773-800`）→ `hrtimer_update_base()` 用
`ktime_get_update_offsets_now()`，其内部同样走 `ktime_get_mono_fast_ns()`（读本核 clocksource）。
在计数器域已被打乱的情况下，各核的 base offset / 重新编程继续踩坑，表现为
"settimeofday 返回后整个系统静止"。**注意这不是 IPI 投递失败**：8 核能起来、`smp:Brought up
1 node, 8 CPUs` 都证明 GIC/IPI 正常；坏的是"时间"。

## 5. MCT / arch timer / GIC 的实际角色（回答阶段 1 的第 3、4 问）

### 5.1 本树里两套硬件的最终角色

| 硬件 | 注册内容 | rating | 最终是否生效 |
|---|---|---|---|
| `exynos_mct.c` | `clocksource mct-frc`（32 位） | `MCT_CLKSOURCE_RATING = 350`（arm64） | ❌ 输给 arch_sys_counter(400) |
| `exynos_mct.c` | `sched_clock`（32 位，先注册） | - | ❌ 被 arch timer 的 56 位覆盖（同 24 MHz） |
| `exynos_mct.c` | `mct_tickN`（per-CPU clockevent，SPI） | 默认 350，**zeroflte 打到 500**（`exynos_mct.c:471-478`） | ✅ **就是当前 tick device** |
| `exynos_mct.c` | `mct-comp`（全局 comparator） | 250 | ❌ |
| `arm_arch_timer.c` | `clocksource arch_sys_counter` | 400 | ✅ **当前 clocksource** |
| `arm_arch_timer.c` | per-CPU clockevent（PPI 14） | 450 | ❌ 输给 MCT 500 |
| `arm_arch_timer.c` | `sched_clock`（56 位） | - | ✅ **当前 sched_clock，但读的是 CNTVCT** |

⇒ 当前结构 = **"MCT clockevent + arch timer clocksource + arch timer sched_clock(CNTVCT)"**，
和原厂"MCT clockevent + arch timer physical clocksource"只差**计数器选错**这一项。

### 5.2 混用两套硬件会不会 skew？

**不会。** clockevent 的编程永远用"相对 delta"（`clockevents_program_event()` 里
`delta = expires - ktime_get()`，再由 `set_next_event(cycles)` 写入相对计数），与 counter 的
绝对基址无关；clocksource 与 sched_clock 也共享同一 rate（都由 24 MHz `fin_pll` 派生）。
原厂方案本身就是混用。**唯一不能容忍的是"同一个 ktime 全局域里存在多个不同的 counter 偏移"**，
这正是 CNTVOFF 造成的。修复后 CNTPCT 全局唯一，混用无碍。

### 5.3 GIC / IPI 路径

- 本板 GIC 是 `arm,gic-400`（`exynos7.dtsi:166-175`），8 核 bringup、IPI reschedule、
  `smp:Brought up 1 node, 8 CPUs` 均已实测通过 ⇒ GIC/IPI 分发本身没问题。
- `clock_was_set()` 的 `smp_call_function_many(..., wait=1)` 在"时间正确"时正常工作；
  挂死的原因是目标 CPU 早已被错误时间编程成"睡到下个世纪"（§3/§4），不是 IPI 送不到。

### 5.4 RCU stall 与 RT throttling 是次生现象

- RCU stall 检测用 `jiffies`（全局）+ 各 CPU 的 quiescent-state 上报；当从核被错误地
  sleep 179 s / 或被 nohz 逻辑困住时，QS 无法上报；同时 stall 报告里的时间戳本身来自
  坏掉的 sched_clock ⇒ 出现 `fqs=0`、8 CPU 全 stall 的刷屏。
- `sched: RT throttling activated`：RT 带宽计时基于 `rq_clock()`，而
  `rq_clock` 的来源是 `sched_clock_cpu()`（`kernel/sched/clock.c:484-490` 在无
  `HAVE_UNSTABLE_SCHED_CLOCK` 时就是 `sched_clock()`）⇒ 每核偏移导致 RT 时间被误算、
  误触发 throttle。
- 两者都不需要单独修，根因修复后应自动消失；`rcu_cpu_stall_suppress=1` 只是把"报警器"关了。

## 6. 为什么 VM（QEMU virt）完全正常

1. QEMU 正确实现 arm64 通用定时器：CNTVOFF=0（且 vCPU 的虚拟计数器与系统计数器一致）。
2. 我们的修复是 **DT 属性驱动**的：QEMU virt 的 DTB 没有
   `arm,cpu-registers-not-fw-configured` / `use-physical-timer` ⇒ workaround 不匹配 ⇒
   仍走 CNTVCT，行为与未打补丁完全一致（回归安全）。
3. 这也是为什么**不能**把该属性写进 SoC 级 `exynos7.dtsi` 的 `/timer` 节点（会影响
   exynos7-espresso 等其它板）；正确位置是**板级 DTS**（zeroflte），与固件行为绑定。

## 7. 修复方案

### 7.1 方案对比

| 方案 | 内容 | 结论 |
|---|---|---|
| **A. 采用** | arm64 arch timer 识别 DT 属性，把 counter 读重定向到 CNTPCT（OOL workaround） | ✅ 改动最小、DT 驱动、QEMU 不回归、三星 2018 同款实现 |
| B. 固件侧 | 让 S-Boot/secure monitor 在 EL2 给所有 CPU 写 CNTVOFF=0，或让内核从 EL2 进入 | ❌ 固件不可改（S-Boot 签名）；uniLoader 在 EL1 无 EL2 可执行代码 |
| C. 改用 MCT FRC 做全局时基 | MCT FRC 是 MCT 块里的单一时钟，全 CPU 一致 | ⚠️ 32 位、需禁用 arch timer sched_clock，改动比 A 大；留作 A 失败时的备选（见 §7.6） |
| D. 禁用 MCT（p203） | `mct_init_dt()` 直接 `return -ENODEV` | ❌ 不解决 counter 路径问题；还会把 clockevent 换成未验证的 arch timer 物理 PPI，引入新风险 |

### 7.2 采用方案 A：用 OOL erratum 框架重定向 counter

**核心思路**（借三星 2018 Exynos5433 补丁的招法）：

1. 在 `ool_workarounds[]`（`arm_arch_timer.c:442-518`）注册一个 `ate_match_dt` 条目，
   `.id = "arm,cpu-registers-not-fw-configured"`，`.read_cntvct_el0 = arch_counter_get_cntpct`。
2. `arch_timer_of_init()` 里的 `arch_timer_check_ool_workaround(ate_match_dt, np)`
   （HEAD 行 1430）会匹配 `/timer` 节点上的属性 → `arch_timer_enable_workaround()`：
   - 把 workaround 指针写进所有 CPU 的 `timer_unstable_counter_workaround`；
   - `atomic_set(&timer_unstable_counter_workaround_in_use, 1)` ⇒ `arch_timer_counter_has_wa()==true`；
   - 因为 `read_cntvct_el0` 非空，**自动**把 `vdso_default` / `clocksource_counter.vdso_clock_mode`
     置为 `VDSO_CLOCKMODE_NONE`。
3. 之后 `arch_counter_register()` 走 arm64/EL1 的"虚拟"分支时：
   `rd = arch_counter_get_cntvct_stable`，而 `__arch_counter_get_cntvct_stable()`
   通过 `arch_timer_reg_read_stable(cntvct_el0)` / `erratum_handler(read_cntvct_el0)`
   （`arch/arm64/include/asm/arch_timer.h:24-41, 89-92, 191-198`）**实际调用我们注册的
   `arch_counter_get_cntpct()`**。
   ⇒ `arch_timer_read_counter`（clocksource/timecounter/get_cycles）、`sched_clock`（`scr`）
   全部变成 CNTPCT；clockevent 本来就走物理 timer/PPI（banner 已打印 `(phys)`），自然一致。
4. 匹配对象是 `/timer` 节点本身（`arch_timer_of_init` 的 `np`），所以属性必须放在 `/timer` 下。
   - uniLoader 已在 `main/diag.c:219-221` 给 `/timer` 注入该属性（本板一直有）；
   - p204 另外在板级 DTS `exynos7420-zeroflte.dts` 的 `&{/timer}` 里显式写上，双保险。

**安全性论证**：

- CNTPCT 由 SoC 全局 System Counter 驱动，天然全 CPU 一致（原厂 `use-physical-timer`
  和三星 2018 补丁都押注这一点）。
- EL1 读 CNTPCT 可行：`CNTHCTL_EL2.EL1PCTEN` 已由固件置位，且 loader 与内核都在 EL1
  实测读过 CNTPCT（§1.6）。
- vDSO 自动关闭 archtimer 模式 ⇒ 用户态 `gettimeofday` 走 syscall，时间正确
  （性能损失可忽略，换取正确性）。
- QEMU 无该 DT 属性 ⇒ 不受影响。

### 7.3 为什么不能只靠 `arm,cpu-registers-not-fw-configured` 的现有 arm32 逻辑

HEAD `arm_arch_timer.c:1436-1441`：

```c
	if (IS_ENABLED(CONFIG_ARM) &&
	    of_property_read_bool(np, "arm,cpu-registers-not-fw-configured"))
		arch_timer_uses_ppi = ARCH_TIMER_PHYS_SECURE_PPI;
	else
		arch_timer_uses_ppi = arch_timer_select_ppi();
```

- 该逻辑被 `IS_ENABLED(CONFIG_ARM)` 挡住，**arm64 上完全无效**；
- 而且它只改 PPI 选择（事件用哪个 timer），**不改 counter 读取**，即使放开也不够。
- 因此必须走 §7.2 的 workaround 路径（这正是 2018 年 Marek 补丁被 arm64 maintainer 拒绝、
  却仍被证明技术上可行的原因）。

### 7.5 为什么 p203（禁用 MCT）是错误方向

1. 时间戳/时间keeper 乱源是 **counter 读取路径（CNTVCT）**，与 MCT 无关（§2.4）。
   禁用 MCT 后 arch timer 的 sched_clock/clocksource **仍然读 CNTVCT**，症状不变。
2. 禁用 MCT 会把 tick device 换成 arch timer 的物理 PPI（rating 450），而这条路径
   在本板**从未验证过**；且本板 DT 没有 `always-on` 属性，
   `arch_timer_c3stop = true`（HEAD `arm_arch_timer.c:1427`），arch timer clockevent 会被
   打上 `CLOCK_EVT_FEAT_C3STOP`，idle 时还要依赖 broadcast（`tick_setup_hrtimer_broadcast()`，
   `arch/arm64/kernel/time.c:70`），又多一层变量。
3. 结论：p203 不测，直接 p204。

### 7.6 备选方案 C（若 p204 意外失败）

如果真机上发现 **EL1 读 CNTPCT 会被 trap**（p204 在 timer_probe 前后静默死、marker 停在
time_init 之前），则改走"MCT FRC 全局时基"备选：

- 保留 MCT（vendor clockevent），但让 `sched_clock` 用 MCT FRC（全局 32 位）：
  - 可用 bootarg 快速验证 `clocksource=mct-frc` 只验证 timekeeping（sched_clock 仍是 CNTVCT）；
  - 正式做法：arm timer 不再注册 sched_clock，或 MCT 的 sched_clock 不再被覆盖
    （参考 2025 年上游 "exynos_mct: Don't register as a sched_clock on arm64" 的逆操作），
    同时 MCT FRC（32 位）作为 clocksource 时 178.96 s 回绕由 clocksource 框架处理
    （`max_idle_ns=79635851949 ns ≈ 79.6 s < 178.96/2`，可行）。
- 代价：sched_clock 读 MCT 是 MMIO，慢；但正确性优先。

### 7.7 可选清理（p204 通过后再做，p205）

1. 删掉 `arch_timer_starting_cpu()` 里的 DSH 诊断打印（或留作 debug option）。
2. 让 MCT 支持 vendor 的 `use-clockevent-only`（不再注册 mct-frc clocksource / sched_clock），
   等价于 2025 年上游补丁 `clocksource/drivers/exynos_mct: Don't register as a sched_clock on arm64`
   （https://lkml.org/lkml/2025/6/18/1754 ，已进 tip/timers-clocksource）。
   **注意**：这不是修 bug 必需，p204 故意不做以免混淆变量；现状下 MCT clocksource(rating 350)
   输给 arch timer(400)、MCT sched_clock 被同频的 arch timer 覆盖，功能无碍。
3. 去掉 bootargs 里的 `nohz=off` / `rcu_cpu_stall_suppress=1`，验证 8 核 tickless idle。
4. 上游化讨论：`arm,cpu-registers-not-fw-configured` 在 arm64 的支持曾被 Marc Zyngier 明确
   拒绝（要求修固件），所以这块补丁**大概率只能 local carry**；若哪天能改 S-Boot/EL3 固件
   把 CNTVOFF 清零，则补丁可整体删除（DT 属性去掉即回退到标准行为）。

## 9. 硬件验证步骤（给 Lead）

### 9.1 烧写

烧 `out/p204-padded.img`（boot 分区镜像；与往常 pNNN 流程相同）。bootargs **先不改**
（保留 `nohz=off`、`rcu_cpu_stall_suppress=1`）。

### 9.2 通过标准（按顺序）

> 本目录下有两个现成脚本，直接把抓到的 dmesg 文本喂进去即可：
> - `./p204-timestamp-check.py dmesg.txt` —— 时间戳单调性硬判定（回退/大跨步列表）
> - `./p204-dsh-report.py dmesg.txt` —— 提取 8 行 DSH 诊断、生成每核偏移报表并自动判读

1. **时间戳单调**：早期 dmesg（0~6 s）所有 `[ N.NNNNNN]` 单调递增。
   快速脚本：
   ```bash
   grep -oE '^\[ *[0-9]+\.[0-9]+\]' dmesg.txt | tr -d '[] ' | \
     awk 'NR>1 && $1+0 < prev-0.000001 {print "NOT MONOTONIC at line " NR ": " prev " -> " $1} {prev=$1}'
   ```
   期望：无输出。允许的例外：时钟被 `adjtimex` 微调（ns 级）、或两次 printk 之间本身有长停顿。
2. **workaround 生效地标**（`loglevel=8` 下必现，出现一次）：
   ```
   [    0.000xxx] arch_timer: Enabling global workaround for DSH: broken Exynos7420 firmware (CNTVOFF not configured)
   ```
2b. **每核"隔断虚拟计数器 EL0 访问"地标**（8 行；OOL workaround 框架的自动副作用，正常）：
   ```
   arch_timer: CPU0: Trapping CNTVCT access
   ...
   arch_timer: CPU7: Trapping CNTVCT access
   ```
   原因：`arch_counter_set_user_access()`（`arm_arch_timer.c:1027-1032`）检测到
   `arch_timer_this_cpu_has_cntvct_wa()` 为真时，不置 `CNTKCTL_EL1.EL0VCTEN` 且
   清掉用户态访问位（用户态读 CNTVCT 会被 trap）。vDSO fast path 已关闭，用户态
   一律走 syscall，所以这是**期望行为**：防止用户态再读到带 per-CPU 偏移的 CNTVCT。

3. **每核 CNTVOFF 硬证据**（8 行；p204 新增诊断）：
   ```
   arch_timer: DSH: CPU0 CNTVCT=... CNTPCT=... CNTVOFF_implied=... ticks (~... ms)
   ...
   arch_timer: DSH: CPU7 ...
   ```
   - 期望：各 CPU 的 `CNTVOFF_implied`（= CNTVCT−CNTPCT = **−CNTVOFF_EL2**）**明显不同**，
     量级可达 10^9~10^11 ticks（几十秒~几千秒 @24 MHz）。
   - 这些行的打印时间戳应彼此单调（因为 sched_clock 已是全局 CNTPCT）。
   - 若全部为 0 → CNTVOFF 假设被证伪，请把完整 dmesg 发我重新分析。
4. **systemd 越过 clock advance**：
   `System time before build time, advancing clock.` 之后必须继续出现
   `Detected architecture arm64`、mount/udev 等后续日志（p196 基线在这里永久静默）。
5. **`date -s` 回归测试**（p200 复现法）：在 ramdisk rc / 或进系统后执行
   `date -s "2026-10-19 03:00:00" && sleep 2 && echo SLEEP-OK && sync`。
   期望：`SLEEP-OK` 正常打印，不再挂死。
6. **可选旁证**（不烧新镜像也能做）：用旧镜像（p196/p199，MCT 正常）把 bootargs 里的
   `clocksource=arch_sys_counter` 换成 `clocksource=mct-frc`：
   - 预期：**时间戳仍然乱跳**（sched_clock 仍走 CNTVCT），
     但 `date -s` + `sleep 2` **不再挂**（timekeeping 的 clocksource 变成全局 MCT FRC）。
   - 这可以独立证明"时间戳"和"clock_settime 挂死"同源于 counter 域不一致。

### 9.3 第二阶段（p204 全过之后）：验证 tickless idle

1. 改 uniLoader bootargs，去掉 `nohz=off`（建议同时去掉 `rcu_cpu_stall_suppress=1`，
   以便看到是否有真 stall）。
2. 期望：`smp: Brought up 1 node, 8 CPUs` 正常；`cat /sys/devices/system/cpu/online` = `0-7`；
   idle 一段时间无 RCU stall、无静默。
3. `grep -c "rcu: INFO: rcu_preempt" dmesg` 应为 0。

### 9.4 失败判读表

| 现象 | 推断 | 下一步 |
|---|---|---|
| 完全没有控制台输出，loader marker 停在 `time_init` 之前 | EL1 读 CNTPCT 被 trap（CNTHCTL.EL1PCTEN=0） | 走备选方案 C（§7.6）；先别急，概率低（loader/内核都实测读过 CNTPCT） |
