- 上游任务：解决"用着用着突然黑屏/没有电量显示"（电池电量计 + 充电器）+ 解释 p216 用户态挂死

## 0. TL;DR

1. **p216 的"用户态挂死"几乎不可能是电池驱动补丁造成的**。我把 p213/p216 的
   **内嵌内核 config、反编译 DTB、内嵌 kernel Image、源码文件 mtime 全部逐项对比**：
   - 内核 config 差异**恰好 3 个符号**（`FUEL_GAUGE_MAX77843` / `CHARGER_MAX77843` / `MFD_MAX77843`），无隐藏依赖；
   - DTB 差异只有：一个**无人引用的 fixed-clock**、一个**保持 disabled 的 hsi2c_1**（其下 2 个电池 child 不会被实例化）、以及 phandle 重编号；
   - p213 与 p216 之间源码变化**只有**两个新驱动 + Kconfig/Makefile + .config；`simpledrm` 的快拷贝优化是在 **p213 构建之前**（22:07:40 vs p213 #246 22:07:46）就已加入，**两个镜像都有**；
   - 三个驱动**没有设备节点就不会 probe**（MFD 需要 `max77843@66`，p216 DTB 里没有）⇒ H1/H2/H3/H5/H6 全部排除。

2. **marker 0x4500 的语义已从源码确认**：`init/main.c:1410-1423` 的
   `run_init_process()` 只有在 `kernel_execve()` **返回 0（/init exec 成功）**时才调用
   `dsh_diag_boot_complete()` → 写 0x4500。`dsh_mark()` 会 `dc civac + dsb` 刷 DRAM。
   ⇒ **p216 内核确实完成了到用户态 /init 的交接**。
   ⚠️ 但 loader 在**下一次启动、覆盖内核镜像之前**才读这个 marker
   （`uniLoader/main/boot.c:197-228`）：必须确认 0x4500 是 **p216 崩溃后下一次 loader 会话**
   读到的；如果是"为了启动 p216 而进 loader"那一刻读到的，那是 **p213 上次成功启动的残留**。

3. **头号新嫌疑：供电/电池欠压（H-power）**，而不是软件挂死。
   主线没有充电管理（本阶段驱动只读，S-Boot 的充电参数是唯一来源），而 p212/p213 的
   "用着用着突然黑屏"本身就极像掉电；p213→p216 之间有一个小时的 GNOME/WiFi/反复挂死测试，
   若电池在此期间净放电，p216 启动到 userspace 高负载阶段（systemd/udev/GNOME 拉起）时
   欠压/掉电，表现就是：**marker 已到 0x4500（用户态已开始）+ 之后完全无声 + USB 消失 +
   无 panic**。这与全部观测一致。
   （loader 的 MUIC 日志 `[muic] id=b5 status=1f/41 ...` 说明测试时 VBUS 正常接入，
   但 VBUS 存在 ≠ 充电已使能/电流足够。）

4. **i2c-gpio 电池方案可行，且有一个"金标准"证据**：
   loader 自己**已经在 GPD2[2:3] 上 bit-bang MAX77843 MUIC 并成功读到 `id=0xb5`**
   （`uniLoader/drivers/usb-console/muic.c`）。内核 `i2c-gpio` 的开漏实现
   （gpiolib `gpio_set_open_drain_value_commit()`：1→direction_input，0→direction_output(0)）
   与 loader 的 `line(high)=input / line(low)=output-low` **语义完全等价**；
   DTS 里的 flags/延时也与同板已工作的 gpg3 i2c-gpio 节点一致。
   ⇒ **p217 的 i2c-gpio 方案预期可用**，风险主要是 gpd2 上拉是否仍在（loader 已依赖它，
   说明板级上拉存在）与 probe 顺序。

5. **已做好零重建的单变量诊断镜像**（p216 的 kernel/dtb/ramdisk 逐字节不变，只有 bootargs 9 字节不同）：
   `/tmp/p216diag/p216diag-padded.img`
   - sha256 `08f3728c36d0b990fd65c3ae469e2dce1c6fa86846a668ba54edac11ba5562df`
   - Samsung sha1 `acfb4a3e8afbd289661380f4e40bb70f764fc0d3`
   烧它一次即可看到 p216 用户态到底走到哪（详见 §2）。

## 1. p216 用户态挂死：证据与根因判断

### 1.1 三个镜像的差别（全部实测核对，不依赖记忆）

| 镜像 | 构建时间/内核 banner | config 电池项 | DTB 电池节点 | hsi2c_1 | 结果 |
|---|---|---|---|---|---|
| p212 | 21:07 | 无 | 无 | disabled（默认） | ✅ 已知可用 |
| p213 | #246 `Mon Oct 19 22:07:46` | 无 | 无 | disabled | ✅ 对照可用 |
| p214 | 22:42 | 无 | 无 | disabled | （中间对照构建） |
| p215 | #247 左右 22:47 | 3 项全开 | 有（enable） | **okay** | ❌ AXI 挂死 |
| p216 | #249 `Mon Oct 19 22:57:16` | 3 项全开 | 有 | **disabled** | ❌ 用户态挂死 |

**实测核对方法**：从 loader 二进制中提取内嵌的 `kernel/config_data.gz`（`IKCFG_ST/ED` 标记）并 diff。

```
$ diff <(extract config p213) <(extract config p216)
+CONFIG_FUEL_GAUGE_MAX77843=y
+CONFIG_CHARGER_MAX77843=y
+CONFIG_MFD_MAX77843=y
（仅 13 行 diff，其余全部相同）
```

**DTB 实测核对**：从 loader 中提取 DTB（sha 与 manifest 完全一致），dtc 反编译后 diff：

```diff
# p216 相对 p213 的真实内容差异（过滤 phandle 重编号后）
+			clock-frequency = <0x61a80>;        /* hsi2c_1 prope… 400kHz */
+			fuelgauge@36 { compatible = "maxim,max77843-fuelgauge"; reg = <0x36>; };
+			charger@69   { compatible = "maxim,max77843-charger";   reg = <0x69>; };
+	clock-hsi2c1 { compatible = "fixed-clock"; clock-frequency = <0x7ed6b40>; clock-output-names = "sclk_hsi2c1"; };
# i2c@13650000 节点本体：
			status = "disabled";               /* 关键：p216 里仍是 disabled */
```

- `clock-hsi2c1` 与 **p213 里已经工作** 的 WiFi PCIe 时钟 `clock-hsi2c7`
  是**同一种写法/同一个频率**（p213 DTB 中已存在 hsi2c7 fixed-clock），且没有任何
  `status="okay"` 的设备引用 `clock-hsi2c1` ⇒ **对 CCF 无运行期影响**；
- `i2c@13650000` 保持 `disabled` ⇒ 控制器不 probe；其 children 不会被
  `of_i2c_register_devices()` 实例化 ⇒ **`fuelgauge@36`/`charger@69` 不会 probe**；
- 其余全是 phandle 重编号（新增节点导致，自洽的）。

**源码 mtime 核对**（22:08–22:57，即 p213 构建后到 p216 构建前）：

```
drivers/power/supply/max77843_fuelgauge.c
drivers/power/supply/max77843-charger.c
drivers/power/supply/Kconfig
drivers/power/supply/Makefile
（+ .config/.config.old/kernel/config_data* 构建产物）
```

**没有其它源文件在这一窗口内被修改**。
特别地：`drivers/gpu/drm/tiny/simpledrm.c` 的 G9209 快拷贝优化 mtime 是 **22:07:40**，
而 p213 的内核 banner 是 **22:07:46**（#246）⇒ **p213 已经包含该优化**，它不是 p216 的变量。

### 1.2 marker 0x4500 的真实语义（源码）

`init/main.c`（DSH 补丁）：

```c
static int run_init_process(const char *init_filename)
{
	...
	ret = kernel_execve(init_filename, argv_init, envp_init);
	if (!ret)
		dsh_diag_boot_complete();      /* L1419-1422 */
	return ret;
}
```

`init/dsh_watchdog.c:122-128`：

```c
void dsh_diag_boot_complete(void)
{
	if (READ_ONCE(dsh_diag_test_mode) != 1) {
		dsh_mark(0x4500);
		return;
	}
	...
}
```

`init/dsh_debug.c` 的 `dsh_mark()`：写入 `dsh_diag.stage`、`dsh_marker`，并执行
`dc civac + dsb sy`（保证复位后 DRAM 里是真值）。

结论：**0x4500 = 内核成功 exec 了 /init，即将返回用户态**。它**不能**说明 userspace 走了多远。

⚠️ **读取时机陷阱**：`uniLoader/main/boot.c`：

```c
void boot_kernel(void *dt, void *kernel, void *ramdisk)
{
	dsh_previous_boot();          /* 先读 marker/regs（此时内存还是上一次内核的残留） */
	dsh_previous_record();
	...
	printk("Booting kernel...\n");
	arch_load_kernel(...);        /* 之后才把新 Image 拷到 0x90000000，覆盖 marker 区域 */
}
```

⇒ **loader 打印的 `[prev] marker=` 描述的是"上一次成功/失败的内核运行"**。
如果你是在“为了启动 p216 而进入 loader”的那次会话里读到的 0x4500，那它来自 p213 的成功启动，
而不是 p216。请核对测试记录。

### 1.4 为什么头号嫌疑是供电（H-power）

1. **原始症状**（本轮任务的起点）就是"用着用着突然黑屏/没有电量显示"——
   在主线没有电量计、没有充电管理的状态下，"黑屏"最直接的解释就是**电池掉到关机电压**。
2. **p216 阶段主线的充电控制并不存在**：本轮驱动**只读**，S-Boot 设置的
   `CHG_CNFG_00/02/09` 是唯一配置；且 p215 的 AXI 挂死导致多次复位/重启，
   测试时长（22:07–23:08 约 1 小时，含 GNOME/GPU/WiFi）可能让电池净放电。
3. **失败形态高度吻合掉电**：
   - marker=0x4500（内核已把控制权交给 /init，**说明内核没挂**）；
   - 之后完全无声、无 panic、无 journal、USB 消失、GNOME 不出；
   - 若在 userspace 高负载（systemd 拉起 udevd/NM/GDM/GPU）瞬间欠压，表现正是如此。
4. **loader 的 MUIC 日志**（p215_raw.log）：
   `[muic] id=b5 status=1f/41 CDETCTRL1=2d CTRL1=00` ——
   loader 的路由条件 `(s2 & BIT(6))` 满足，说明当时**是带 VBUS 的正常 B 线**；
   但这只证明"插着 USB"，**不证明充电电流已使能/足够**（屏幕+WiFi+GPU 功耗可能大于 USB 供电）。
5. p213 能跑 GNOME 不代表 p216 时电量和 p213 测试时一样。

**需要 Lead 确认的关键证据**（任一即可大幅缩小范围）：
- p216 测试前/后的电池电量或电压（TWRP 状态栏、原厂 ROM、或 loader 新增 FG 读取命令）；
- p216 失败后手机是**完全断电/黑屏无反应**，还是**还停在 loader/可交互**；
- p216 失败后 USB 是否**再也没有枚举**（`lsusb` 无 1209:9210）；
- 是否出现"等待一段时间/充电后又可以启动"的现象。

### 1.5 次号嫌疑：观测假象

- p216 bootargs：`loglevel=4 systemd.log_level=warning` ⇒ 内核 console 只剩 warning，
  systemd 只写 journal，**userspace 阶段串口全程静音**（90 秒级启动看起来就像挂了）。
- loader→kernel 切换时 USB **会重新枚举**；若用只 open 一次 `/dev/ttyACM0` 的 v1 脚本抓取，
  boot 之后的所有输出（包括 ramdisk rc 的 `dsh_log`）都会丢失 ——
  已在上一轮 systemd 分析中给出修正版 `/tmp/test_debian_boot_v2.py`（自动重连 + raw log）。
- 判定"是否真的挂"的证据：**p216 测试的 raw USB 日志**（不是过滤后的行）。

### 2.3 电池电压/供电检查

- **最快的**：TWRP 状态栏/原厂系统读电量；或开机进入原厂 ROM 看电量。
- **建议给 loader 加一个 `bat` 命令**（代码基础已有）：
  loader 的 `drivers/usb-console/muic.c` 已实现 GPD2[2:3] bit-bang I2C
  （MUIC 地址 0x4a/0x4b，即 7-bit 0x25），**把同样的读写函数复用到 FG（7-bit 0x36，
  写地址 0x6c/读 0x6d）** 即可读：
  - `VCELL` reg `0x09`（16-bit LE，78.125 µV/LSB）
  - `SOC` reg `0x06`（高字节整数 %）
  - `CHG_DTLS_00(0xB3)` / `CHG_DTLS_01(0xB4)`（charger 地址 0x69 → 写 0xd2/读 0xd3）
  
  这样每次进 loader 都能先看电池电压/电量/充电状态，再决定是否 boot。
  （实现要点：单独 `#define` FG/CHG 的 dev-addr 参数，复用 `start/send_byte/read_reg`；
  只读不改配置，安全。）

### 2.4 供电相关的低风险改进

- 测试前保证电量 > 60%（若测得 < 3.6V 不要跑 GNOME 测试）；
- systemd 侧可加低电保护/日志：等 p217 电池驱动就绪后，用 upower 或 udev 规则，
  在 `capacity < 5%` 时进入低功耗 target；
- 本轮驱动只读不会写充电配置；**第二步再加充电控制**（充电使能/电流/浮充电压），
  之前不要靠 Linux 充电。

## 3. i2c-gpio 电池方案（p217+）：设计与可行性论证

### 3.1 为什么必须绕开 hsi2c_1

p215 实测：使能 `hsi2c_1` 后，内核第一次读 `0x13650000` 控制器寄存器即 **AXI 静默挂死**
（无 oops，看门狗复位）。根因：CMU_PERIC0（`0x13610000`）的 HSI2C1 门控被 S-Boot 关闭，
而本板的 CMU_PERIC0 节点被整体 disable，CCF 无法打开它；fixed-clock 只解决"时钟对象缺失"，
不解决"硬件门控"。⇒ **i2c-gpio 完全绕开该地址与 PERIC0，是正确路线**。

### 3.2 金标准证据：loader 已经在这两根线上成功访问 MAX77843

`uniLoader/drivers/usb-console/muic.c`（loader 裸机代码）：

```c
#define GPD2_CON 0x134700e0UL
#define GPD2_DAT 0x134700e4UL
#define SDA 2
#define SCL 3
/* Drive only low; release to the board pullups for a logic one. */
static void line(unsigned int pin, int high)
{ mask32(GPD2_CON, 15U << (pin * 4), (high ? 0U : 1U) << (pin * 4)); usb_udelay(5); }
...
int usb_muic_prepare(void)
{
	read_reg(0x00, &id) ... ;
	printk("[muic] id=%02x status=%02x/%02x ...", id, s1, s2, ...);
```

实测日志（`/tmp/p215_raw.log`）：`[muic] id=b5 status=1f/41 ...`
⇒ **GPD2[2:3] 上的 bit-bang I2C 可以工作、板级上拉存在、MAX77843 在该线上有响应**。
这正是电池芯片所在的总线（vendor：hsi2c_1 = GPD2[2:3]）。

内核 `i2c-gpio` 的开漏语义与 loader 完全一致（gpiolib 源码）：

```c
/* drivers/gpio/gpiolib.c:3006 */
static void gpio_set_open_drain_value_commit(struct gpio_desc *desc, bool value)
{
	if (value) ret = gc->direction_input(gc, offset);      /* 释放 → 输入，靠上拉拉高 */
	else { ret = gc->direction_output(gc, offset, 0); }   /* 拉低 → 输出 0 */
}
```

Samsung pinctrl 的 `samsung_gpio_set_direction()`
（`drivers/pinctrl/samsung/pinctrl-samsung.c:591`）：input→功能 0，output→`PIN_CON_FUNC_OUTPUT`(1)，
与 loader 的 `CON` 写法一致。⇒ **内核 i2c-gpio 在这两根线上会重演 loader 已验证的行为。**

同板已工作的 gpg3 i2c-gpio（s2mps15/s2mpb02，`exynos7420-zeroflte-touch-power.dtsi:19-33,63-67`）
使用的 DT flags 与新节点**完全相同**。

### 3.3 当前 DTS 实现审查（p217 默认分支，`#else`）

```dts
/ {
	i2c_max77843: i2c-max77843 {
		compatible = "i2c-gpio";
		sda-gpios = <&gpd2 2 (GPIO_ACTIVE_HIGH | GPIO_OPEN_DRAIN)>;
		scl-gpios = <&gpd2 3 (GPIO_ACTIVE_HIGH | GPIO_OPEN_DRAIN)>;
		i2c-gpio,delay-us = <5>;        /* 半周期 5us ≈ 100kHz，与 loader 相同 */
		i2c-gpio,timeout-ms = <100>;
		#address-cells = <1>; #size-cells = <0>;
		fuelgauge@36 { compatible = "maxim,max77843-fuelgauge"; reg = <0x36>; };
		charger@69   { compatible = "maxim,max77843-charger";   reg = <0x69>; };
	};
};
```

审查结论：**结构正确，可以按此构建 p217**。补充确认：
- `exynos7.dtsi` 的 `hsi2c_1`（`i2c@13650000`）默认就是 `status = "disabled"`
  （`arch/arm64/boot/dts/exynos/exynos7.dtsi:438-449`）⇒ 默认分支不碰它，安全；
- DTS 已包含 `<dt-bindings/gpio/gpio.h>`（L16），`GPIO_ACTIVE_HIGH|GPIO_OPEN_DRAIN` 可用；
- `i2c-gpio,timeout-ms` 在 6.6 驱动中受支持（`drivers/i2c/busses/i2c-gpio.c:310-318`）；
- `.config` 已有 `CONFIG_I2C_GPIO=y`（kbtest2/.config 已确认）。

### 3.4 建议的小改进（可选，降低变量）

1. **i2c-gpio 模式下把 `clock-hsi2c1` fixed-clock 也 gate 掉**（挪到 `#if DSH_MAX77843_USE_HSI2C1`
   里或删除），p217 默认构建不再包含任何无关 CCF 节点；
2. 可选给 i2c-gpio 节点加显式 pinctrl 状态，保证 gpd2-2/3 上拉，不依赖 S-Boot 残留
   （同板 gpg3 节点没加也能工作，所以这是"保险"而非"必须"）：
   ```dts
   &pinctrl_bus0 {
       i2c_max77843_bus: i2c-max77843-bus {
           samsung,pins = "gpd2-2", "gpd2-3";
           samsung,pin-function = <EXYNOS_PIN_FUNC_INPUT>;  /* GPIO */
           samsung,pin-pud = <EXYNOS_PIN_PULL_UP>;
       };
   };
   /* 并在 i2c-gpio 节点加：pinctrl-names="default"; pinctrl-0=<&i2c_max77843_bus>; */
   ```
3. `CONFIG_MFD_MAX77843` 可关（i2c-gpio 直连模式不需要）；`EXTCON_MAX77843` 保持 off。

### 3.5 预期日志与验证

成功时 dmesg（loglevel=8）应出现：

```
i2c-gpio i2c-max77843: using lines SDA:... SCL:...
max77843-fuelgauge 2-0036: MAX77843 fuel gauge registered
max77843-charger 2-0069: MAX77843 charger registered (read-only)
```

验证：

```sh
i2cdetect -l | grep -i max77843        # adapter 名称来自节点名 i2c-max77843
i2cdetect -y <N>                       # 期望 0x36、0x69 有响应（0x66/0x25 可选）
ls /sys/class/power_supply/            # max77843-fuelgauge / max77843-charger

```

### 3.6 失败对照表

| 现象 | 判据/下一步 |
|---|---|
| `fuel gauge does not respond: -121`(EIO) | bus 起了但 0x36 无应答：把 `delay-us` 加到 10（50kHz）；`devmem 0x134700e0` 看 gpd2 CON 是否 func1/0 切换；`i2cdetect -y N` 全扫 |
| `-6`(ENXIO)/全 `--` | 地址错/没供电/引脚反：核对 SDA=gpd2-2、SCL=gpd2-3（vendor），确认上拉；loader 的 `[muic] id=b5` 已证明 0x25 有响应，可先用 0x25 验证总线 |
| i2c-gpio 平台设备都没 probe | 反编译 DTB 确认 `i2c-max77843` 节点存在；`CONFIG_I2C_GPIO=y` |
| probe 卡在 `i2c-gpio:get_sda`（DSH 探针 0x71/0x72/0x73） | GPIO controller 未就绪 → probe defer；检查 `pinctrl_bus0` 是否先 probe（可能与 UFS 顺序有关） |
| upower 不显示电池 | `systemctl restart upower`；确认 `type=Battery`、`present=1` |

> 注：`drivers/i2c/busses/i2c-gpio.c` 里已有 DSH 探针
> `dsh_diag_note(0x71..0x73, ...)`（当前树），可用 dsh 诊断记录确认 probe 到哪一步。

## 4. 给 Lead 的测试步骤（按优先级）

1. **先取证（不烧机）**：TWRP 挂 sda20 → `journalctl -D …` 看 p216 那次 boot 的日志；
   `e2fsck -fy`；记录当前电池电量。
2. **确认 p216 失败形态**：手机是完全断电还是停在 loader？USB 是否消失？
   （决定 H-power 是否成立）
3. **满电后烧 p216diag**（§2.1）跑一次，用 `/tmp/test_debian_boot_v2.py` 抓 raw log：
   - 正常启动 ⇒ 电池补丁无罪，直接进 p217；
   - 停在某处 ⇒ 把最后 20 行发我，我按日志定位。
4. **p217（i2c-gpio）**：用当前树默认分支构建（当前 `diag.c` 已是 loglevel=8/info），
   烧后验证 §3.5；如果 `0x36/0x69` 有响应但 upower 不显示，再查 power_supply 属性。
5. 若怀疑供电：**在此之前先给 loader 加 `bat` 命令**（§2.3），每次 boot 前读
   `VCELL/SOC/CHG_DTLS`，把电压记录进测试日志；低电时不跑 GNOME 测试。

## 5. 风险与回滚

| 风险 | 缓解 |
|---|---|
| p216diag 只是改 bootargs，不改功能，随时可回退到 p216 | 刷回 `out/p216-padded.img` 即可 |
| p217 i2c-gpio 打不开 0x36（上拉/时序） | 先 `i2cdetect`；用 0x25（loader 已验证有响应）证明总线；`delay-us` 调到 10 |
| p217 电池驱动 probe 失败影响启动 | 纯 i2c 只读，失败只影响 power_supply 设备，不影响启动；可用 `status="disabled"` 一键回滚 |
| 充电电流/电压被误写 | 本阶段驱动**全部只读**，不写 CHG 配置 |
| 电池欠压导致测试误判 | 每次测试记录电量/电压；低电不跑高负载测试 |
