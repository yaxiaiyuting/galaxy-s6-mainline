## 二、根因：Exynos wakeup-EINT 的 chained handler 注册顺序 bug

### 2.1 定位过程

在手机上实测 `/proc/interrupts`：

```
 38: GIC-0 415  13470000.pinctrl    ← 其他 pinctrl 的父中断都在
 45: GIC-0 416  14870000.pinctrl
 ...
 59: gpa1 6 Level stmfts_irq        ← 触摸 IRQ 存在
 ❌ 没有 10580000.pinctrl 的父中断（wakeup-eint 的 chained handler）
```

但**设备树、SoC 数据、驱动 match 表、aliases 全部正确**：

```
wakeup-interrupt-controller: compatible = "samsung,exynos7-wakeup-eint"  ✓
                             interrupts = <GIC_SPI 16 LEVEL_HIGH>        ✓
                             interrupt-parent = <&gic>                   ✓
GIC phandle = 1                                                          ✓
aliases: pinctrl0 = &pinctrl_alive                                       ✓
exynos7_pin_ctrl[0].eint_wkup_init = exynos_eint_wkup_init               ✓
```

加调试日志（p247）后看到实际执行路径：

```
DSH-EINT: wkup_init called for 10580000.pinctrl, nr_banks=4
DSH-EINT: found wkup child wakeup-interrupt-controller
DSH-EINT: bank gpa0 eint_type=2 pins=8
DSH-EINT: bank gpa1 eint_type=2 pins=8
DSH-EINT: bank gpa2 eint_type=2 pins=8
DSH-EINT: bank gpa2 -> WKUP_MUX (no interrupts prop)
DSH-EINT: bank gpa3 eint_type=2 pins=8
DSH-EINT: bank gpa3 -> WKUP_MUX (no interrupts prop)
DSH-EINT: 10580000.pinctrl muxed_banks=2
DSH-EINT: parent chained IRQ = 37
DSH-EINT: chained handler registered, 2 banks
```

⇒ 函数是**执行了**的，但注册顺序有问题。

### 2.2 源码级根因

`drivers/pinctrl/samsung/pinctrl-exynos.c` 的 `exynos_eint_wkup_init()`：

```c
/* 原代码 */
irq = irq_of_parse_and_map(wkup_np, 0);
if (!irq) { dev_err(...); return 0; }

muxed_data = devm_kzalloc(...);

irq_set_chained_handler_and_data(irq, exynos_irq_demux_eint16_31, muxed_data);
// ↑ 此刻 muxed_data->nr_banks 还是 0，muxed_data->banks[] 是空的

bank = d->pin_banks;
idx = 0;
for (i = 0; i < d->nr_banks; ++i, ++bank) {
    if (bank->eint_type != EINT_TYPE_WKUP_MUX) continue;
    muxed_data->banks[idx++] = bank;
}
muxed_data->nr_banks = muxed_banks;    // ← 才在这里填
```

**中断注册瞬间到数据填充完成之间，如果 EINT 触发：**

```c
static void exynos_irq_demux_eint16_31(struct irq_desc *desc)
{
    ...
    for (i = 0; i < eintd->nr_banks; ++i)   // ← nr_banks == 0，循环不执行
        ...
}
```

⇒ **demux 什么都不做 → 中断源永远不被清除 → 硬件中断线一直拉低
→ 中断风暴 / EINT 永久卡死**

### 2.3 为什么会"卡几秒后重启"

中断风暴占满 CPU → 桌面冻结 → 看门狗超时或 panic → 重启。
这同时解释了：
- **触摸无响应**（EINT 卡死）
- **按键失效**（同一 EINT 控制器）
- **按键按下卡几秒后重启**（中断风暴）

### 2.4 修复

把填充 `muxed_data` 的循环和 `nr_banks` 赋值移到
`irq_set_chained_handler_and_data()` **之前**。

```c
/* 修复后 */
bank = d->pin_banks;
idx = 0;
for (i = 0; i < d->nr_banks; ++i, ++bank) {
    if (bank->eint_type != EINT_TYPE_WKUP_MUX) continue;
    muxed_data->banks[idx++] = bank;
}
muxed_data->nr_banks = muxed_banks;

irq_set_chained_handler_and_data(irq, exynos_irq_demux_eint16_31, muxed_data);
```

### 2.5 验证

```
修复前：触摸 IRQ 卡死在 377，划屏幕完全不动
修复后：377 → 9470（持续增长）✓
```

## 三、顺带搞清的 DT 结构

kernel 在运行时通过 of_changeset 生成 `*-gpio-bank` 子节点：

```
gpa0-gpio-bank: interrupts = SPI 0..7    → 每引脚独立中断
gpa1-gpio-bank: interrupts = SPI 8..15   → 每引脚独立中断
gpa2-gpio-bank: 无 interrupts            → MUX（走 chained handler）
gpa3-gpio-bank: 无 interrupts            → MUX
```

对应关系：

| 功能 | 引脚 | 中断方式 |
|---|---|---|
| 触摸屏 | gpa1-6 | 独立中断 SPI 14 |
| 音量上/下、Home | gpa0-2/3/5 | 独立中断 SPI 2/3/5 |
| 电源键 | gpa2-2 | MUX（chained handler） |

## 五、性能实测数据

### 5.1 渲染能力

| 测试 | 结果 |
|---|---|
| glmark2 全屏 1440x2560（build） | **160 FPS** |
| glmark2 全屏 1440x2560（buffer） | **110 FPS** |
| glmark2 窗口 720x1280（build） | 622 FPS（内部） |
| 合成器翻转（glmark2 窗口模式运行中） | 31 fps |
| 静态桌面 | 0 fps（正常，无重绘） |

**⇒ 31fps 不是 vsync bug**：connector mode 是 `1440x2560`（60Hz），mutter 能正常读到。
31fps 是 glmark2 占满 GPU 时合成器被饿的结果。

### 5.2 CPU 性能（确认不是瓶颈）

```
AES-128-CBC 16384B: 611,718 kB/s  (611 MB/s)
SHA256     16384B: 511,519 kB/s  (511 MB/s)
```

对应 Cortex-A57/A53 约 1.5GHz+，**CPU 不是卡顿原因**。

### 5.3 已知限制

- **无 cpufreq**：`/sys/devices/system/cpu/cpu*/cpufreq` 不存在。
  根因是 CMU_CPU (`0x14C00000`) 在 AXI 死区，主线的 `cpufreq-dt` + OPP 表都不适用。
  CPU 频率由 S-Boot 设定后在内核里恒定。
- **AFBC 维持关闭**：见 `panfrost-AFBC深度研究-20261020.md`。
  真正的主故障是 tiler job（js=1）的 `DATA_INVALID_FAULT`，与 AFBC 无关。
