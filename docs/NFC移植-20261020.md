# NFC 移植调研报告 —— SM-G9209 (zeroflte / Exynos7420) → mainline Linux 6.6

- 日期：2026-10-20
- 执行：NFC 子代理（独立上下文，静态分析为主）
- 约束：**未刷机、未重启手机**；只改 NFC 相关 DTS / `.config`；未动 `drivers/power/supply`、`drm/exynos`、`iommu`、`input`、`bluetooth`、`uniLoader`
- 结论性质：**软件方案可行，但被本板 PERIC1 死区卡住硬件访问；当前只能交付"默认 disabled"的代码 + 一份单变量上机验证方案**

---

## 0. 一句话结论（TL;DR）

**芯片是 NXP PN66T（PN548AD + eSE），主线有现成 `nxp-nci` 驱动，接法与主线已支持的 msm8916-samsung-serranove 完全一致，软件路径没有 TEE 依赖、也不需要重新下载固件；但本板 NFC 的 I2C 引脚 GPJ0 的 pinmux（`pinctrl@14cd0000`）和 hsi2c_6 的时钟门控（`CMU_PERIC1 0x14C80000`）都落在实测"一读就 AXI 挂死"的死区 `0x14C00000–0x14CE0000` 内。Linux 无法完成 pinmux/门控，i2c-gpio 也没有退路（GPJ0 的 GPIO 寄存器同样在 0x14CD0000）。因此现在不能 enable；DTS 节点已写好但默认 `status="disabled"`。**

| 项目 | 结论 | 置信度 | 关键证据 |
|---|---|---|---|
| NFC 芯片 | **NXP PN66T = PN548AD + eSE**（不是三星 S3FWRN5） | 实锤 | 原厂 `libnfc-nxp.conf` 的 `#PN548AD 0x03`、`libpn548ad_fw.so`、Android 跑通日志 `Product: PN66T / FW 0x100122` |

## 1. 硬件确认（全部带 vendor 源码证据）

### 1.1 芯片型号：NXP PN66T（PN548AD + eSE）

三条独立证据链，结论锁死：

1. **国行原厂固件里只有 NXP 的 NFC 文件，没有任何三星 NFC 文件**
   - `/vendor/etc/libnfc-nxp.conf`：`NXP_NFC_DEV_NODE="/dev/pn547"`、`FW_STORAGE="/system/vendor/firmware"`、`#PN548AD  0x03`
   - `/vendor/firmware/libpn548ad_fw.so`
   - `/vendor/lib64/hw/nfc_nci.universal7420.so`（NXP `phNxpNciHal_*` API）
   - 详见 `NFC-最终结论与崩溃根因.md`、`NFC-移植交接.md`
2. **vendor 内核 defconfig**：`arch/arm64/configs/exynos7420-zeroflte_defconfig`
   ```
   1088: CONFIG_NFC=y
   1089: # CONFIG_NFC_NCI is not set      ← 注意：vendor 用私有 char 驱动，不用内核 NCI
   1097: # CONFIG_SEC_NFC is not set      ← 三星 S3FWRN5 驱动是关的
   1106: CONFIG_NFC_PN547=y
   1107: # CONFIG_NFC_PN547_CLK_BBCLK2 is not set
   1109: # CONFIG_NFC_PN547_ESE_SUPPORT is not set
   1110: CONFIG_NFC_PN547_LDO_CONTROL=y
   ```
3. **Android LOS20 已实跑通**（不是推测）：
   ```
   NxpNciR: 40011900031E030008000102038081828302D002FF02000418100122   ← CORE_INIT_RSP
   NxpHal : getChipType HwVersion : 0x18
   NxpHal : getChipType Product : PN66T
   NxpHal : FW version from device = 0x100122                          ← FW 10.1.22
   NxpNciR: 41030100                                                   ← RF_DISCOVER_RSP = STATUS_OK
   ```
   出处：`NFC-NXP移植完成报告.md` §一。`dumpsys nfc` → `mState=on`（`evidence-nxp/dumpsys-nfc-working.txt`）。

> **注意**：vendor DTS 里同时存在 `sec-nfc@27` 和 `pn547@2B` 两个节点（`exynos7420-zero_common.dtsi:461,487`），
> 它们共用同一组 GPIO/中断线，只能编译其中一个驱动。国行 CHN 变体实际生效的是 **pn547**；
> `sec-nfc` 节点是给其它 S6 变体（S3FWRN5）用的公共 dtsi 残留。两个驱动同时编译会 panic
> （`NFC-最终结论与崩溃根因.md` 有实锤记录），但那是 Android 3.10 的事，与主线无关。

### 1.2 总线 / 地址 / GPIO

| 信号 | 值 | vendor 证据 |
|---|---|---|
| 控制器 | `hsi2c_6` @ **0x14E00000**，GIC SPI **461** | `exynos7420.dtsi:844-859`（`interrupts = <0 461 0>`） |
| 7bit 地址 | **0x2B** | `exynos7420-zero_common.dtsi:488` `reg = <0x2B>`；原厂 `ctc_stock.dts:5358` `reg = <0x2b>` |
| SDA | **GPJ0-0** | `exynos7420.dtsi:856` `gpio_sda = <&gpj0 0 0x1>` |
| SCL | **GPJ0-1** | `exynos7420.dtsi:857` `gpio_scl = <&gpj0 1 0x1>` |
| I2C pinmux | `hs_i2c6_bus` = `gpj0-1`, `gpj0-0`，func 2，pull-up | `exynos7420-pinctrl.dtsi:928-933`（父节点 `pinctrl@14CD0000`，:919） |
| VEN | **GPF1-5**，高有效 | `exynos7420-zero_common.dtsi:496` `pn547,ven-gpio = <&gpf1 5 0>`；`nfc_pn547_en` @ `pinctrl.dtsi:903-908` |
| FIRM | **GPF5-4** | `:497` `pn547,firm-gpio = <&gpf5 4 0>`；`nfc_n5_firm` @ `pinctrl.dtsi:896-901` |
| IRQ | **GPA0-6**，vendor 用 `IRQF_TRIGGER_RISING` | `:490-495` `interrupts = <6 0 0>` + `interrupt-parent = <&gpa0>`；`pn547.c:1490` |
| CLK_REQ | GPA2-6，**原厂 Exynos 驱动不解析** | `pn547.c` 里只有 `CONFIG_NFC_PN547_CLOCK_REQUEST`（MSM）和 `CONFIG_NFC_PN547_8226_USE_BBCLK2` 才会用；本配置两个都未开 ⇒ 芯片自带时钟 |
| PWR_REQ | GPF5-1，**只有 `CONFIG_NFC_PN547_ESE_SUPPORT` 才用**（eSE 供电请求）；本配置未开 ⇒ 主线忽略 | `pn547.c:1015-1018, 1320` |

> **任务描述里的一处纠正**：NFC **不在** hsi2c_1（0x13650000）。hsi2c_1 是 MAX77843 充电/电量计（电池子代理的战场）。
> NFC 在 hsi2c_6（0x14E00000），控制器地址本身**不在**死区，但它的 **pinmux + 时钟门控**在另一个死区
> `0x14C00000–0x14CE0000`（见 §4），问题比电池更麻烦 —— 电池还能用 gpd2 的 i2c-gpio 绕，NFC 没有可用的替代引脚。

### 1.3 电源

1. **芯片主供电由 VEN（GPF1-5）控制**：vendor `pn547.c:1478-1487` 在 probe 里
   `VEN=1 → FIRM=1 → 5ms → VEN=0 → 5ms → VEN=1`，进入固件下载模式；HAL open 时再走 `PN547_SET_PWR=1/2`。
   所以主线只要正确驱动 `enable-gpios`/`firmware-gpios` 即可（都在 `pinctrl_alive`，可访问）。
2. **I2C 1.8V：S2MPS15 LDO20 "VDD20_1P8_AP"**
   - 原厂 DTS：`ctc_stock.dts:5076-5080`，`regulator-min/max = 0x1b7740 (1.8V)`，**没有 `regulator-boot-on`**
   - vendor 驱动：`pn547.c:1334-1341` 在 probe 时 `regulator_get(NULL, "VDD20_1P8_AP")` + `regulator_enable()`
   - ⇒ 主线必须确认 LDO20 已上电，否则 GPJ0 的 I2C 上拉没电。**这是 NFC 的第二个前置条件**（见 §6.2）。
3. 没有其它 NFC 专用 regulator 节点；eSE 的 LDO23 与本任务无关。

### 1.4 eSE（embedded Secure Element）

- 独立 NXP **P61**，挂 SPI：原厂 `ctc_stock.dts:4600-4610` `ese_spi@0 { compatible = "p61"; p61-mosi/miso/cs/clkpin = <&gpg4 3/2/1/0>; p3-vdd-1p8 = "VDD_1.8V_ESE"; }`
- 供电 LDO23 `VDD_1.8V_ESE`：`ctc_stock.dts:5096-5100`
- vendor defconfig `# CONFIG_NFC_P61 is not set`（虽然 dts 有节点，但驱动没编）
- Android 移植报告明确：**eSE 相关功能（SWP、eSE 卡模拟）不通，但 NFC 基础功能不受影响**

**对本任务的结论**：eSE 不需要移植。NFC 读卡/写卡/HCE 不依赖它。eSE 若以后要做，是独立的 SPI + 可能的 TEE 工程，
不要和 NFC bring-up 混在一起。

### 1.5 是否需要 TEE？

**不需要。** 依据：
- Android 上跑通用的就是普通内核 char 驱动 + 普通 userspace HAL，没有任何 TEE/secure world 调用参与 NCI 数据通路；
- vendor pn547 节点上的 `secure-mode` 属性（`exynos7420-zero_common.dtsi:460`）是三星 pinctrl 的
  "secure gpio recover function" 标志（安全世界事务后恢复 GPIO 状态），**不是 NFC 功能依赖 TEE 的证据**；
- 与指纹（TEE-only）有本质区别：NFC 的控制器、固件、RF 协议栈全在 AP 侧。

> 但注意：**PERIC1 死区**是"安全/电源域"层面的问题，不是 NFC 协议本身需要 TEE。见 §4。

## 2. 主线方案：为什么是 `nxp-nci`

### 2.1 vendor 驱动不能直接搬

vendor `drivers/nfc/pn547.c`（1659 行）是一个 **裸 I2C char 驱动**：
- `misc_register()` 创建 `/dev/pn547`，只实现 `read/write/ioctl(PN547_SET_PWR)`；
- **不注册 net/nfc 子系统**，不走 NCI 核心（defconfig 里 `# CONFIG_NFC_NCI is not set` 就是证据）；
- 固件下载、NCI 会话全在 Android HAL（`libnfc-nxp`）里完成。

把它移植到 6.6 只能给 Android HAL 用；Debian 上没有对应 HAL，`neard` 也不认 `/dev/pn547`。**没有意义。**

### 2.2 主线 `nxp-nci` 完全匹配

- 驱动：`drivers/nfc/nxp-nci/{core,firmware,i2c}.c`，Kconfig：
  `CONFIG_NFC_NXP_NCI` + `CONFIG_NFC_NXP_NCI_I2C`
- compatible：`"nxp,pn547", "nxp,nxp-nci-i2c"`（binding：`Documentation/devicetree/bindings/net/nfc/nxp,nci.yaml`）
- 关键：主线里已有**一模一样的接法**：
  `arch/arm64/boot/dts/qcom/msm8916-samsung-serranove.dts:194-206`
  ```dts
  nfc@2b {
      compatible = "nxp,pn547", "nxp,nxp-nci-i2c";
      reg = <0x2b>;
      interrupt-parent = <&tlmm>;
      interrupts = <21 IRQ_TYPE_EDGE_RISING>;
      enable-gpios = <&tlmm 20 GPIO_ACTIVE_HIGH>;
      firmware-gpios = <&tlmm 49 GPIO_ACTIVE_HIGH>;
  };
  ```
  同一颗芯片、同一个 0x2b 地址、同一组 GPIO 语义 ⇒ 驱动侧零风险。
- NCI 核心 `net/nfc/nci/` 实现了 `dep_link_up`（`core.c:974`），所以 **不需要 `CONFIG_NFC_DIGITAL`**。
- 用户态：`neard` 通过内核 NFC generic netlink 使用 `/dev/nfc0`（见 §3.4）。

### 2.3 固件：大概率不需要下载

- Android 日志：`FW version from device = 0x100122`，HAL 判断 `FW update not required`
  ⇒ **芯片内有非易失固件（10.1.22），每次上电直接启动 NCI 模式**。
- 主线 `nxp-nci` 只在用户态显式发 `NFC_CMD_FW_DOWNLOAD` 时才下载固件；正常 open 只做
  `set_mode(NCI)` → VEN=1/FIRM=0 → NCI CORE_RESET/INIT。芯片有固件就能直接跑。
- 如果将来需要下载：原厂 `libpn548ad_fw.so` 里 `gphDnldNfc_DlSequence`（34422 字节）**正好是主线固件格式的
  63 个 `0xC0`(WRITE) 帧**，我已在静态侧验证过帧结构：
  ```
  frame 0: off=0     sz=228  cmd=0xc0 head=c000220113125b13d3f62064
  frame 1: off=230   sz=550  cmd=0xc0 head=c08013200002060800040217
  ...
  frame 62: off=33902 sz=518 cmd=0xc0 head=c000fe200002c31b0187f016
  frames=63 consumed=34422/34422 cmds={0xc0:63}
  ```
  （每帧 = 2 字节大端长度 + payload，与主线 `firmware.c` 的解析一致；但主线文件还需 reset/check-integrity 帧，
  目前**不需要**，所以没有继续构造。）

### 2.4 时钟：不需要 AP 供时钟

- `CONFIG_NFC_PN547_CLK_BBCLK2=y` 未开、`CONFIG_NFC_PN547_CLK_REQ*` 未定义
  ⇒ vendor 在 Exynos 上根本不解析 `clk_req-gpio`，也不操作 `sclk_isp_sensor1`。
- PN548 板级自带时钟源。主线只用一个 fixed-clock 给 hsi2c 控制器算分频（见 §5.1），与芯片时钟无关。

### 2.5 主线 DTS 方案（已写入，默认 disabled）

见 §5.1。核心：
```dts
&hsi2c_6 {
    clocks = <&hsi2c6_clk>;          /* 133MHz fixed，避开 CMU_PERIC1 */
    /delete-property/ pinctrl-names; /* GPJ0 pinmux 在死区，绝不能引用 hs_i2c6_bus */
    /delete-property/ pinctrl-0;
    clock-frequency = <400000>;
    status = "disabled";             /* DSH_ENABLE_NFC=0 */
    nfc@2b {
        compatible = "nxp,pn547", "nxp,nxp-nci-i2c";
        reg = <0x2b>;
        interrupt-parent = <&gpa0>;
        interrupts = <6 IRQ_TYPE_EDGE_RISING>;
        enable-gpios = <&gpf1 5 GPIO_ACTIVE_HIGH>;
        firmware-gpios = <&gpf5 4 GPIO_ACTIVE_HIGH>;
    };
};
```

## 3. 用户态：Debian 12 的现实

### 3.1 `apt install neard` 在 Debian 12 上**不可用**

- Debian bookworm **没有** `neard` 包；`neard` 目前只在 **sid/forky（0.20-3）**。
  证据：<https://packages.debian.org/search?keywords=neard> 只列出 forky/sid；bookworm 页面返回
  "Package not available in this suite"。
- `nfctool` 在 `neard-tools` 包里，同样只在 sid/forky。
- Ubuntu pool 里有 `neard 0.16-0.1`（2017）和 `0.20-3`（2026）的 arm64 deb：
  <http://in.archive.ubuntu.com/ubuntu/ubuntu/pool/universe/n/neard/>
  - 0.20-3 依赖 `libc6 >= 2.38`，bookworm 只有 2.36 ⇒ 不能直接装；
  - 0.16 太老，且混发行版不推荐。

**⇒ 需要 rootfs 侧二选一（等 Lead 执行）：**
1. **源码编译 neard**（推荐）：`git clone https://git.kernel.org/pub/scm/network/nfc/neard`（或 GitHub `linux-nfc/neard`），
   Debian 构建依赖大致为：`build-essential autoconf automake libtool pkg-config libglib2.0-dev libdbus-1-dev libnl-3-dev libnl-genl-3-dev libreadline-dev`。
2. 写一个最小 netlink 探针（类似现有 `nfcprobe.c` 的思路）：`NETLINK_GENERIC` + `"nfc"` family +
   `NFC_CMD_DEV_UP` → `NFC_CMD_START_POLL` → 收 `NFC_CMD_TARGET_FOUND`。只用于验证 RF 是否工作。
   （本报告不附带未测试的 C 代码；如需要，Lead 可指派。）

### 3.2 `nfc-list`（libnfc）不适用

`nfc-list` 属于 **libnfc**（nfc-tools），libnfc 是 userspace 驱动库，直接操作 USB/UART 读卡器
（PN533/ACR122 等），**不走内核 NFC 栈**，看不到 `/dev/nfc0`。
主线 `nxp-nci` 的正确用户态是 **neard + nfctool**（`nfctool -l` / `nfctool --poll`）。

### 3.3 内核配置（已改）

当前内核 `.config` 原来是 `CONFIG_NFC=m` + `CONFIG_NFC_NCI=m` + `NXP_NCI is not set`；
rootfs 没有装模块，所以 `=m` 等于没有。已改为**内置**：

```
CONFIG_NFC=y
CONFIG_NFC_NCI=y
CONFIG_NFC_NXP_NCI=y
CONFIG_NFC_NXP_NCI_I2C=y
```

（`CONFIG_NFC_S3FWRN5=m` 保留不动，它是三星变体的模块，不影响。）
`CONFIG_NFC_DIGITAL` 不需要（NCI 自带 `dep_link_up`）。

### 3.4 验证命令（总览）

```bash
# 内核
dmesg | grep -iE "nxp|nci|i2c.*14e00000|nfc"
ls -l /dev/nfc0
cat /sys/class/nfc/*/name 2>/dev/null
# 总线（若 hsi2c_6 起来了）
i2cdetect -y -r 6          # 期望 0x2b（驱动绑定后显示 UU）
i2cget -y -f 6 0x2b 0x00   # 不应答 = 芯片没电/没固件
# 用户态（neard 编译/安装后）
nfctool -l                 # 列出 nfc0
nfctool --poll             # 开始轮询，拿标签靠近
journalctl -u neard -f
```

## 4. ★ 致命阻塞点：PERIC1 死区

### 4.1 地址地图（本板实测）

| 块 | 地址 | 状态 | 依据 |
|---|---|---|---|
| `pinctrl_alive`（gpa/gpf） | `0x10580000` | ✅ 可读 | 多次实测，本报告用的 GPIO 全在这 |
| `pinctrl_bus0`（gpd2 等） | `0x13470000` | ✅ 可读 | 电池/触摸 i2c-gpio 已验证 |
| **`pinctrl_nfc`（GPJ0！）** | **`0x14CD0000`** | ⛔ 在死区内（未单点实测，但与 0x14CE0000 同类） | 主线 `exynos7.dtsi:377`；vendor `pinctrl@14CD0000` |
| `pinctrl_touch`（GPJ1） | `0x14CE0000` | ⛔ **实测挂死** | `硬件实测-PERIC1不可访问-20261018.md`（loader `mrd 14ce0000`，p117 内核二分） |
| **`CMU_PERIC1`（HSI2C6 gate）** | **`0x14C80000`** | ⛔ **实测挂死** | `硬件实测-PERIC1与PMIC-20261018.md` §2 |
| hsi2c_6 控制器 | `0x14E00000` | ❓ 未实测（同块的 hsi2c_7 `0x14E10000` 可读且触摸已工作） | `exynos7420-zeroflte.dts:734-745`（hsi2c7 固定时钟方案） |
| hsi2c_6 gate | `CMU_PERIC1 + 0x0900` bit 6 | ❓ 状态未知 | `drivers/clk/samsung/clk-exynos7.c:753,806`；vendor `clk-exynos7420.c:2397` 同位 |

死区：**`0x14C00000 – 0x14CE0000`**（含 `0x14C80000` 与 `0x14CE0000`，都已实测挂死；`0x14CD0000` 在同段内，按纪律不许碰）。

### 4.2 为什么 `i2c-gpio` 救不了 NFC（与电池的关键差异）

电池/充电的 MAX77843 挂在 hsi2c_1（0x13650000），但它的引脚是 **gpd2-2/3**，
GPIO 寄存器在 **`pinctrl_bus0 0x13470000`（实测可读）** ⇒ 可以改 i2c-gpio 绕开死区。

NFC 的引脚是 **GPJ0-0/1**，GPIO/pinmux 寄存器在 **`pinctrl@14CD0000`** —— 同一条死区。
所以：
- 硬件 I2C6：需要写 `0x14CD0000` 做 pinmux，**不能**；
- i2c-gpio：需要写 `0x14CD0000` 的 CON/DAT 寄存器，**同样不能**；
- 没有第三组可用引脚（NFC 硬连在 GPJ0）。

**⇒ 不存在"像电池那样用 i2c-gpio 绕过去"的方案。**

### 4.3 还能怎么救？

**前提 ①：S-Boot 已经替我们做好 pinmux + 门控（唯一不需要改 bootloader 的可能）**

- 触摸的 GPJ1 就是 S-Boot 预 mux 好的（主线 hsi2c_7 删掉 pinctrl 也能工作，见 `exynos7420-zeroflte.dts:747-762`）；
- 如果 S-Boot 的 pinctrl 初始化表把 **所有 hsi2c 引脚**都 mux 了、并且 PCLK_HSI2C6 门控是开的，
  那么 `DSH_ENABLE_NFC=1` 的 p235 就能直接起 I2C6；
- **但 S-Boot 没有理由为 NFC 做这些**（触摸可能是下载/充电 UI 需要），所以这个可能性只能靠实测，不能猜。
- 门控状态也未知：hsi2c7 的 gate 是开的（bit 7），hsi2c6（bit 6）是否同批打开未知；
  同批打开的可能性存在（S-Boot 可能整组使能 PERIC1 gate），但无证据。

**前提 ②：uniLoader 预初始化（超出本子代理权限，且很可能也救不了）**

- 需要在跳转前写：
  - `GPJ0CON (0x14CD0000)`：pin0/pin1 的 4bit 功能位设为 `0x2`（hsi2c6）
    → `val = (readl(0x14CD0000) & ~0xFF) | 0x22; writel(val, 0x14CD0000);`
  - `GPJ0PUD (0x14CD0008)`：pin0/pin1 上拉（2bit 一组，`0x3`）
    → `val = (readl(0x14CD0008) & ~0xF) | 0xF; writel(val, 0x14CD0008);`
  - `CMU_PERIC1 + 0x0900 (0x14C80900)`：bit6 = 1（PCLK_HSI2C6）
    → `writel(readl(0x14C80900) | (1 << 6), 0x14C80900);`
- **但**：如果 `0x14CD0000/0x14C80000` 在 loader 阶段就已经断电/被保护，写同样会挂死
  （loader 里裸读 `0x14CE0000` 已经实测挂死，见 §4.1）。所以在没有弄清 PERIC1 为什么不可访问之前，
  **不建议让 uniLoader 去碰这三个地址**。
- 这条路线需要 Lead 决策 + 硬件测试，且不是 NFC 子代理的改动范围。

**结论**：NFC 能否在主线跑起来，取决于一个**纯硬件/引导层问题**（PERIC1 可访问性），
不是驱动或 DTS 能解决的。**在解决它之前，不要投入用户态/固件工作。**

### 4.4 第二个前置条件：LDO20（VDD20_1P8_AP）

即使 GPJ0/门控都通了，I2C 上拉还需要 S2MPS15 LDO20 上电：
- 原厂 `ctc_stock.dts:5076-5080` 没有 `regulator-boot-on`；
- vendor 驱动在 probe 时显式 `regulator_enable()`；
- 主线当前 `exynos7420-zeroflte-touch-power.dtsi` 的 s2mps15 节点只声明了 LDO15，
  **LDO20 没有消费者，也没有 always-on**。

处理选项（等 Lead 定）：
1. 在 s2mps15 的 `regulators` 节点里补 `LDO20 { regulator-always-on; }`
   （注意：s2mps15 的 regmap 对某些寄存器读会 -ENXIO，touch 团队踩过；加约束可能 probe 失败，需实测）；
2. 用户态在启动脚本里直接 `i2cset` 打开 LDO20（与当前 LDO17 的做法一致）。
   寄存器 = `S2MPS15_REG_L1CTRL + 20 - 1`（mainline `s2mps11.c:729` 的定义），
   **不要凭记忆猜地址**，先在设备上 `i2cget` 对照 s2mps15.h；
3. 先测 S-Boot 是否已经把它留在开状态（`i2cget` 读 LDO20 控制寄存器看 enable 位）。

## 6. 上机验证方案（**现在不要执行**，电量 13%）

> 任务明确要求：不刷机、不重启。以下步骤是给 Lead 在**充好电、有恢复手段**之后用的。
> 任何一步挂死，按 `NFC-移植交接.md` §八的方法物理恢复（长按电源 30s 等）。

### 6.1 前置

1. 电量 > 50%（或全程 USB 供电）；
2. 备份当前 BOOT 并 pull 到宿主机；
3. 确认 p234 默认可正常启动（它只是多了 disabled 节点 + built-in NFC 驱动，风险极低 —— 建议先单独验证 p234）；
4. 准备好 p235（enabled）和回滚镜像。

### 6.2 阶段 1：确认 LDO20（不改内核）

在**当前运行的 p228 Debian** 上（只读 + 一条 i2cset）：
```bash
i2cdetect -l                          # 找 s2mps15 的 i2c-gpio 总线号
# 读 LDO20 控制寄存器（地址按 s2mps15.h：S2MPS15_REG_L1CTRL + 19）
i2cget -y -f <bus> 0x66 <LDO20_REG>
# 若 enable 位为 0，再写（值 = enable | VSEL；先算清楚，不要照抄）
i2cset -y -f <bus> 0x66 <LDO20_REG> <val>
```
如果这一步就把 I2C 总线搞挂/报 -ENXIO，说明 PMIC/总线本身还有问题，先停下。

### 6.3 阶段 2：p235 单变量测试（唯一的硬件风险点）

```bash
# 刷 p235（仅当电量充足、已备份）
adb push out/p235-padded.img /tmp/ 2>/dev/null || true
# 注意：Debian 下没有 adb；手机当前跑 mainline，刷机走 Lead 的既有流程（不要由 NFC 代理执行）
```
启动后看：
- **如果启动到 console/登录** ⇒ 0x14E00000 可访问，门控大概率是开的；继续 6.4；
- **如果黑屏/卡死** ⇒ HSI2C6 门控没开（或 pinmux 没做），AXI 挂死；
  物理复位后刷回 p234。**结论：需要 S-Boot/uniLoader 预初始化，NFC 主线移植暂停。**

### 6.4 阶段 3：总线与驱动

```bash
dmesg | grep -iE "14e00000|nxp|nci|nfc"
i2cdetect -y -r 6        # 期望 0x2b（UU=驱动已绑定；2b=芯片应答但驱动没绑）
ls -l /dev/nfc0
```
- 若 `i2cdetect` 超时：GPJ0 没 mux 或 LDO20 没电 → 回到 6.2/§4；
- 若出现 `0x2b` 但驱动没绑：检查 `compatible`/`interrupts`/`enable-gpios`（本报告已按 serranove 写死）。

### 6.5 阶段 4：用户态

```bash
# Debian 12 没有 neard 包 —— 先源码编译（见 §3.1），或临时用自制 netlink 探针
nfctool -l
nfctool --poll           # 拿一张 NFC 卡/手机靠近
journalctl -u neard -f
```
期望：`nfctool -l` 看到 `nfc0`；`--poll` 能发现 tag（NFC-A/B/F）；dmesg 无 AXI/timeout。

### 6.6 判据表

| 现象 | 结论 |
|---|---|
| p235 卡死 | HSI2C6 gate 未开 → 只能 S-Boot/uniLoader；停止 |

## 7. 结论与建议

1. **硬件身份和主线驱动映射已 100% 确认**：NXP PN66T (PN548AD)，I2C6/0x2B，GPF1-5/GPF5-4/GPA0-6，
   `nxp-nci` 是正确驱动，不需要 TEE、eSE，不需要重新下固件。
2. **唯一的、也是决定性的阻塞**是 PERIC1 死区：GPJ0 pinmux（0x14CD0000）和 HSI2C6 门控（CMU_PERIC1 0x14C80000）
   都在 `0x14C00000–0x14CE0000`，Linux 不能碰；i2c-gpio 无退路。
3. 因此**不能把 NFC 节点默认 enable** —— 已按安全默认交付（p234 disabled；p235 只是实验镜像）。
4. **建议 Lead 决策**：
   - **A（推荐先做）**：充好电后，用 p235 做一次单变量启动测试（10 分钟内出结论）。成功则继续用户态；失败则 NFC 暂停，
     把结论归档为"需 S-Boot/引导层配合"。
   - **B（不推荐现在做）**：在没弄清 PERIC1 为什么不可访问之前，让 uniLoader 去写 `0x14CD0000/0x14C80900` —— 
     loader 里裸读 0x14CE0000 已经挂死过，写很可能同样挂死。
5. **如果 A 成功**，剩余工作量：装/编译 neard（Debian 12 无包）、`DSH_ENABLE_NFC=1`、可选补 LDO20 always-on。
   这部分是小时级，不是天级。

## 9. 附：给后续接手人的 5 条硬结论

1. **不要**把 `sec-nfc`（三星）和 `pn547`（NXP）两个驱动同时编 —— 它们共用 GPIO/IRQ，Android 上已炸过。
2. **不要**在主线里给 hsi2c_6 加 `pinctrl-0 = <&hs_i2c6_bus>` —— `hs_i2c6_bus` 在 `0x14CD0000`，死区。
3. **不要**用 i2c-gpio 挂 GPJ0 —— GPIO 寄存器同样在 `0x14CD0000`。
4. **不要**在 loader 里裸读/写 `0x14C00000–0x14CE0000` —— 已多次挂死。
5. **不要**指望 `nfc-list`（libnfc）—— 主线 nxp-nci 用 neard；Debian 12 还没有 neard 包，要自己编译。
