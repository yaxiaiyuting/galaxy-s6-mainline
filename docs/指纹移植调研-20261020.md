## 0. 一句话结论

**S6 的指纹是 Synaptics（原 Validity）VFS7xxx 系列、SPI 接口，但"采集 + 匹配"整体跑在 Trustonic TEE 的 trustlet 里；内核驱动只是 TEE 的电源/中断/时钟帮手。**

因此 mainline 6.6 上的结论是：

> **短期不可行，不建议投入写驱动。**  
> 不是"缺一个 SPI 驱动"的问题，而是缺 **整套 TEE 运行时（MobiCore/gud）+ 安全世界 SPI 配置 + 闭源采集/匹配算法**。  
> 而且 SPI4 的时钟门控（`0x14C80900/0x14C80A00`）和引脚复用（`0x14CA0000`）正好落在你们实测"一碰就挂死"的 `0x14C00000–0x14CE0000` 区间内。

## 1. 芯片型号：确认到什么程度

### 1.1 已确认（vendor 源码直接证据）

**Synaptics（2014 年收购 Validity）VFS7xxx 系列。**

## 2. 硬件接法（带 vendor DTS 证据）

### 2.1 总线：SPI4 @ `0x14D70000`，CS0，最高 19.2 MHz

```dts
/* arch/arm64/boot/dts/exynos7420-zerolte_fingerprint-sensor_00.dtsi:65-99 */
spi_4: spi@14d70000 {
	status = "okay";
	/delete-property/ dma-mode;
	/delete-property/ dmas;
	/delete-property/ dma-names;
	secure-mode;                       /* <-- 关键：整条 SPI 交给安全世界 */
	#address-cells = <1>;
	#size-cells = <0>;
	pinctrl-names = "default";
	pinctrl-0 = <&spi4_bus &spi4_cs>;

	vfsspi-spi@0 {
		compatible = "vfsspi,vfs7xxx";
		reg = <0>;
		spi-max-frequency = <19200000>;
		pinctrl-names = "default", "sleep", "idle";
		pinctrl-0 = <&btp_irq &btp_reset &btp_ldo &btp_ldo2 &ocp_en>;
		pinctrl-1 = <&btp_irqsleep>;
		pinctrl-2 = <&btp_irqidle>;

		vfsspi-sleepPin = <&gpf3 4 0x00>;   /* reset / sleep */
		vfsspi-drdyPin  = <&gpa0 7 0x00>;   /* DRDY 中断 */
		vfsspi-ldoPin   = <&gpf1 6 0x00>;   /* LDO enable 1 */
		vfsspi-ldoPin2  = <&gpf1 7 0x00>;   /* LDO enable 2 */
		vfsspi-ocpen    = <&gpv7 4 0x01>;   /* OCP enable（安全世界管） */
		vfsspi-orient   = <0>;
		vfsspi-ldocontrol = <1>;
	};
};
```

> 注意：指纹**不在** `hsi2c_1`（`0x13650000`）上，所以不存在"必须改 i2c-gpio/SPI"的改线问题；它本来就是 SPI4（GIC SPI 468）。  
> SPI4 的风险不在 `0x13650000`，而在它自己的时钟/引脚死区（见 §5.1）。

### 2.2 引脚汇总

| 信号 | 引脚 | pinctrl 块 | 主线可达性 | 说明 |
|---|---|---|---|---|
| SPI4 CLK/MOSI/MISO | `gpv7-3/2/0`（vendor `spi4_bus` 列表顺序，具体角色以 SoC pinmux 表为准） | `pinctrl@14CA0000` (`pinctrl_ese`) | ❌ 在 `0x14C00000–0x14CE0000` 死区 | vendor `spi4_bus` |
| SPI4 CS | `gpv7-1` | `pinctrl@14CA0000` | ❌ 同上 | vendor `spi4_cs` |
| OCP enable | `gpv7-4` | `pinctrl@14CA0000` | ❌ 同上 | 安全世界用 SMC 控制，不走 GPIO |
| DRDY / IRQ | `gpa0-7` | `pinctrl@10580000` (`pinctrl_alive`) | ✅ 已实测可访问 | 上升沿中断 |
| Reset / Sleep | `gpf3-4` | `pinctrl@14870000` (`pinctrl_bus1`) | ✅ 已实测可访问 | 硬复位 |
| LDO enable 1 | `gpf1-6` | `pinctrl@14870000` | ✅ | 电源使能 |
| LDO enable 2 | `gpf1-7` | `pinctrl@14870000` | ✅ | 电源使能 |

> 注意：**SPI4 的数据引脚和 OCP 都在 GPV7 这一个 bank 里，而这个 bank 的 pinctrl 基址是 `0x14CA0000`，正好在你们列的禁区内。**

### 2.3 电源

vendor 驱动**没有用 regulator 框架**，而是直接 GPIO 拉 LDO enable：

```c
/* vfs7xxx.c:865-910，secure 分支 */
if (ocp_en)
    exynos_smc(MC_FC_FP_BTP_OCP_HIGH, 0, 0, 0);  /* OCP 由 TEE 开 */
usleep_range(2950, 3000);
if (ldo_pin2) gpio_set_value(ldo_pin2, 1);
gpio_set_value(ldo_pin, 1);
...
exynos_smc(MC_FC_FP_BTP_OCP_LOW, 0, 0, 0);
```

- `ldoPin` / `ldoPin2` = `gpf1-6` / `gpf1-7`，是外部 LDO 的 enable（不是 PMIC regulator）。
- **OCP enable = `gpv7-4`，但 secure 编译下不直接拉 GPIO，而是 SMC 进 TEE**（`MC_FC_FP_BTP_OCP_HIGH = 0x83000023`）。
  - 这说明 GPV7 这个 pinctrl bank（含 SPI4 引脚 + OCP）在运行时是**安全世界拥有**的。
  - 换句话说：即使 mainline 能碰 `0x14CA0000`，也不应该碰——会和安全世界抢同一个 bank。

### 2.4 中断与字符设备

- IRQ：`gpa0-7`，驱动用 `gpio_to_irq(drdy_pin)`，上升沿。
- 内核创建 `/dev/vfsspi`（class `validity_fingerprint`，device `vfsspi`）：
  - `vfs7xxx.c:1974-1984`
  - Android `ueventd` 权限：`/dev/vfsspi 0660 system system`（`device/samsung/universal7420-common/ramdisk/etc/ueventd.samsungexynos7420.rc:119`）

## 4. mainline 6.6 现状

### 4.1 没有 VFS7xxx / MobiCore 驱动

在 `/home/duanjb666/linux7420/linux-6.6` 里：

```
grep -rliE "vfs7|vfsspi|mobicore|trustonic|gud-exynos" drivers/
→ 只命中 AMD GPU 寄存器头文件（误报）
```

`drivers/tee/` 只有 `optee` 和 `amdtee`。  
**OP-TEE 驱动不能跑 Trustonic 的 trustlet**：两者是完全不同的 TEE OS / ABI / 签名体系。

### 4.2 libfprint 不适用

写这个报告时查了 libfprint 上游 `libfprint/drivers/synaptics/synaptics.c`：

```c
dev_class->type = FP_DEVICE_TYPE_USB;
dev_class->scan_type = FP_SCAN_TYPE_PRESS;
id_table[] = { { .vid = SYNAPTICS_VENDOR_ID, .pid = 0x00BD }, ... }
```

- 它是 **USB** 驱动，面向 VFS7552/"Prometheus" 这类 **match-on-chip** 设备（Dell XPS 2017 等）；
- 设备自己存模板、自己做匹配，主机只发 BMKT 命令；
- **不是** S6 这种 SPI + match-in-TEE 的 VFS7xxx。

libfprint 里的 `vfs5011` 是更老的 USB swipe 传感器（S5 时代），也不适用。  
python-validity 那套（VFS451/471/491/495 等）同样是 USB ThinkPad 传感器。

结论：**libfprint 没有任何驱动能覆盖 zeroflte 这颗 SPI VFS7xxx。**

### 4.3 mainline DTS 也没有 SPI4

`arch/arm64/boot/dts/exynos/exynos7.dtsi` 里只定义了 `spi_0`（`0x14d20000`，`exynos7.dtsi:477-491`），没有 `spi_4`。  
pinctrl 里倒是有 `spi4_bus`（`exynos7-pinctrl.dtsi:409-414`），挂在 `pinctrl_ese @0x14ca0000` 下。

## 5. 可行性逐项拆解

### 5.1 总线/时钟/引脚：三个硬障碍

| # | 障碍 | 证据 |
|---|---|---|
| 1 | SPI4 的 PCLK/SCLK 门控在 `0x14C80900` / `0x14C80A00`，属于 `0x14C00000–0x14CE0000` 死区 | `arch/arm64/mach-exynos/include/mach/regs-clock-exynos7420.h:476-477`：`ENABLE_PCLK_PERIC1 = PERIC1(0x0900)`、`ENABLE_SCLK_PERIC10 = PERIC1(0x0A00)`，而 `EXYNOS_CLKREG_PERIC1` 基址 = `0x14C80000` |
| 2 | SPI4 的 4 根数据/CS 引脚在 `GPV7` → `pinctrl@14CA0000`，也在死区 | vendor `spi4_bus/spi4_cs` 用 `gpv7-0..3`；mainline `exynos7-pinctrl.dtsi:400-414` 把 `gpv7` 挂在 `pinctrl_ese @0x14ca0000` |
| 3 | mainline 已把 `clock-controller@14c80000`（CMU_PERIC1）整个 disable；SPI4 没有可用的时钟父节点 | `arch/arm64/boot/dts/exynos/exynos7420-zeroflte.dts:403-405` |

对比一下触摸的既有经验：触摸用 `hsi2c7` 时，你们能用 fixed-clock 绕过 CMU_PERIC1，**很可能**是因为 hsi2c7 的 gate 被 S-Boot 留着开了，而且 I2C 引脚已由 S-Boot 复用好（这是从"touch 能工作"反推的，未直接读 gate 寄存器确认）。  
指纹没有这个前提：

- SPI4 的 gate 由 vendor 内核在 SPI 设备 probe/runtime PM 时打开（`fp-spi-pclk` / `fp-spi-sclk`，见 `drivers/clk/samsung/clk-exynos7420.c:2412,2434`；`spi-s3c64xx.c:1803-1809` 在 probe 时 `clk_prepare_enable`），S-Boot 没有理由提前打开它；
- GPV7 的 pinmux 由 vendor 驱动 `pinctrl_select_state()` 写 `0x14CA0000`，S-Boot 也不会替 Linux 配。

补充一个可验证的推断：mainline 的 `spi-s3c64xx.c:1379-1383` 同样在 probe 时 `clk_prepare_enable(pclk/sclk)`。  
如果 DT 里继续引用被 disable 的 `clock_peric1`，SPI4 会永久 `-EPROBE_DEFER`；如果改用 fixed-clock 绕过，则 gate 永远不会被打开（因为 gate 寄存器在死区），控制器访问会挂死。**两条路都堵死。**

**换句话说：SPI4 控制器基址 `0x14D70000` 本身不在禁区内，但它的"电"（时钟 gate）和"路"（引脚 mux）都在禁区内。**  
除非先把 `0x14C00000–0x14CE0000` 这块的总线/电源域问题解决（那是另一个 bring-up 工程，且与 TEE 的 TZPC 配置纠缠），否则 mainline 连一个字节都发不出去。

### 5.2 TEE：不是"可选"，是"必须"

- `secure-mode` 写在 SPI4 节点上（DTS 第 70 行）。
- secure 编译下内核无 SPI 数据通道（`vfs7xxx.h:49-55`）。
- OCP 上电走 `exynos_smc(MC_FC_FP_BTP_OCP_HIGH)`（`vfs7xxx.c:874-880`），不是 GPIO。
- 采集/匹配/模板/HAT 全在 trustlet 里（见 §3.2c）。
- 用户态入口是 MobiCore（`libMcClient.so` + `/dev/mobicore`）。

要在 mainline 上复用这套，至少需要：

1. 把 `drivers/gud/gud-exynos7420/`（45 文件 / 344 KB，3.10 API）移植到 6.6；
2. 让 TEE OS 仍然在运行（如果 S-Boot 仍加载它；这一点需要实测，见 §9.4）；mainline 没有驱动去握手；
3. 在 mainline 里复刻 vendor 的 secure SPI 配置（时钟 gate + pinmux + TZPC + SMC PM 序列）；
4. 在 Debian 上重新实现/移植 MobiCore TCI 客户端（`libbauthtzcommon.so` 是 bionic + Android 依赖）；
5. 写 PAM/验证程序，处理模板、HAT、错误码、锁屏状态等。

而 3 又回到 5.1 的死区问题；4 是闭源 TCI 协议逆向。  
所以 **"TEE 路线" 不是"绕一下"，而是"把整个 Android 安全栈搬到 Debian"**。

### 5.3 协议/算法：内核驱动里没有

即使假设 SPI4 能通，vendor 的 `vfs7xxx.c` 在 secure 模式下也**不包含**传感器协议：

- 没有固件下载；
- 没有图像帧格式；
- 没有校准；
- 没有 swipe 拼接；
- 没有特征提取/匹配。

这些都在 655 KB 的 trustlet 里（Synaptics Usdk5）。  
要自己写 mainline 驱动，等价于：

1. 逆向 trustlet 里的 SPI 命令序列 / 寄存器序列；
2. 逆向图像格式与校准；
3. 自己实现或接入一个指纹匹配器（libfprint 的 image device + NBIS/bozorth3 之类）；
4. 自己做模板存储与安全保护。

这是**研究项目**级别，不是"移植驱动"级别。

### 5.4 安全/信任链

- 三星的指纹模板由 TEE 保护，配合 HAT（Hardware Auth Token）给上层做认证。
- 如果改成 mainline 纯软件方案，模板落在普通文件系统里，安全性显著下降（对解锁场景要慎重）。
- Trustonic trustlet 是签名 + 设备密钥绑定的；mainline 无法"重新签一个"。

## 6. 工作量与路线评估

### 路线 A：复用 TEE（"把 Android 栈搬过来"）

| 项 | 估计 |
|---|---|
| 移植 gud/MobiCore 到 6.6 | 2–6 周（熟悉 TEE 的人），且要处理 ION/smem/SMC/电源管理 |
| 解决 CMU_PERIC1 / SPI4 时钟与 pinmux | 未知，可能数周–数月；涉及死区、电源域、TZPC，失败风险高 |
| 复刻 secure SPI 配置 + SMC PM 序列 | 2–4 周，需要 TEE 侧配合（否则只能猜） |
| Debian 侧 TCI 客户端 / PAM | 1–3 个月（协议逆向 + 调试） |
| **合计** | **6–12 个月，成功率低，且高度依赖不可见的 TEE 行为** |

### 路线 B：完全自写（native mainline driver）

| 项 | 估计 |
|---|---|
| SPI4 可达性 | 同路线 A，仍是死区问题 |
| 传感器协议逆向 | 3–6 个月（655 KB TEE 二进制 + 无文档） |
| 图像处理/校准/拼接 | 3–6 个月 |
| 匹配算法/模板 | 3–6 个月 |
| **合计** | **1–2 年，成功率极低** |

### 路线 C：只做"手指存在"检测

- 只拉 LDO、读 DRDY GPIO（`gpa0-7`），当一个大号触摸键用。
- 但 OCP 在 TEE 手里、LDO 上电时序也在 TEE 手里，**连"传感器有没有电"都不确定**；即使能亮，也没有认证价值。
- 工作量：1–3 天（如果硬件配合），但不解决用户需求。

## 7. 推荐

### 7.1 结论：**不要在 mainline 上做这颗指纹**

理由按重要性排序：

1. **数据在 TEE 里**：mainline 没有 Trustonic MobiCore 驱动，OP-TEE 也读不了三星 trustlet。
2. **SPI4 的时钟/引脚在实测死区**：`0x14C80900`、`0x14C80A00`、`0x14CA0000`，且与 TEE 的 GPV7 所有权冲突。
3. **协议/算法完全闭源**：vendor 内核驱动在 secure 模式下不含任何采集/匹配逻辑。
4. **安全模型**：即使硬做出来，也只是弱化的纯软件匹配。

### 7.2 替代方案（务实）

- **Debian 登录/解锁**：买一个 libfprint 支持的 **USB** 指纹读卡器（例如常见的 UPEK/Validity USB、Synaptics Prometheus USB 等），Debian 12 的 libfprint 1.94 + fprintd 开箱可用。  
  这是唯一低成本、可维护的"Linux 上用指纹"路线。
- **手机本身**：保留 PIN/密码；主页键继续当普通 GPIO 按键用（mainline 已经能用）。
- 如果只是想要"指纹手势"（返回/主页）：这颗传感器的手势也在 TEE 里，同样不可用。
- 如果一定要在原机上用指纹：继续用 LOS20（Android）那一套，或双系统；mainline Debian 下没有现实路径。

### 7.3 如果将来仍想推进：先做"零风险"的信息收集

不要一上来写驱动，也不要去碰死区。先在 **LOS20（vendor 内核）** 上收集：

```bash
# 1. 传感器类型 / 设备节点
cat /sys/class/fingerprint/fingerprint/type
ls -l /dev/vfsspi /dev/mobicore
dmesg | grep -iE "vfs|finger|btp|mobicore"

# 2. SPI4 时钟 gate 是否被打开
cat /sys/kernel/debug/clk/clk_summary | grep -iE "spi4|fp-spi"

# 3. GPV7 的 pinmux 当前状态（确认 S-Boot/TEE 是否已经 mux 好）
cat /sys/kernel/debug/pinctrl/*/pinmux-pins | grep -i gpv7

# 4. TEE 是否真的在跑
ls -l /dev/mobicore
cat /proc/interrupts | grep -iE "spi|gpa"
```

这些能回答三个关键问题：

1. SPI4 的 gate 在 boot 后是否已经是开的（若开，fixed-clock 方案才有一线可能）；
2. GPV7 是否已被 S-Boot/TEE 复用为 SPI 功能（若是，可绕开 `0x14CA0000`）；
3. TEE/MobiCore 是否在 mainline 启动路径下仍然存活。

只有当 1、2 的答案都是"是"，路线 A 才值得进一步评估；否则直接放弃。

## 9. 未决问题（诚实标注）

1. **精确 PN**：vendor 源码只到 `VFS7xxx` / `Viper`，没有 `VFS7500` 之类的字符串；公开拆解报告也没有可引用的 PN。  
   → 结论按"VFS7xxx 系列 / Viper"写，不编造具体型号。
2. **TZPC 是否把 SPI4 标记为 secure**：DTS 的 `secure-mode` 强烈暗示是，但没有在 mainline 下实测。  
   → 即使不是，5.1 的时钟/pinmux 死区仍然卡死。
3. **S-Boot 是否提前打开了 SPI4 gate / 复用 GPV7**：未知，需要在 LOS20 上用 debugfs 查（§7.3）。  
   → 若两者都是"是"，路线 A 才有一线可能；但我仍然不推荐。
4. **TEE 在 mainline 启动链下是否仍存活**：你们文档已证实 ATF 在（`msr tcr_el1` 被拦截），但 Trustonic TEE OS 是否被 S-Boot 加载、mainline 是否还能握手，需要实测。  
   → 没有 MobiCore 驱动，即使 TEE 活着也进不去。

## 10. 最终建议（给决策者）

- **把指纹从 mainline 的 TODO 里划掉**，标注为"TEE-only peripheral, not supportable"。
- 在 `文档/05-专项/` 里保留本报告，避免后来的人重复踩坑。
- 如果产品需求必须有指纹：走 **USB 指纹读卡器 + libfprint/fprintd**，或保留 Android 双系统。
- 如果只是想"研究一下"：本报告已经把"为什么不行"和"需要什么才能行"写清楚了；不建议再投入内核驱动开发。
