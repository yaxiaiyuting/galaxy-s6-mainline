## 二、四个必须同时满足的条件

蓝牙能工作的前提是下面四条**全部**成立，缺一条就表现为
`hci0: command 0x0c03 tx timeout` / `BCM: Reset failed (-110)`：

| # | 条件 | 说明 |
|---|---|---|
| 1 | **BT_EN 高** | gpf4-1，用 gpioset 常驻持有（gpio-hog 不可靠，见下） |
| 2 | **BT_WAKE 高** | gpr3-4 |
| 3 | **UART 时钟切到 24MHz 晶振 / 4 = 6MHz** | 不能走 AUD PLL，见第三节 |
| 4 | **LPASS UART CPU 中断使能** | LPASS 基址 0x11400000 + 0x58，BIT(1) |

## 三、根因链条（实测推导）

### 3.1 表面现象

```
Bluetooth: hci0: command 0x0c03 tx timeout
Bluetooth: hci0: BCM: Reset failed (-110)
```

HCI 层显示已提交 4 字节，但 UART 驱动的发送计数一直是 0
—— 说明**字节根本没进移位寄存器**。

### 3.2 第一层：UART 中断根本没到 GIC

- `/proc/interrupts` 里 UART 的中断计数恒为 0
- 但 UART 内部状态寄存器已显示"发送中断待处理"
- 读 LPASS 的 CPU 中断使能寄存器（0x11400000 + 0x58）：**0x00000000**

⇒ **LPASS 把 UART 中断屏蔽了**。打开 BIT(1) 后 GIC 计数立刻 0 → 1。

这条初始化在 vendor 驱动和主线 LPASS 驱动里都有，
但本板适配时没配 —— 属于**平台级遗漏**。

### 3.3 第二层：时钟源错了

**决定性证据（vendor DTS）**：

```dts
uart@11460000 {
    samsung,separate-uart-clk;
    clocks = <...>;
    clock-names = "gate_pclk4", "gate_uart4", "sclk_uart4";
    uart-sclk-frequency = <0x6f94740>;   // = 117,000,000
};
```

**但 117 MHz 是 vendor 在它自己的 PLL 配置下的值。**
本机实测（UART 内部回环，4096 字节收发一致）：
把分频按 117 MHz 设定后，实际速率只有 **≈48.4 kbaud**，
而不是目标 115200 —— **说明真实时钟与软件声明不一致**。

⇒ 结论：`fout_aud_pll` 那条路在本板并没有真正跑起来
（CMU_AUD 的 PLL 配置我们没能力正确还原，且 CMU_TOPC 在 AXI 死区）。

**最终方案：绕开 AUD PLL，切到板上已知的 24 MHz 晶振**
（`fin_pll`，来自 oscclk，稳定且不依赖任何未初始化的 PLL）。

- 24 MHz 晶振 → CMU_AUD 的 UART 分频 → **6 MHz**
- 6 MHz 下 115200 的分频 = 6e6/(115200×16) = 3.25
  → 整数 3 + UDIVSLOT 补偿 → 实测通信正常

### 3.4 第三层：gpio-hog 不可靠

DTS 里的 `gpio-hog` 只做了「申请 GPIO」，**没有把引脚功能切成输出**：

```
pin 178 (gpf4-1): (MUX UNCLAIMED) (GPIO UNCLAIMED)
 gpio-178 (bt_en) in  hi          ← 一直是 input！
```

而且 hog 一旦持有 line，用户态 `gpioset` 会报
`Device or resource busy`，彻底没法调试。

⇒ **移除 gpio-hog，改为 systemd 服务跑 `gpioset --mode=signal`**，
引脚功能由 `&serial_4` 的 `pinctrl-0` 显式设成 OUTPUT。

## 四、systemd 服务的三个坑

### 坑 1：`Type=notify` 拒绝子进程的 READY=1

```
Got notification message from PID 2127, but reception only permitted for main PID 2118
```

Python 脚本调用 systemd-notify 是 fork 出来的子进程。
修法：`NotifyAccess=all`，或者干脆用 **bash + Type=simple**（最终采用后者）。

### 坑 2：`power off` 是异步的 + Busy

```
Set Powered for hci0 failed with status 0x0a (Busy)
Set Public Address for hci0 failed with status 0x0b (Rejected)
```

- 固件刚下完时控制器还在 HCI_SETUP/POWERON 收尾 → `power off` 返回 Busy
- `power off` 被接受后也是异步的，立刻发 `set_public_address`，
  内核 `hdev_is_powered()` 仍为真 → `MGMT_STATUS_REJECTED`

修法：固件就绪后再 `sleep 4`，然后 **power off 重试直到 current settings
里真的没有 powered**，再设地址。

### 坑 3：dmesg 判断固件就绪会假阳性

`dmesg | grep "BCM4358A3 Samsung Zero EU"` 会匹配到**上一次尝试**的旧行。

修法：先记录基线计数，等计数**增加**。


### 安装

```sh
install -m755 g9209-bluetooth.sh /usr/local/libexec/
install -m644 g9209-bluetooth.service /etc/systemd/system/
install -m644 g9209-bluetooth.conf /etc/
install -m644 g9209_bt_transport.ko /lib/modules/$(uname -r)/extra/
depmod -a
systemctl daemon-reload
systemctl enable --now g9209-bluetooth.service
```

### 模块编译

```sh
make -C /lib/modules/$(uname -r)/build M=$(pwd) modules
```

## 六、初始化流程（脚本做的事）

```
1. 清理残留：pkill btattach / gpioset；rmmod g9209_bt_transport；等 hci0 消失
2. BT_EN 拉低 3 秒（硬复位 BCM4358，1 秒不够）
3. modprobe g9209_bt_transport
     ↳ mux 切到 24MHz 晶振 → UART 6MHz
     ↳ 打开 LPASS UART CPU 中断
4. BT_WAKE=1、BT_EN=1（gpioset 常驻持有）
5. btattach -B /dev/ttySAC0 -P bcm -S 115200
6. 等 dmesg 出现新的 "BCM4358A3 Samsung Zero EU"（基线计数法）
7. sleep 4 让控制器收尾
8. power off（重试直到真的断电）→ public-addr → power on
9. wait btattach（保持服务存活）
```

## 七、已知遗留

- **重启后必须重新初始化**：BCM4358 的地址和固件状态不持久，
  所以服务要在每次开机（以及模块重载后）跑一遍。
  当前 `Restart=on-failure` + 完整硬复位可以自愈。
- **AUD PLL 那条路彻底放弃**：CMU_TOPC 在 AXI 死区，
  无法还原 vendor 的 PLL 配置。24 MHz 晶振路径足够用。
- **功耗**：BT_WAKE 常驻高电平，未做 runtime PM。后续可优化。
