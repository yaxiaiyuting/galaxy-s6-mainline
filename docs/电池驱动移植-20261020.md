# MAX77843 电量计 + 充电器驱动移植（G9209 / Exynos7420，主线 Linux 6.6）— 2026-10-20

> 任务：解决"用着用着突然黑屏/没有电量显示"——给主线补上 BCM…不，是 **MAX77843 fuel gauge + charger**。
> 本轮范围：代码 + 分析 + DTS + 编译验证 + 跟随 Lead 的硬件 A/B；**未归我刷机，`.config` 由 Lead 改**（清单在 §5）。
> 结论：**最小可行方案已落地并编译通过**。硬件路径经历一次实测修正：
> **p215 用 hsi2c_1 时整机挂死（0x13650000 AXI 无应答）⇒ 默认改为 i2c-gpio（gpd2-2/3）访问 MAX77843，完全绕开 PERIC0 门控问题**。

## 0. TL;DR（给 Lead）

1. **主线缺的是两个驱动**：`max77843_fuelgauge.c` 和 `max77843-charger.c` 从未合并（`drivers/power/supply/` 里没有），MFD `drivers/mfd/max77843.c` 虽声明了 cell 但没有任何地方能绑定。本轮已补上（fuelgauge 完整读写、charger **只读**）。
2. **硬件 I2C 路线 p215 实测失败**：mainline `hsi2c_1` 的 `clocks` 指向 `clock_peric0(PCLK_HSI2C1)`，板级 DTS 又把 `clock-controller@13610000` 整体 disable ⇒ 先 -EPROBE_DEFER；用 fixed-clock 绕过 CCF 后，**p215 第一次访问 `0x13650000` 就 AXI 静默挂死**（S-Boot 把 CMU_PERIC0 的 HSI2C1 门控关了，内核打不开）⇒ p215 由看门狗复位。
3. **修正后的默认方案：i2c-gpio**（p217+）。只用 `pinctrl_bus0` 的 `gpd2-2`(SDA)/`gpd2-3`(SCL)（0x13470000，**已实测可访问**），完全避开 0x13650000 与 CMU_PERIC0；同板已证明 i2c-gpio 可用（touch-power dtsi 的 s2mps15/s2mpb02 就挂在 gpg3 的 i2c-gpio 上）。驱动代码不用改，只改 DTS。
4. **MAX77843 是四 I2C 地址芯片**：`0x66`=TOPSYS/PMIC、`0x69`=charger、`0x36`=fuel gauge、`0x25`=MUIC。主线 MFD 只给 0x66/0x69 建了 regmap，**0x36 没人建**（vendor MFD 建了）——本驱动自己建。**所以 `i2cdetect` 至少要看到 0x36/0x69 两个响应**，只看 0x66 不够。
5. **`CONFIG_MFD_MAX77843` 当前没开**（`# CONFIG_MFD_MAX77843 is not set`）。默认方案**不需要它**；只有切到 MFD 绑定模式才需要。
6. 需要的 CONFIG 只有两个：`CONFIG_FUEL_GAUGE_MAX77843=y`、`CONFIG_CHARGER_MAX77843=y`（Lead 已加，另外顺手加了 `CONFIG_MFD_MAX77843=y`——默认直连模式下它不会 probe，无副作用；`CONFIG_EXTCON_MAX77843` 保持关闭）。
7. **充电配置一行没写**：只读，S-Boot 配好的充电参数继续生效；安全。第二步再考虑写电流/浮充电压。

## 1. 阶段 1：原厂驱动提取（带行号）

### 1.1 数据格式（fuel gauge，全部按 16-bit、SMBus word 小端）

| 量 | 寄存器 | 原厂实现 | 换算 | 主线驱动 |
|---|---|---|---|---|
| VCELL | `0x09` (VCELL) | `max77843_fuelgauge.c:169-200` | 78.125 µV/LSB：`uV = raw*78125/1000` | `max77843_fg_read_vcell()` |
| VFOCV | `0xFB` | `:207-233` | 同上（OCV，暂不用） | — |
| AVG_VCELL | `0x19` | `:237-259` | 同上 | （可加） |
| CURRENT | `0x0A` | `:555-591` | 有符号 16-bit，1.5625µV/10mΩ = **156.25 µA/LSB**：`uA = (s16)raw*15625/100` | `max77843_fg_read_current()` |
| AVG_CURRENT | `0x0B` | `:593-637` | 同上 | `max77843_fg_read_avg_current()` |
| TEMP | `0x08` | `:337-368` | 16-bit 补码，LSB=1/256℃；返回 0.1℃：`tenths = (s16)raw*10/256` | `max77843_fg_read_temp()` |
| SOC（REP） | `0x06` | `:404-430` | 高字节=整数 %，低字节=1/256%；`soc = round(raw/256)` 限幅 0-100 | `max77843_fg_read_soc()` |
| VFSOC/AVSOC | `0xFF` / `0x0E` | `:370-402` | 同上（备用 SOC 源） | — |
| FULLCAP | `0x10` | `:455-469` | raw/2 = mAh ⇒ **500 µAh/LSB** | `CHARGE_FULL` |
| FULLCAP_NOM | `0x23` | `:488-502` | 同上 | `CHARGE_FULL_DESIGN` |
| REMCAP/Age/Cycles | `0x05/0x07/0x17` | `:471-655` | 非必需 | 未用 |

**关键结论：读取不需要"解锁/加载模型"**。原厂 `max77843_fg_init()`（`:1232-1292`）只做：
1. 读 FULLCAP/FULLCAP_NOM 作基准；
2. 若温度不用 FG 源，则写 `CONFIG(0x1D)` bit8（本驱动**跳过所有写**）；
3. 可选 QRTABLE20/30 校准（`:1549-1571`，只有 set_property 里触发，跳过）。
ModelGauge m3 的模型/算法在芯片内部自运行，主线只需读结果。所谓"解锁"是 MAX17042 写模型参数才需要（`MODEL_UNLOCK1=0x59/MODEL_UNLOCK2=0xC4`），读写电量值不需要。

### 1.2 充电器（只读需要的部分）

| 量 | 寄存器 | 原厂实现 | 解码 |
|---|---|---|---|
| VBUS 有效 | `CHG_DTLS_00(0xB3)` | `max77843_charger.c:128-167` | bits[6:5]=CHGIN_DTLS，`0x3`=输入有效 |
| 充电状态 | `CHG_DTLS_01(0xB4)` | `:169-207` | 低 4 位：0/1/2=CHARGING（预充/CC/CV），3/4=FULL（top-off/done），5/6/7=NOT_CHARGING（过温/热关机/超时），8/A/B=DISCHARGING，其余 UNKNOWN |
| 快充电流 | `CHG_CNFG_02(0xB9)` | `:350-362` | bits[5:0]：code≤2 → 100mA，否则 code×50mA |
| 输入限流 | `CHG_CNFG_09(0xC0)` | `:364-404` | bits[6:0]：≤3→100mA；≥0x78→4000mA；否则 q=code/3，余数 0/1/2 → q×100 / +33 / +67 mA |
| 充电使能 | `CHG_CNFG_00(0xB7)` | `:837-863` | bit0=CHG_MASK（1=charging enabled）；bit1=OTG，bit2=BUCK，bit3=BOOST |
| 中断状态 | `CHG_INT_OK(0xB2)` | `:405-426` | bit6=CHGIN_OK, bit5=WCIN, bit4=CHG, bit3=BAT, bit2=BATP |

原厂完整流程（`max77843_charger_probe:2249-` + `max77843_charger_initialize:1062-1116` + IRQ 状态机）非常复杂，依赖 Samsung `sec-battery` 框架（`power_supply_register` 的私有 prop、充电类型表、AICL、慢充、OTG…）。**本阶段刻意不 port**，只读状态就足够 GNOME/upower 显示"充电/满/放电"。

### 1.3 寄存器访问方式

- FG block 是**独立 I2C 从地址 0x36**（vendor：`drivers/mfd/max77843.c:44-47,284-290` 用 `i2c_new_dummy` 建 MUIC 0x25 / CHG 0x69 / FG 0x36；主线 `drivers/mfd/max77843.c:72` 只建了 0x69）。
- 原厂 FG 读 word 用 `i2c_smbus_read_word_data()`（`drivers/mfd/max77843.c:107-120`）⇒ **LSB first**，与主线 `max17042_battery` 的 `REGMAP_ENDIAN_NATIVE`(LE) 一致；本驱动直接用 `i2c_smbus_read_word_data()`。
- 本阶段**不写任何寄存器**。

## 2. 阶段 2：实现

### 2.1 新增 `drivers/power/supply/max77843_fuelgauge.c`

- `power_supply` 设备名 **`max77843-fuelgauge`**，`type = POWER_SUPPLY_TYPE_BATTERY`（必须；upower 只把 Battery 类型当系统电池）。
- 属性：`STATUS / PRESENT / TECHNOLOGY / CAPACITY / VOLTAGE_NOW / CURRENT_NOW / CURRENT_AVG / TEMP / CHARGE_FULL / CHARGE_FULL_DESIGN`。
- `STATUS`：优先查 `max77843-charger` 这个 power_supply；若 charger 驱动未就绪/未绑定，则用电流方向推断（>100mA 充电、<-100mA 放电、否则 FULL）。⇒ charger 驱动不工作时电量仍能显示。
- `PRESENT=1` 硬编码：能跑到这个驱动说明电池就在给整机供电（真机上没有电池开不了机），避免 STATUS bit 误判导致 upower 显示"电池缺失"。
- **双绑定模式**：
  - platform driver：MFD cell `max77843-fuelgauge`（`OF: maxim,max77843-fuelgauge`），probe 里用 `devm_i2c_new_dummy_device(adapter, 0x36)` 自建 FG client；
  - i2c driver：直接 `fuelgauge@36` 设备。
  - 两种模式共用 `max77843_fg_probe_common()`，读值全是懒加载（每次 `get_property` 读一次 I2C），upower 30s 轮询即可，不需要中断/工作队列。

### 2.2 新增 `drivers/power/supply/max77843-charger.c`

- `power_supply` 设备名 **`max77843-charger`**，`type = POWER_SUPPLY_TYPE_MAINS`。
- 属性：`STATUS / ONLINE / PRESENT / CHARGE_TYPE / CONSTANT_CHARGE_CURRENT_MAX / INPUT_CURRENT_LIMIT`（后两个是**读**当前配置，不是设置）。
- **只读**：不写 `CHG_CNFG_00/02/09`，S-Boot 设置的充电参数保持不变；不会出现"驱动写错电流/电压"的安全问题。
- 同样支持 MFD platform 绑定（用 `max77693_dev->regmap_chg`）和直接 `charger@69` i2c 绑定（自建 8/8 regmap）。

### 2.3 Kconfig / Makefile（`drivers/power/supply/`）


### 2.4 DTS 改动（`arch/arm64/boot/dts/exynos/exynos7420-zeroflte.dts`）

> **p215 之后修正**：默认不再用 hsi2c_1，改用 i2c-gpio。下面的第 3 条是当前默认；第 2/4 条保留为备用路径。

1. 新增 `hsi2c1_clk` fixed-clock（133MHz，备用；仅 `DSH_MAX77843_USE_HSI2C1=1` 时使用）；
2. **备用** `DSH_MAX77843_USE_HSI2C1=1`：`&hsi2c_1 { clocks=<&hsi2c1_clk>; status="okay"; fuelgauge@36/charger@69; }`（pinctrl 继承 `hs_i2c1_bus`=gpd2-2/3 func2 pull-up）。**注意：p215 实测会挂死**，除非先在 loader 里打开 CMU_PERIC0 的 HSI2C1 门控；
3. **默认（p217+）i2c-gpio 访问 MAX77843**：
   ```dts
   / {
       i2c_max77843: i2c-max77843 {
           compatible = "i2c-gpio";
           sda-gpios = <&gpd2 2 (GPIO_ACTIVE_HIGH | GPIO_OPEN_DRAIN)>;
           scl-gpios = <&gpd2 3 (GPIO_ACTIVE_HIGH | GPIO_OPEN_DRAIN)>;
           i2c-gpio,delay-us = <5>;        /* ≈100kHz */
           i2c-gpio,timeout-ms = <100>;
           #address-cells = <1>; #size-cells = <0>;
           fuelgauge@36 { compatible = "maxim,max77843-fuelgauge"; reg = <0x36>; };
           charger@69  { compatible = "maxim,max77843-charger";   reg = <0x69>; };
       };
   };
   ```
   - 引脚来源（vendor `ctc_stock.dts` hsi2c@13650000）：`gpio_sda=<&gpd2 2>`、`gpio_scl=<&gpd2 3>` ⇒ **SDA=gpd2-2, SCL=gpd2-3**；
   - generated DTB 校验：gpio phandle 反查 = `gpd2-gpio-bank` ✓，flags=0x6 与同板正常工作的 s2mps15/s2mpb02 i2c-gpio 节点**完全一致** ✓；
   - `hsi2c_1` 保持 mainline 默认 `disabled`（不再触发 p215 的挂死）。
4. 备用 `DSH_MAX77843_USE_MFD=1`：`max77843@66` + `fuelgauge/charger` 子节点 + `gpa1-4` IRQ + `chg-irq` pinctrl（需要 `CONFIG_MFD_MAX77843=y`，且 0x66 必须响应）。
   ⚠️ 各模式**互斥**（MFD 自己会在 0x69 建 dummy client），切换只能改宏。

> 为什么默认 i2c-gpio：把"电池能否显示"的依赖面压到最小——只需要 pinctrl_bus0（已实测可访问）+ gpd2 两个 GPIO；不碰任何未验证的 IP 块、不需要 MFD/IRQ/0x66、不需要 PERIC0 时钟。100kHz 对秒级轮询足够。

```
CONFIG_CHARGER_MAX77843=y
```

### 5.2 构建 + 启动

1. `cd <HOME>/linux7420 && ./build_mainline.sh pNNN`（p217 起默认就是 i2c-gpio 版 DTS）；
2. **loader 先 `watchdog arm`** 再 boot（虽然 i2c-gpio 不碰新地址，保持习惯）；
3. 期望 dmesg / 屏幕日志：
```

max77843-fuelgauge N-0036: fuel gauge status=0x....
max77843-fuelgauge N-0036: MAX77843 fuel gauge registered
max77843-charger N-0069: charger INT_OK=0x..
max77843-charger N-0069: MAX77843 charger registered (read-only)
```
（总线号 N 取决于 probe 顺序，`i2cdetect -l` 里找 `i2c-max77843` 或 `i2c-gpio`。）

### 5.3 验证节点（核心目标）

```bash
ls /sys/class/power_supply/          # 期望 max77843-fuelgauge / max77843-charger
cd /sys/class/power_supply/max77843-fuelgauge
cat capacity voltage_now current_now temp status present
#   capacity     0..100
#   voltage_now  µV（~3.4e6..4.4e6）
#   current_now  µA（充电为正、放电为负）
#   temp         0.1℃（250 = 25.0℃）
cat /sys/class/power_supply/max77843-charger/{online,status,input_current_limit,constant_charge_current_max}

i2cdetect -l | grep -i max77843   # 找到 i2c-gpio 总线号
i2cdetect -y <N>                  # 期望 0x36 / 0x69 响应（0x66、0x25 可选）
upower -d | grep -E "percentage|state|present"   # percentage ≈ capacity
```
- 验收：`capacity` 随放电下降/充电上升；GNOME 顶栏出电池图标；upower 10% 低电告警（不依赖 IRQ）。
- 只读 charger 驱动不会修改充电配置（安全）。

### 5.4 已静态核对、可提前排除的驱动层风险

- fuelgauge 用 `i2c_smbus_read_word_data`；i2c-gpio adapter 自带 SMBus 支持（i2c-gpio 注册 `I2C_FUNC_I2C|I2C_FUNC_SMBUS_EMUL`），且 emulated word read 字节序（`i2c-core-smbus.c:495`）符合 MAX17050（LSB first）。
- charger 用 regmap（8/8），走 i2c_transfer，不依赖 SMBus。
- `i2c-gpio` 节点 flags/structure 与同板已工作的 PMIC i2c-gpio 完全一致（DTB 反编译比对过）。
- 引脚无冲突：board DTS 里没有其它消费者使用 gpd2-2/3；pinctrl_bus0 驱动此前已被 gpg3 i2c-gpio 使用（能 probe）。

### 5.5 排障对照表（p217+）

| 现象 | 判据 / 下一步 |
|---|---|
| 成功 | 见 §5.2 日志 + §5.3 sysfs |
| `fuel gauge does not respond: -121`（remote I/O error） | i2c-gpio 已起但 0x36 无应答。① 把 `i2c-gpio,delay-us` 改 10（50kHz）重试；② 用 `devmem 0x134700e0` 看 gpd2CON 是否被 GPIO 驱动改成 func1、并观察 DAT 位在传输时翻转；③ 用 `i2cdetect -y <N>` 全扫确认地址 |

## 6. 风险与回滚

### 6.1 风险

| # | 风险 | 缓解 |
|---|---|---|
| R1 | **hsi2c_1 (0x13650000) 首次访问挂死 — 已实测发生（p215）** | 根因：CMU_PERIC0 的 HSI2C1 门控被 S-Boot 关掉、内核 CCF 无法打开。已绕开：默认 i2c-gpio，不访问该地址。若以后要回硬件 I2C：需 loader 开 `0x13610900` bit9（PCLK_HSI2C1）/`0x13610800`（ACLK_PERIC0），并先 watchdog 探 `0x13610000`/`0x13650000` |
| R2 | gpd2-2/3 引脚被别的消费者占用/状态异常 | board DTS 无其它 gpd2-2/3 消费者；pinctrl_bus0 已实测可访问；i2c-gpio 自己管理方向。若不通可用 devmem 检查 0x134700e0 |
| R3 | 0x36/0x69 地址不响应（芯片变体/地址不同） | 先 i2cdetect 全扫；若 0x36 无响应但 0x66 有，则用 MFD 模式验证；最坏情况 bus 通但 FG 块坏（不太可能，原厂 LOS20 WiFi/充电都靠它） |
| R4 | 只读驱动不影响充电，但若 S-Boot 之后没有重新使能充电（比如 fastboot 模式退出）⇒ 插线不充 | 第二步：按 vendor `battery,fast_charging_current/input_current_limit/chg_float_voltage` 写 CNFG_00/02/04/09；本阶段先观察 `input_current_limit`/`constant_charge_current_max` 读出值判断充电是否已开 |
| R5 | MUIC 未启用 ⇒ USB 检测/OTG 不完整 | 不影响当前 USB gadget（现在就是好的）；MUIC 留到第二步且必须先验证不会打断 USB |
| R6 | upower 对 `CHARGE_FULL`/`CHARGE_FULL_DESIGN` 单位敏感 | 已用 µAh（500 µAh/LSB）；若显示怪可先删掉这两个属性，只留 capacity/voltage |

### 6.2 回滚（一行级）

1. `fuelgauge@36` / `charger@69` 加 `status = "disabled";`（或整块 `&hsi2c_1 { status = "disabled"; }`）→ 电池驱动不加载，系统回到现状（不会挂）；
2. 或把 DTS 块删掉 + 两个 CONFIG 去掉；
3. 驱动本身只读 I2C（FG 只读；charger 只读 CHG 状态寄存器），**不会**写坏充电配置，回滚无副作用。

## 7. 后续（第二步，按优先级）

### 7.1 充电控制（真正解决"用着用着黑屏"的根治项）

> 现状：S-Boot 配置的充电参数继续生效（TWRP 能充电也说明硬件默认会充）；本驱动只读。
> 若 p217 里读到 `CHG_CNFG_00` bit0=0 或输入限流过小，就需要内核显式使能/配置。
> 以下数值全部来自 vendor（`max77843_charger.c`）+ G9209 原厂 `battery` 节点，**不要盲写**——
> 先读回 `CHG_CNFG_00/02/04/09` 确认现状，再决定写多少。

| 寄存器 | 字段 | 编码 | G9209 建议值（vendor battery 节点） |
|---|---|---|---|
| `CHG_CNFG_00(0xB7)` | bit0 CHG enable | 1=使能充电（bit2 BUCK 保持 1） | 0x05（CHG\|BUCK） |
| `CHG_CNFG_02(0xB9)` | bits[5:0] 快充电流 | `mA/50`（≤2 视为 100mA）；bits[7:6] OTG 限流保留 | 2100mA ⇒ 0x2A |
| `CHG_CNFG_04(0xBB)` | bits[5:0] 浮充电压 | `(mV-3650)/25`；bits[7:5] MINVSYS 保留 | 4350mV ⇒ code 28（0x1C）；4400mV ⇒ code 30 |
| `CHG_CNFG_09(0xC0)` | bits[6:0] 输入限流 | vendor 反编码：`code=3q(+0/1/2)`，q=100mA 整数部分，余数 33/67mA | 1800mA ⇒ 0x36 |
| `CHG_CNFG_01(0xB8)` | 重启阈值 | 0x10/0x20/0x30=150/200/disabled mV | 可选 |

原厂 `battery` 节点关键值（`ctc_stock.dts:8300+`，数组按线缆类型索引，索引 0 = 默认/AC）：
`battery,input_current_limit=<0x708(1800mA) ...>`、`battery,fast_charging_current=<0x834(2100mA) ...>`、
`battery,chg_float_voltage=<0x10fe(4350mV) / 0x1130(4400mV，另一机型)>`、
`battery,full_condition_soc=<0x5d(93%)>`、`battery,full_condition_vcell=<0x109a(4250mV)>`。

实现建议（等 p217 只读数据确认后再做）：
1. charger 驱动加 `set_property` 支持 `POWER_SUPPLY_PROP_CONSTANT_CHARGE_CURRENT_MAX / INPUT_CURRENT_LIMIT / CHARGE_TYPE`；
2. probe 时若 DT 有 `maxim,fast-charge-current-microamp` / `maxim,input-current-limit-microamp` /
   `maxim,float-voltage-microvolt` / `maxim,charge-enable` 才写（默认不写，保持只读安全）；
3. 温度保护：读 FG TEMP（本驱动已提供），>45℃ 或 <0℃ 禁止快充（可先只 log）；
4. 充满判定：FG `capacity>=93% && VCELL>=4.25V` 或 charger DTLS=done ⇒ FULL。

### 7.2 其他

1. **fuel alert IRQ**：SALRT(0x03)+CONFIG bit2+`INTSRC_MASK`；或直接给 charger/gpa1-4 加 EINT。低电告警目前由 upower 容量阈值承担，够用。
2. **MUIC/extcon**：`CONFIG_EXTCON_MAX77843` 前必须先验证不打断 DWC3 gadget（单独 A/B）。
3. **Samsung 低电补偿/容量校准**：原厂 `max77843_fuelgauge.c:993-1660`；若 SOC 跳变再 port。
4. **loader `bat` 命令**（`电池与启动问题-20261020.md` §2.3 建议）：复用 loader 已有 GPD2 bit-bang，读 FG `0x06/0x09` + charger `0xB3/0xB4`，每次 boot 前记录电池电压/充电状态——对排查"黑屏是否掉电"极有价值，但属于 uniLoader 改动，由 Lead 决定。

## 8. 事实边界

## 10. 硬件实测记录（p215，2026-10-20 22:5x）

- p215 = 第一版（hsi2c_1 + fixed-clock）：
  - 现象：**整机 AXI 静默挂死，由 loader watchdog 复位**（无 oops）。
  - 结论：`0x13650000`（hsi2c_1 控制器）被访问时永不应答。最可能原因：**CMU_PERIC0(0x13610000) 里 HSI2C1 的 PCLK 门控在 S-Boot 里是关的**，而本板把整个 CMU_PERIC0 节点 disable，内核无法通过 CCF 打开；fixed-clock 只解决 CCF 时钟对象缺失，不解决硬件门控。
  - 该结果与本文 §6.1 R1 预判一致。
- p216 = 对照镜像（hsi2c_1 `status="disabled"`）：用于验证"驱动/总线不参与时系统本身正常"。
- **处置**：默认改为 i2c-gpio（§2.4 第 3 条），彻底避开 0x13650000。硬件 I2C 恢复路径见 R1。
- **i2c-gpio 方案的"金标准"证据（来自 `电池与启动问题-20261020.md`，loader 源码级确认）**：
  uniLoader 自己就在 **GPD2[2:3] 上 bit-bang I2C 访问 MAX77843 MUIC**（`uniLoader/drivers/usb-console/muic.c`，
  "只拉低、释放靠板上拉"），实测日志 `[muic] id=b5 ...` ⇒ 这两根线**硬件层面已证明可读 MAX77843**、
  上拉存在；内核 i2c-gpio 的开漏语义（gpiolib `gpio_set_open_drain_value_commit()`：
  1→direction_input / 0→direction_output(0)）与 loader 完全等价；同板 gpg3 i2c-gpio（s2mps15/s2mpb02）
  已工作。⇒ p217 方案可行性高，剩余风险只在 probe 顺序/延时。
- **p216 的用户态挂死与本驱动无关**（`电池与启动问题-20261020.md` §1：config 差异仅 3 项、DTB 里
  hsi2c_1 仍 disabled、电池 child 不会实例化；头号嫌疑是电池欠压/无充电管理）。
  ⇒ 也从侧面说明本任务"有电量显示+低电告警"的价值，以及第二步充电管理的必要性。
