# 图形性能优化 —— GTK4 真正走 GPU

日期：2026-10-20
状态：**✅ 已应用并实测**

---

## 一、问题

1. **GNOME 设置界面打不开**
2. **整体帧率很低，尤其应用窗口拖动/滚动明显卡顿**

---

## 二、根因

### 2.1 主因：`GSK_RENDERER=cairo` 强制软件渲染

早期为了绕开 panfrost 的 `js fault` / `SError` 崩溃，
在 `/etc/environment` 里全局设了：

```
GSK_RENDERER=cairo
```

后果：**所有 GTK4 应用**（GNOME 设置、文件管理器、文本编辑器、
计算器…）都退化成 Cairo 纯软件渲染。在 2K（1440x2560）屏 + 300% 缩放下
几乎不可用，而且 GTK4 的 cairo 后端本身有 bug —— 设置界面就是因此打不开。

### 2.2 次因：`PAN_MESA_DEBUG=noafbc`

`noafbc` 会关掉 **AFBC**（ARM Frame Buffer Compression）带宽压缩。
在 Mali-T760 这种老 GPU 上，关掉压缩意味着显存带宽压力大增，
填充率受限的场景（模糊、阴影、大面积重绘）掉帧明显。
`nocrc` 只是跳过 CRC 校验，代价小得多。

### 2.3 附带发现：usb0 抢了默认路由

`/etc/systemd/network/20-usb0-static.network` 里配了 `Gateway=192.168.42.1`，
生成的默认路由是 `proto static`、**metric 0**，
优先级高于 WiFi 的 DHCP 默认路由（metric 600）。
于是所有出网流量走 USB（宿主没做 NAT）→ 手机完全没网，apt 全挂。

---

## 三、修复

```sh
# /etc/environment
GSK_RENDERER=gl        # GTK 4.8 认 gl/vulkan/cairo；ngl 是 4.14+ 才有
PAN_MESA_DEBUG=nocrc   # 保留 AFBC，仅跳过 CRC

# /etc/systemd/system/gdm.service.d/50-g9209-render.conf
[Service]
Environment=GSK_RENDERER=gl
Environment=PAN_MESA_DEBUG=nocrc

# /etc/systemd/network/20-usb0-static.network —— 去掉 Gateway
[Network]
Address=192.168.42.2/24
LinkLocalAddressing=no
```

## 六、遗留问题

### 6.1 panfrost js fault

```
panfrost 14ac0000.gpu: js fault, js=1, status=DATA_INVALID_FAULT
```

驱动能自愈（重置 job slot），系统不崩，但会有视觉毛刺。
这是 panfrost 在 Mali-T760 上的已知问题（Mesa 22.3 已较老），
根因大概率是某个 GPU 特性报告错误（`features: 00000000,00000407`）。

后续方向：
- 升级 Mesa（需要 backports 或自行编译）
- 在 panfrost 里针对性禁用出问题的特性
- 用 `PAN_MESA_DEBUG=noafbc` 换取稳定（代价是性能）

### 6.2 300% 缩放的性能代价

300% 缩放意味着每个逻辑像素渲染成 3×3 物理像素，
总填充量是 100% 时的 **9 倍**。
在 2K 屏上这是很大的负担，尤其 `desktop blur` 场景只有 84 FPS。

如果想更快，可以把缩放降到 200%（填充量降到 4/9），
再用 `text-scaling-factor` 放大文字。但这会改变 UI 尺寸，
需要用户确认观感。
