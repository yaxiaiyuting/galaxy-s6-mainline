## 0. 结论速览（TL;DR）

**根因不是 systemd、不是 rootfs、不是日志配置，而是 PID 1 的身份错误：**

> ramdisk 的 `/init`（`pmsg-init`）是 PID 1，但它 `fork()` 出子进程去执行 `/bin/sh /etc/rc`。
> 因此 `/etc/rc`、`switch_root`、systemd **全部是 PID ≥ 2 的子进程**。
> busybox 1.38.0 的 `switch_root` 在 `getpid() != 1` 时直接打印 usage 并 `exit(1)`，
> **根本不做任何切换**；即使绕过它，systemd 252 也会以
> `"Can't run system mode unless PID 1."`（`src/core/main.c:2537-2541`）拒绝启动。

**修复**：让 PID 1 进程本人完成切换（PID 1 handover）。

1. `/etc/rc` 挂载好新根后不再调用 `switch_root`，而是写 `/tmp/dsh-handover` 并 `exit 88`；
2. PID 1（`pmsg-init`）检测到子进程退出码 88 后，自己 `execv("/bin/switch_root", ...)`；
3. switch_root 以 PID 1 身份通过检查 → `MS_MOVE` + `chroot` + `exec /sbin/init`
   → **systemd 以 PID 1 运行**。

**验证**：宿主 QEMU virt + 真实 Debian 12 rootfs 的端到端模拟 **两次全部通过**：
systemd 252 以 PID 1 启动，`sysinit/basic/multi-user/graphical.target` 全部到达，
出现 `g9209 login:` 提示，`journald/udevd` 正常工作（证据见 §3）。
最终镜像 p196 内嵌的 `/init` 也用同样方法复核通过（含新增的 kmsg 双保险载体）。

## 1. 事实更正：`chroot ... ENOENT` 不是 rootfs 部署问题

### 1.1 现象回顾

早期诊断脚本报告：

```
chroot /mnt /bin/sh -c '...'
→ chroot: can't execute '/bin/sh': No such file or directory   (ENOENT)
```

而宿主 `/mnt/debclean` 里 `/bin/sh`、`dash`、`/lib/ld-linux-aarch64.so.1`、
`libc.so.6` 全部存在且完整。

### 1.2 真正原因

旧版 `dsh_precheck()` 在 **`mount /dev/sda20 /mnt` 之前** 调用：

```sh
dsh_precheck() {
    mount -t proc proc /mnt/proc     # 此时 /mnt 还是 ramdisk 里的空目录！
    ...
    chroot /mnt /bin/sh               # chroot 进了 ramdisk 自己的空 /mnt
}
```

`chroot /mnt` 成功（`/mnt` 是 ramdisk 的空目录），随后 busybox `chroot`
`execve("/bin/sh")` 在**空的 `/mnt` 里**当然 ENOENT。
所以该 ENOENT **不是 rootfs 问题，也不是 tar/符号链接问题**。
（`chroot` 自检后来被移到 `dsh_try_switch_root()` 里、mount 成功之后，即当前 rc 的 L104-111。）

### 1.3 宿主 qemu 验证：rootfs 用户态完全正常

```bash
qemu-aarch64 -L /mnt/debclean /mnt/debclean/bin/sh -c 'echo CHROOT_OK'
# → CHROOT_OK
qemu-aarch64 -L /mnt/debclean /mnt/debclean/usr/bin/dash -c 'echo DASH_OK'
# → DASH_OK
qemu-aarch64 -L /mnt/debclean /mnt/debclean/lib/systemd/systemd --version
# → systemd 252 (252.39-1~deb12u2) +PAM +AUDIT ... default-hierarchy=unified
qemu-aarch64 -L /mnt/debclean /mnt/debclean/usr/lib/ld-linux-aarch64.so.1 \
             --list /mnt/debclean/lib/systemd/systemd
# → libsystemd-core-252.so / libsystemd-shared-252.so / libc.so.6 / libseccomp ...
#   全部解析成功
```

**结论：Debian 用户态二进制本身完好，不要再怀疑部署。**
（本次 E2E 模拟里同样的 rootfs 完整启动到了 multi-user，见 §3。）

### 1.4 以后遇到 `chroot ... exec ENOENT` 的 30 秒排查清单

1. 确认 chroot 之前目标分区**真的已经 mount**（`grep /mnt /proc/mounts`）；
2. `readlink -f /mnt/bin/sh` / `/mnt/lib` / `ld-linux-aarch64.so.1` 符号链接链是否完整；
3. `chroot /mnt /usr/lib/aarch64-linux-gnu/ld-linux-aarch64.so.1 --list /usr/bin/dash`
   （直接调用动态加载器，可区分"ELF 损坏"与"interpreter 缺失"）；
4. 检查 ext4 是否 `nodev/noexec`（会得到 EACCES 而不是 ENOENT）；
5. tar 部署完整性（tarball sha256、解压日志、`find | wc -l` 对比宿主）。

## 2. 真正的根因链（源码级）

### 2.1 PID 1 是谁：`pmsg-init`，而不是 `/etc/rc`

`bringup/pmsg-init.c`（p196 版本）：

| 行号 | 代码 | 含义 |
|---|---|---|
| L101 | `if (argc != 1 \|\| getpid() != 1) return 2;` | 只允许作为 PID 1 运行（我们 qemu 直接跑它也复现了 exit 2） |
| L128 | `child = fork();` | **fork 出子进程** |
| L135 | `execve("/bin/sh", {"sh", "/etc/rc"}, env);` | 子进程执行 `/etc/rc`（PID≥2） |
| L169-240 | DSH handover（本次新增） | 见 §4 |

⇒ **`/etc/rc`、`switch_root`、systemd 全部是 PID ≥ 2 的子进程。**
`pmsg-init` 留在父进程里做 `poll()`/`waitpid()` 报告与 120 秒超时/自动重启逻辑，
这正是它当初设计成 fork 的原因——但和 systemd 对 PID 1 的要求根本冲突。

### 2.2 busybox `switch_root` 的前置条件与失败行为

源码：`util-linux/switch_root.c`（ramdisk 里是 **busybox 1.38.0**，Debian 版；
对应上游 1.36 源码 L233）：

```c
/* L233 附近 */
if (!dry_run && getpid() != 1) {
    // Show usage, it says we must be PID 1
    bb_show_usage();
}
```

`bb_show_usage()` = 向 stderr 打印 usage 文本 + `exit(EXIT_FAILURE)`（exit 1），
**位置在任何实际切换动作之前**（在 `delete_contents("/")`、`mount(".", "/", MS_MOVE)` 之前）。

本地 qemu 直接复现（无需手机）：

```bash
qemu-aarch64 /tmp/rd-sysd/bin/busybox switch_root /mnt /sbin/init
# → Usage: switch_root [-c CONSOLE_DEV] NEW_ROOT NEW_INIT [ARGS]
#   ... PID must be 1. NEW_ROOT must be a mountpoint.
# → exit=1
```

完整前置条件（源码顺序）：

1. 参数 ≥ 2 个；
2. `NEW_ROOT` 是**挂载点**且与 `/` **不同设备**（否则 usage 退出）；
3. `getpid() == 1`（否则 usage 退出）；
4. 当前根 `/` 是 ramfs/tmpfs（否则 `root filesystem is not ramfs/tmpfs`）；
5. 当前 `/` 存在普通文件 `/init`；
6. 之后才：`delete_contents("/")` 释放 initramfs → `mount(".", "/", MS_MOVE)` →
   `chroot(".")` → `execv(NEW_INIT, ...)`。

**exec 失败时**：`bb_perror_msg_and_die("can't execute '%s'")` → 打印后 `exit`。
若此时是 PID 1 → 内核 `panic("Attempted to kill init!")` → `panic=10` 重启。
**但在旧架构里 switch_root 只是子进程，它 exit 不会 panic，PID 1 继续活着。**

### 2.3 systemd 252 的要求

`src/core/main.c`（v252）关键位置：

| 行号 | 内容 |
|---|---|
| L2537-2541 | `safety_checks()`：`if (arg_action == ACTION_RUN && arg_system && getpid_cached() != 1) return log_error_errno(EPERM, "Can't run system mode unless PID 1.");` |
| L2720-2800 | `if (getpid_cached() == 1) { arg_system = true; ... log_set_target(LOG_TARGET_KMSG); log_open(); ... }`（**PID1 早期默认日志进 kmsg**） |
| L2482-2520 | `parse_configuration()`：**先** `parse_config_file()`（/etc/systemd/system.conf + conf.d），**后** `proc_cmdline_parse()`（`systemd.*` cmdline）⇒ cmdline 后解析、覆盖配置文件 |
| L2868 | `parse_configuration()` 调用点 |
| L2876 | `safety_checks()` 调用点（在 PID1 早期 kmsg 打开之后） |
| L2935 | 最终 `log_open()`（按 config+cmdline 决定的 target 重新打开） |

补充：非 PID1 启动时 systemd 会走 "Running as user instance" 分支
（`arg_system=false`），随后 `sd_booted() <= 0` 检查也会失败：

```
"Trying to run as user instance, but the system has not been booted with systemd."
```

即：**systemd 在非 PID1 上是双重拒绝，不可能"勉强跑起来"。**

### 2.4 六个现象的统一解释

| 现象 | 解释 |
|---|---|
| `exec switch_root` 之后再无任何输出 | switch_root 打印 usage 到 **stderr**；rc 子进程的 stdout/stderr 被 `pmsg-init` 重定向进 pipe（`pmsg-init.c` 子进程分支 `dup2(pipefd[1],1/2)`），由父进程 `report()` 转写。`report()` 写的是 **父进程启动时 open 的 `/dev/console` fd**——而 `ttyGS0` 的**内核 console 要等 rc 配好 ACM gadget 之后才注册**（`u_serial.c:1019 gs_console_init()` → `register_console()`），`pmsg-init` 启动时 `/dev/console` 只能解析到 tty0（VT/dummy console）。所以 usage 文本进了 tty0，USB 看不到。rc 的 `dsh_log` 之所以可见，是因为它**每次重新 `> /dev/ttyGS0`**。 |
| 没有 panic、没有重启 | PID 1（`pmsg-init`）自始至终没退出：子进程 exit(1) 后它读到 pipe EOF → 打印 REPORT END（同样不可见）→ 未设置 `automatic` 时进 `idle:` 循环 `pause()`。`panic=10` 只对内核 panic / PID1 退出生效，永远不会触发。 |
| `/var/log/journal/` 为空 | systemd 一秒钟都没运行，自然没有 journal。 |
| 自定义 `dsh-diag.service` 没生成 `/dsh-diag.txt` | 同上，systemd 未运行。 |
| USB 设备一直是 `1209:9210`（内核 ACM） | gadget 是 ramdisk 的 rc 通过 configfs 建好的内核对象，从未切根，所以一直存在。这反而证明了"没有发生任何切换"。 |
| 手机"看起来像进了 Debian"（早期 p185 出现过 BusyBox shell） | 误判：那是 rc 尾部 `usb_console` 在 **ramdisk** 里起的 `getty -l /bin/sh`（它打开 `/dev/ttyGS0`，所以 USB 可见），不是 Debian 的 shell。 |

**附注（`LogTarget=journal`）**：`/etc/systemd/system.conf.d/dsh.conf` 里的
`LogTarget=journal` 不是本次根因（systemd 根本没跑），但如果 systemd 真的跑起来，
它会因为早期 journald 尚未就绪而把日志丢掉。既然 bootargs 已加
`systemd.log_target=kmsg`（cmdline 后解析、会覆盖配置文件），建议仍删掉该文件保持干净。

## 4. 修复方案（已落地 p196）

### 4.1 改动清单

#### ① `bringup/pmsg-init.c`：PID 1 handover（L169-240）

```c
/* DSH: PID1 handover.
 * /etc/rc 是 fork 出来的子进程，它跑 switch_root 会被 busybox 的
 * getpid()!=1 检查拒绝；所以 rc 用 magic exit code 88 请求 PID1 代劳。 */
if (WIFEXITED(status) && WEXITSTATUS(status) == 88) {
    /* 读取 /tmp/dsh-handover（两行：newroot / init，缺省 /mnt /sbin/init） */
    ...
    /* 写 /dev/ttyGS0：不依赖 /dev/console 解析，USB 直接可见 */
    tty = open("/dev/ttyGS0", O_WRONLY | O_NOCTTY | O_CLOEXEC);
    if (tty >= 0) { dprintf(tty, "G9209 PID1 HANDOVER root=%s init=%s pid=%d\n", ...); ... }
    /* p196 新增：kmsg 双保险（第二载体）。printk 直接分发到所有 console，
     * 完全不经过 tty open/close/drain 路径，即使 ttyGS0 fd 写失败也能看到。 */
    if (kmsg >= 0)
        dprintf(kmsg, "<6>G9209 PID1 HANDOVER root=%s init=%s\n", hroot, hinit);
    ...
    char *hargs[] = {"switch_root", hroot, hinit, NULL};
    execv("/bin/switch_root", hargs);        /* 此时 PID==1，检查通过 */
    /* 失败：ttyGS0 + report + kmsg 三重记录，然后 _exit(127)
     * → PID1 退出 → kernel panic → panic=10 重启 → ramoops/pstore 留尸体 */
    ...
    _exit(127);
}
```

设计要点：
- **必须是 PID 1 本人 `exec`**——没有任何"子进程变成 PID1"的办法；
- 复用 busybox `switch_root`（而不是自己写 MS_MOVE/chroot），因为它已经处理
  `delete_contents`、跳过其它文件系统挂载点、`MS_MOVE` 后 `chroot(".")` 等细节；
- `/tmp/dsh-handover` 可行：`pmsg-init` 在 `fork()` **之前**已挂载 `/tmp` tmpfs
  （`pmsg-init.c` L86 附近 `virtual_mount("/tmp","tmpfs",...)`），父子同 mount namespace，
  子进程 close 后父进程再读，顺序有保证；
- 子进程 `exit 88` 不会被 `set -e`/`|| true` 之类吞掉：`exit` 直接结束 shell，
  父进程 `waitpid` 得到 `WIFEXITED && WEXITSTATUS==88`；
- `WIFEXITED()` 在超时杀子（SIGKILL）时为 false，不会误触发；`status` 初值 0 也不等于 88。

#### ② `bringup/rc`：挂载 + 门禁 + handover 请求


### 4.2 为什么不是别的方案

| 方案 | 为什么不采用/仅作备选 |

### 4.3 rootfs 侧建议（下一版 rootfs 镜像可带上）

1. **删除** `/etc/systemd/system.conf.d/dsh.conf` 中的 `LogTarget=journal`
   （cmdline 会覆盖，但删掉更干净、避免以后忘记加 cmdline 时踩坑）。
2. **免密 USB shell**（可选，强烈建议，方便后续调试）：
   `/etc/systemd/system/serial-getty@ttyGS0.service.d/autologin.conf`：
   ```ini
   [Service]
   ExecStart=
   ExecStart=-/sbin/agetty -a root -L 115200 ttyGS0 vt100
   ```
3. **可选 mask**：`ssh.service`、`cloud-init*`、`systemd-networkd-wait-online.service`
   （cloud 镜像自带，手机上大概率失败并拖慢 multi-user 约 90s）。
4. **journal 持久化无需配置**：`/var/log/journal` 已存在（root:adm 2755），
   `Storage=auto` 自动持久化。**journald 的 kernel cmdline 只支持
   `systemd.journald.forward_to_*`/`max_level_*`，不支持 `storage=`**
   （`src/journal/journald-server.c:1624-1673`），别再找 storage 的 cmdline 参数。
5. **可选最早 marker unit**（用于离线判断 systemd 是否真的启动）：
   `/etc/systemd/system/dsh-early.service`：
   ```ini
   [Unit]
   DefaultDependencies=no
   After=systemd-journald.socket
   Before=sysinit.target
   [Service]
   Type=oneshot
   ExecStart=/bin/sh -c 'echo "PID1=$(cat /proc/1/comm) uptime=$(cut -d. -f1 /proc/uptime)" > /dsh-early.txt'
   [Install]
   WantedBy=sysinit.target
   ```
   `systemctl enable dsh-early.service`
   （不过修复后 kmsg 日志已经足够，这个只是双保险。）
6. 不要用 `/var/lib/systemd/` 时间戳、journal 目录空做"systemd 是否启动"的判据：
   前者正常启动也不一定写，后者在 `Storage=volatile` 时重启即丢。

若 multi-user 迟到 ~90s，先看 `sysinit/basic`（7s 量级）即可判定成功。

### B. 看到 `PID1 HANDOVER`，但**没有** systemd 日志

1. 先等 10~20 秒（kmsg 可能有延迟）；确认 `dmesg | tail`。
2. 若 10 秒周期重启 → systemd PID1 崩溃 → `panic=10`。用 ramoops 取尸体：
   `./read-ramoops.sh`（该设备 DTS 有 `ramoops@46d80000`，`CONFIG_PSTORE_RAM/CONSOLE=y`）。
3. 若没有重启也没日志：
   - rc 里把 `$TARGET` 临时改成 `/bin/sh`（`dsh_try_switch_root /dev/sda20 /bin/sh`）
     做 Plan C：先验证"切根后 shell + USB console 可用"；
   - 起来后手动 `exec /lib/systemd/systemd`（此时进程不是 PID1 会被拒，仅用于看报错）；
     更有效的是在 shell 里 `cat /dsh-stage.txt /proc/mounts`，确认 proc/sys/dev/run 都挂上；
   - 检查 `/etc/machine-id` 是否存在且非空、`/etc/fstab` 是否与设备匹配；
   - 给 bootargs 加 `systemd.log_level=debug`（已有）+ 试 `systemd.mask=systemd-udevd.service`
     排除 udev 早期问题。
4. 一种常见早期失败：`/sys/fs/cgroup` 挂载/cgroup2 不可用（内核配置已确认齐全，
   但可用 `systemd.unified_cgroup_hierarchy=1` 显式指定）。

### C. rc 日志都正常，但**没有** `PID1 HANDOVER`

说明 `exit 88` 没有传导到 pmsg-init：
1. 看 pmsg 报告的 `REPORT END ... status=...`；**22528 = 88<<8** 表示子进程确实 exit 88；
2. 若 status 不是 22528：rc 没有走到 `exit 88`（precheck 失败 return、mount 失败、
   或被 `set -e`/函数上下文影响）——检查 `/dsh-stage.txt` 与 rc 日志最后一条；
3. 若 status=22528 但仍无 HANDOVER：检查 `pmsg-init` 的 `WIFEXITED/WEXITSTATUS`
   分支是否被编译进去（`strings` 查 `PID1 HANDOVER`），以及 `/tmp/dsh-handover` 是否写入；
4. 临时方案：把 pmsg-init 改成 `execve("/bin/sh", {"sh","/etc/rc"})`（PID1 直接变成 rc），
   验证"PID1=rc 时 switch_root 能跑"，即可反证问题只在 handover 传导。

### D. 只有 `switch: start`，之后停住

多半是块设备/mount 问题：
- rc 日志应有 `switch: waited Ns, /dev/sda20: FOUND/MISSING`、`mount FAILED`；
- 检查 `/proc/partitions`、`ls /sys/class/block`、`dmesg | grep -E 'ufs|sd[a-z]'`；
- ext4 若曾有并发写坏（例如宿主 loop 挂载同一镜像/手机侧双写），需要 `fsck.ext4 -y`；
- 分区 table/号变化时 rc 的 `PART` 参数要跟着改。

### E. 完全无输出（连 rc 日志都没有）

1. USB ACM 内核 console 依赖 gadget 注册（`u_serial.c:1019 gs_console_init()` →
   `register_console()`，`CON_PRINTBUFFER` 会在注册时把整段 dmesg 回放到 USB）；
2. 在 ramdisk 诊断里看 `cat /proc/consoles`、`/sys/class/udc`、
   `ls -la /dev/ttyGS0`、`cat /proc/cmdline`（确认 `console=ttyGS0` 在最后）；
3. 用 `keep_bootcon`/`earlycon` 或 pstore 兜底。
