## 1. 路径 A 判定依据

### 1.1 simpledrm 身份确认（源码 + 实测双重）

`.config`（`linux-6.6/.config`）：
```
CONFIG_DRM=y
CONFIG_DRM_SIMPLEDRM=y                     # 4390 行
CONFIG_DRM_FBDEV_EMULATION=y               # 4168 行
CONFIG_FRAMEBUFFER_CONSOLE=y               # 4497 行
CONFIG_DRM_GEM_SHMEM_HELPER=y
CONFIG_DRM_PANFROST=y
```

`drivers/gpu/drm/tiny/simpledrm.c`（本树）：
```c
#define DRIVER_NAME "simpledrm"
...
static struct drm_driver simpledrm_driver = {
    DRM_GEM_SHMEM_DRIVER_OPS,              // 含 .dumb_create = drm_gem_shmem_dumb_create
    .driver_features = DRIVER_ATOMIC | DRIVER_GEM | DRIVER_MODESET,
};
static struct platform_driver simpledrm_platform_driver = {
    .driver = {
        .name = "simple-framebuffer",       /* connect to sysfb */
        .of_match_table = simpledrm_of_match_table,   // compatible = "simple-framebuffer"
    },
};
```

手机实测（Lead 之前的查询）：
```
/sys/class/drm/card0/device/uevent:
  DRIVER=simple-framebuffer
  OF_NAME=framebuffer
  OF_FULLNAME=/chosen/framebuffer@e2a00000
  OF_COMPATIBLE_0=simple-framebuffer
/sys/class/drm/card0-Unknown-1/modes → 1440x2560     ← simpledrm 的 connector 类型为 Unknown
/dev/dri/card1 → DRIVER=panfrost (/soc@0/gpu@14ac0000)
```
⇒ 与 simpledrm 源码逐项对上：**card0 就是 simpledrm 的 KMS 设备**，`fbcon` 走 `drm_fbdev_generic`。

### 1.2 硬件显示链路其实一直是通的（本方案最大的底气）

loader 注入的 DT（`/tmp/p207.dts`，由 uniLoader 生成，实际节点在 `/chosen/framebuffer@e2a00000`）：
```dts
framebuffer@e2a00000 {
    compatible = "simple-framebuffer";
    reg = <0x00 0xe2a00000 0x00 0x1000000>;   // 16 MB @ 0xe2a00000
    width = <0x5a0>;                           // 1440
    height = <0xa00>;                          // 2560
    stride = <0x1680>;                         // 5760 = 1440*4
    format = "a8r8g8b8";                       // DRM_FORMAT_ARGB8888
};
```
这块内存是 **S-Boot 初始化好 DECON/DSIM/panel 后留下的扫描缓冲**。Linux 里的 simpledrm 只做一件事：把用户态内容 memcpy 进这块内存；真正的扫描输出一直由 bootloader 配置好的显示硬件完成（所以 fbcon 能显示、且我们**从不访问 DECON/DSIM/CMU_DISP 寄存器**，绕开了本板所有"未上电 IP 块访问即挂死"的风险）。

### 1.3 mutter 在 simpledrm 上能跑：实测证据 + 源码依据

**实测证据（p207 启动串口日志，`/tmp/wifi_p207_snap2.log`）**：
```
[  OK  ] Started gdm.service - GNOME Display Manager.
[   25.877] systemd[1]: systemd-logind.service: Got notification message from PID 263
           (FDSTORE=1, FDNAME=session-c1-device-226-0)
[   25.877] systemd-logind.service: Added fd 12 (session-c1-device-226-0) to fd store.
```
- `session-c1` = logind 的 **greeter 显示会话**（class c 类），`device-226-0` = 主设备号 226(DRM)、次设备号 0 = **card0**。
- 即：**GDM 已经成功把 greeter 会话建立起来，并把 simpledrm 的 card0 的控制权交给了 greeter**。
- 紧接着 26.465s 的崩溃栈 `Comm: gnome-shell` ⇒ **gnome-shell 已经启动并在跑**。
- 之前那次 gdm 卡 `activating` 是偶发/早期 boot 状态，p207 这次 gdm 是正常 Started 的。

**源码依据（Debian 12 对应 mutter 43.8，逐行核对）**：
1. `src/backends/native/meta-backend-native.c create_render_device()`：
   只有 `meta_backend_is_headless()` 分支才 `drmGetRenderDeviceNameFromFd()` 找 render node；正常路径直接打开 card 节点并 `gbm_create_device()`。
   ⇒ **没有 render node 不是问题**（simpledrm 本来就不提供 render node）。
2. `src/backends/native/meta-render-device.c detect_hardware_rendering()`：
   GL_RENDERER 是 `llvmpipe`/`softpipe`/`swrast` 时只是把 `is_hardware_rendering` 置 FALSE，**不是错误**。
3. `src/backends/native/meta-renderer-native.c choose_primary_gpu_unchecked()`：
   `for (allow_sw = 0; allow_sw < 2; allow_sw++)` —— 先挑硬件渲染 GPU，**再挑软件渲染 GPU**；`create_render_device()` 对非硬件加速的 GBM device 也返回，代码里注释 "Check first hardware rendering devices, and if none found, then software rendering devices"。
4. `NEWS`：`* Fall back to CPU copy path when using a software renderer`。
   ⇒ mutter 43 官方就支持 "kms_swrast/llvmpipe 作为主 GPU"，会把帧通过 CPU copy 交给 dumb buffer。

### 1.4 Mesa 侧的软件 KMS 路径

`Mesa 22.3`（Debian 12）`src/gbm/backends/dri/gbm_dri.c`：
```
dri_device_create():
    ret = dri_screen_create(dri);
        → loader_get_driver_for_fd(fd)
            card0 非 render node → loader_get_pci_driver() 返回 NULL（platform 设备）
                                 → loader_get_kernel_driver_name() = "simpledrm"
        → dlopen("simpledrm_dri.so") 失败（Mesa 没有这个驱动）
    if (ret) ret = dri_screen_create_sw(dri);
        → 先试 zink → 再试 kms_swrast → 最后 swrast
```
⇒ 只要有 `kms_swrast_dri.so`（Debian bookworm arm64 的 `libgl1-mesa-dri` 已包含，已核对
<https://packages.debian.org/bookworm/arm64/libgl1-mesa-dri/filelist>），gbm 就能在 simpledrm
上创建软件渲染设备，mutter 的 EGL/GBM + dumb buffer 扫出即可成立。

### 1.5 为什么 p207 会崩：panfrost 电源问题（非显示驱动）

崩溃现场（wifi-net-fixer 用 loader `prevlog` 抓到）：
```
[26.465750] SError Interrupt on CPU1, code 0x00000000bf000000 -- SError
[26.465763] CPU: 1 PID: 375 Comm: gnome-shell Not tainted 6.6.0-dirty #238
[26.465783] pc : panfrost_gpu_soft_reset+0x34/0xe4
[26.465796] lr : panfrost_device_resume+0x18/0x48
[26.465896] Kernel panic - not syncing: Asynchronous SError Interrupt
  panfrost_gpu_soft_reset → panfrost_device_resume → pm_generic_runtime_resume
  → __genpd_runtime_resume → rpm_resume → panfrost_perfcnt_close
  → panfrost_postclose → drm_file_free → drm_release → __fput
```
- gnome-shell 启动时打开了 panfrost 的 card1/renderD128 做 GPU 枚举，随后释放 fd；
- 关闭时 panfrost 需要 runtime-resume GPU 去写 perfcnt 寄存器 → `panfrost_device_resume()` → 软复位读 `0x14AC0000`；
- 但 `pd_g3d`(0x105C4100)/`CMU_G3D`(0x14AA0000) 的 genpd 上电是"名义上电"：没有 vendor 的完整上电序列（TOP0 异步桥、PMU sys_pwr、pd-option 等），GPU 寄存器实际不可访问 → AXI 无应答 → SError → panic。

**⇒ 处理：先禁用 GPU（p209）。mutter 检测不到 card1 就完全不会走 panfrost 路径，软件渲染 GNOME 立即可用。GPU 加速留到第二优先级。**

### 1.6 那 8 条 `g_propagate_error: assertion 'src != NULL'` 是良性的

GDM 43 `common/gdm-settings.c gdm_settings_get_value()`：
```c
for (l = settings->backends; l; l = l->next) {
    res = gdm_settings_backend_get_value (backend, key, value, &local_error);
    if (res) break;
}
if (!res) g_propagate_error (error, local_error);
```
`gdm-settings-desktop-backend` 读取 `/etc/gdm3/custom.conf`、`/run/gdm3/custom.conf`：
key 不存在时返回 FALSE **且不设置 GError** ⇒ `g_propagate_error(error, NULL)` 触发 GLib critical。
调用方 `gdm_settings_direct_get_*()` 收到 FALSE 后**回退到 schema 默认值继续**。
⇒ 这 8 行只是"某些配置项没在文件里、用默认值"的 GLib bug 噪音，**不是挂死/崩溃根因**，不用管它。

### 2.4 缩放：1440x2560 上 GNOME 默认 UI 太小（p209 实测反馈）

simpledrm 只暴露一个模式 `1440x2560@60`（`DRM_MODE_INIT(60, 1440, 2560, 0, 0)`，refresh 精确 60.000），
Wayland 下 GNOME 默认 scale=1 → 逻辑分辨率 1440x2560 显示在 5.1 寸屏上，所有 UI 元素很小。
`xrandr`、`org.gnome.desktop.interface scaling-factor` 在 Wayland 都无效，**正确做法是 mutter 的
`monitors.xml` 里写整数 scale=2**（不需要开 fractional scaling）。

已对照 mutter 43.8 源码核对格式与取值（`backends/meta-monitor-config-store.c`、
`meta-monitor.c:208-210`：无 EDID 的 connector，vendor/product/serial 固定为 "unknown"；
`<mode>` 是必填，refresh 用 `DRM_MODE_INIT` 算出的 60.000）：

```xml
<monitors version="2">
  <configuration>
    <logicalmonitor>
      <x>0</x>
      <y>0</y>
      <scale>2</scale>
      <primary>yes</primary>
      <monitor>
        <monitorspec>
          <connector>Unknown-1</connector>
          <vendor>unknown</vendor>
          <product>unknown</product>
          <serial>unknown</serial>
        </monitorspec>
        <mode>
          <width>1440</width>
          <height>2560</height>
          <rate>60.000</rate>
        </mode>
      </monitor>
    </logicalmonitor>
  </configuration>
</monitors>
```

写入位置（**rootfs 在 /dev/sda20 上，写入后跨重启持久**）：
```sh
# GDM 登录界面（greeter 以 gdm 用户运行，HOME=/var/lib/gdm3）
mkdir -p /var/lib/gdm3/.config
# 写入上面的 monitors.xml 后：
chown -R gdm:gdm /var/lib/gdm3/.config
systemctl restart gdm3        # 登录界面立即变 2x

# 用户会话（以 root 自动登录、绕过 gdm 的方案为例）
mkdir -p /root/.config
# 同样内容写入 /root/.config/monitors.xml
```

若 2x 仍嫌小：把 `<scale>` 改 3（整数缩放都支持）；或叠加文字缩放
`gsettings set org.gnome.desktop.interface text-scaling-factor 1.25`（在会话内执行）。

### 3.2 如果 gdm 又卡在 activating（概率低，但备好）

不要 debug gdm，直接**绕过 gdm**（zenlte 主线移植最终就是这么用的：`/root/.bash_profile` 起 gnome-shell）：
```sh
# 1) 停掉/禁用 gdm，让默认 target 回 multi-user
systemctl stop gdm3 2>/dev/null
systemctl disable gdm3 2>/dev/null
systemctl set-default multi-user.target

# 2) tty1 自动登录 root（GDM 会抢 tty1，所以必须先停 gdm）
mkdir -p /etc/systemd/system/getty@tty1.service.d
cat >/etc/systemd/system/getty@tty1.service.d/autologin.conf <<'EOF'
[Service]
ExecStart=
ExecStart=-/sbin/agetty -a root --noclear %I $TERM
EOF

# 3) root 登录 tty1 后直接起 gnome-shell（带 tty 守卫，不影响 ttyGS0 串口 shell）
cat >/root/.bash_profile <<'EOF'
if [ "$(tty)" = "/dev/tty1" ] && [ -z "$GS_STARTED" ]; then
    export GS_STARTED=1
    export GBM_ALWAYS_SOFTWARE=1
    exec dbus-run-session -- gnome-shell --wayland --display-server --no-x11 >>/tmp/gnome-shell.log 2>&1
fi
EOF

systemctl daemon-reload
systemctl restart getty@tty1
sleep 20
tail -100 /tmp/gnome-shell.log
```
要点：
- **必须在 tty1（VT，seat0）的 logind session 里跑**。不能从 ttyGS0 串口 shell 直接跑：
  serial session 没有 seat，mutter 的 `MetaLauncher` 会报 `Could not get seat for session` 后退出。
- `.bash_profile` 里的 tty 守卫保证串口调试 shell 不受影响。
- 想恢复 GDM：`systemctl set-default graphical.target; systemctl enable --now gdm3; rm /root/.bash_profile`（或删掉那段）。

## 6. 路径 B（exynos_drm / DECON）评估 —— 本阶段不实施

> 只有当用户要求"GPU 加速 / 触屏 / 正确 KMS 能力"时才需要。就"GNOME 出画面"而言不必走。

### 6.1 树里已经有的（从 zenlte 主线移植，全部默认关闭）
- `exynos7.dtsi`：`pd_disp@105c4080`、`cmu_disp@13ad0000`、`sysmmu_disp_ro/rw@13a00000/13a10000`（含 vendor 要求的 `master` clock）、`decon@13930000`（带 iommus/arch timer 修正）

- `drivers/iommu/exynos-iommu.c`：+222 行（v5/v6 静态版本表、`exynos_iommu_master_ready()`、`exynos_iommu_map_identity()`、SYSMMU fault 不再 panic）
- `drivers/gpu/drm/exynos/exynos7_drm_decon.c`：+109 行（bootloader fb identity map、triple buffer `VIDW_BUF_START1/2`）
- `drivers/gpu/drm/exynos/exynos_drm_dma.c`：IOMMU 未就绪返回 `-EPROBE_DEFER`
- `drivers/gpu/drm/exynos/exynos_drm_drv.c`：bind 前 `drm_aperture_remove_framebuffers()`（去掉 simpledrm 冲突）
- `drivers/pmdomain/samsung/exynos-pm-domains.c`：+122 行（Exynos7420 DISP 上电序列，**照搬 zenlte，含 TOP0/VPP 访问**）

### 6.2 必须先探测的地址（loader + watchdog，30s 自动复位）
| 地址 | 用途 | 状态/风险 |
|---|---|---|
| `0x13AD0000` CMU_DISP | DECON/SYSMMU 时钟 | **未实测**。启用 CMU_DISP 后 `of_clk_init()` 启动早期就会读它，挂死=启动死循环 → 必须先 probe |
| `0x105C4080` pd_disp | DISP 电源域 | **未实测** |
| `0x13930000` DECON | 显示控制器 | **未实测** |
| `0x13A00000`/`0x13A10000` SYSMMU | 显示 IOMMU | 之前只"部分实测可访问"，需再确认 |
| `0x13ED0000` VPP | pm-domain pre 序列会读改写 | **未实测**（zenlte 序列里有） |
| `0x105D0000` TOP0 | pm-domain pre 序列会读改写 | **已实测读就挂死（p69）** → zenlte 的 `exynos7420_disp_pre[]` 不能直接照搬！必须去掉 TOP0 的 RMW 或改成只写 |
| `0x14C00000~0x14CE0000` | — | **绝对死区，永远不要碰** |

### 6.3 若将来走路径 B 的建议顺序
1. loader 带 watchdog 逐个 `mrd 0x13AD0000 / 0x105C4080 / 0x13930000 / 0x13ED0000 / 0x13A00000 / 0x13A10000`（S-Boot 显示仍在跑，此时寄存器大概率可访问）；
2. 改 `exynos-pm-domains.c` 的 7420 DISP 序列：删掉/改写 TOP0 与 VPP 的读写（本板 TOP0 读挂死）；或者干脆不给 DECON 挂 `power-domains`（bootloader 已把 DISP 上电，`pd_ignore_unused` 保持它）；
3. 打开 `DSH_ENABLE_DISP_IOMMU 1` → 开 CMU_DISP + sysmmu（仍需 sysmmu 的 `master` clock 语义）；
4. `&decon { status = "okay"; }`。
5. **DSI/panel 不用写**：zenlte 主线方案不包含 DSI 驱动/panel 节点，靠 bootloader 初始化的 DSIM 继续扫描，DECON 用 identity map 接管 bootloader fb（`exynos_drm_drv.c` 的 `drm_aperture_remove_framebuffers()` 会移除 simpledrm）。
6. 风险：任一新地址访问挂死 → AXI 无应答、无 oops；loader watchdog 是唯一保险，必须每次先 arm。

## 7. 后续：panfrost GPU 加速修复（第二优先级，可选）

- 崩溃链：`panfrost_perfcnt_close → pm_runtime_resume → panfrost_device_resume → panfrost_gpu_soft_reset → 读 0x14AC0000 → SError`。
- 根因：`pd_g3d`/`CMU_G3D` 只有"名义 genpd 上电"，缺 vendor 完整序列：
  - vendor 参考：`/home/duanjb666/los20/kernel/samsung/universal7420/arch/arm64/mach-exynos/pm_domains-exynos7420.c`（及 `-cal.h`）
  - 关键：pd-option=0x1101、BUCK6EN/PMU sys_pwr、TOP0 异步桥时钟、save/restore list；但 **TOP0(0x105D0000) 本板读挂死**，vendor 那种 read-modify-write 不能直接用，需要改成只写固定值或先 probe 清楚。

### 7.1 近路（建议 p209 验证通过后立刻试）：DTS 去掉 GPU 的 power-domains

**机制（已逐行核对 panfrost 6.6 源码 + genpd 行为）**：
1. `panfrost_probe()` 里 `panfrost_device_init()` 会调 `panfrost_gpu_init()`，**读 `0x14AC0000` 的 GPU_ID/features**（`panfrost_gpu.c:262`）。p207 里 panfrost 能绑定、gnome-shell 能拿它当硬件 GPU，**说明 probe 时 G3D 已经真正上电可访问**（S-Boot 留下的电源状态 + panfrost 自己 enable 的 `aclk_g3d`/`pclk_sysreg_g3d`）。
2. panfrost 的 autosuspend 只有 50ms（`panfrost_drv.c:593`）。一旦有 job put，设备 runtime-suspend → **genpd 把 pd_g3d 断电**（写 `0x105C4100=0`，没有 vendor off 序列）。
3. 再 resume 时 genpd 只写 `0x105C4100=0xf`（我们的 `samsung,exynos5433-pd` 通用配置，pd-option=0），**没有 vendor 的 TOPC1 门控 / 7 个 PMU sys_pwr / pd-option=0x1101 / save_list 恢复** → G3D 实际没上电 → panfrost 读 `0x14AC0000` → SError。
4. 若 GPU 节点**不挂 power-domains**：genpd 永远不会把 pd_g3d 断电；panfrost 的 runtime suspend 只写 GPU 自己的 power 寄存器（不关 CCF 时钟、不动电源域），resume 时重新 soft reset 就能正常读 → **GPU 大概率直接可用（且是硬件加速）**。pd_g3d 无消费者 → 靠 bootargs 里已有的 `pd_ignore_unused` 保持上电（当前 bootargs 正好有）。

**改动（仅 DTS，1 行；等 p209 测试完再改，避免污染当前构建；补丁文件：`display-p210-gpu-no-pd.patch`）**：
```diff
 &gpu {
-    status = "disabled";
+    status = "okay";
+    /delete-property/ power-domains;
 };
```
**判读**：p210 = p207 + 上面改动。若 `gnome-shell` 不再在 26s 左右 panic、`dmesg` 无 SError、
`journalctl -b | grep -i panfrost` 有 GPU 正常初始化、GNOME 动画明显流畅 ⇒ GPU 加速恢复。
**风险/代价**：GPU 电源域常开（功耗略高）；这是过渡方案。若仍 SError，说明第一次 probe 的"可访问"并非持久状态，
必须走 §7.2 的完整 vendor 序列。

### 7.2 完整 vendor G3D 上电序列（真正修复，需硬件探测）

vendor `pd-g3d` 上电需要下列全部动作（地址已从 vendor `pm_domains-exynos7420-cal.h` / `regs-pmu-exynos7420.h` 解析）：

| 顺序 | 动作 | 地址 | 本板可访问性 |
|---|---|---|---|
| 1 | 开 TOPC1 门控 bit9（top→local clock） | `0x10570A04` | **未实测**（0x10570000 CMU_TOPC 在 p69 被标记为"启用即挂"——**必须先 loader `mrd` 探测**） |
| 2 | 写 7 个 PMU SYS_PWR：CLKRUN 0x1460 b0、CLKSTOP 0x14A0 b0、DISABLE_PLL 0x14E0 b0、RESET_LOGIC 0x1520 b0、MEMORY 0x1560 b1/b0、RESET_CMU 0x15A0 b0 | PMU `0x105C0000` 区 | ✅ 已实测可访问 |
| 3 | 写 pd-option `0x1101` | `0x105C4108`（PMU） | ✅ PMU 区可访问 |
| 4 | 写 local_pwr_cfg `0xf` | `0x105C4100` | ✅ PMU 区可访问 |
| 5 | 等 status == 0xf | `0x105C4100` | ✅ |
| 6 | 恢复 save_list（断电前保存的 SFR）：`DIV_G3D 0x14AA0600`、`G3D_LOCK 0x14AA0000`、`G3D_CON 0x14AA0100`、`G3D_CON1 0x14AA0104`、`G3D_CON2 0x14AA0108`、`MUX_SEL_G3D 0x14AA0200`、`ENABLE_ACLK_G3D 0x14AA0800`、`ENABLE_PCLK_G3D 0x14AA0900`、`ENABLE_SCLK_G3D 0x14AA0A00` | CMU_G3D `0x14AA0000` | ✅ `0x14AA0000` 已实测可访问 |

vendor 还做两件本板可以先跳过的事：`exynos_tmu_core_control()`（TMU 降噪 WA，mainline 无 TMU 驱动）；`g3d_pin_config_set()` + `s2m_set_dvs_pin()`（BUCK6EN/DVS 引脚，PMIC 相关）。
**注意**：vendor 的 top clock 在第 1 步；若 loader 探测发现 `0x10570A04` 也挂，则只能靠 "S-Boot 已把该门控打开" 的现状
（即 §7.1 的免 sequence 方案），完整序列不可达。

建议实现方式（`drivers/pmdomain/samsung/exynos-pm-domains.c`，仿照现有 `exynos7420_disp_cfg`）：
- 新增 compatible `samsung,exynos7420-g3d-pd` + `exynos7420_g3d_cfg`；
- pre 序列：sys_pwr 7 项（PMU）+ TOPC1（**仅在探测安全后**）；
- `local_pwr_option = 0x1101`；
- post 序列：save_list 恢复（需在 off_pre 时先保存，参照 vendor `exynos_save_sfr/exynos_restore_sfr`）；
- off 路径暂不实现时，可先给域加 `GENPD_FLAG_ALWAYS_ON`（避免断电后无法恢复）。
- zenlte 参考文档 `参考-zenlte主线移植/HANDOVER-DISPLAY-GPU-TOUCH.md` 的已知坑：
  - Panfrost T760 r0p1 的 AFBC/CRC/tiling 会让 fragment job 挂起/花屏 → `PAN_MESA_DEBUG=noafbc,nocrc`
  - 需要 `power/control=on` 的 systemd 服务缓解 GPU 超时
  - 启用 `scale-monitor-framebuffer` 会破坏 2x 缩放下触屏映射（本板触屏另说）
- 临时 workaround（不推荐长期）：保持 GPU 常开解决不了"首次 resume 就 SError"，还是得补电源序列。
