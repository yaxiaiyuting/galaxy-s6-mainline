# GPU DVFS 实现方案 — Exynos 7420 / Mali-T760 MP8（SM-G9209）

> 目标：把 GPU 从"固定 266MHz（CCF 谎报 700MHz）"变成**真变频**：
> 空闲降到 266MHz 省电，需要时升到 700MHz 保证视频/3D 性能。
> 前提：700MHz 必须真的能跑 —— 2026-10-22 的实测是**一升频就 SError/panic**。
>
> 本文档 = 硬件分析 + patch 形式实现 + 上机验证清单 + 风险回滚。
> 状态：**只写代码和文档，未 build、未刷机、未碰设备。**

## 0. 结论速览（TL;DR）

| # | 结论 |
|---|---|
| 1 | 700MHz 挂机**几乎不可能是电压问题**：vendor 全档 900000µV，266MHz 与 700MHz 同压（`gpu_dvfs_table_default[]`，`gpu_exynos7420.c:52-60`）。 |
| 2 | 真正的原因是 **GPU 在 PLL 重锁窗口里继续跑**：`g3d_pll` 的 LOCK 位在写 PMS 之前就是 1，mainline 的 `samsung_pll35xx_set_rate()` busy-poll 会**立即返回**，relock 的尾巴（最长 **37.5µs**）全喂给了 GPU。 |

## 2. 硬件事实汇总（带行号，全部可复核）

### 2.1 CMU_G3D 的时钟树（唯一真相）

vendor `drivers/clk/samsung/clk-exynos7420.c`：

```
:850   PLL(g3d_pll, "g3d_pll", pll_1452x, G3D_LOCK, G3D_CON, G3D_CON, 31, ... table_g3d ...)
:1280  MUX(mout_g3d, ..., EXYNOS7420_MUX_SEL_G3D, 8, 1, EXYNOS7420_MUX_STAT_G3D, 8, 3, ...)
         PNAME(mout_g3d_p) = {"g3d_pll", "fin_pll"}      ← :797
:1633  DIV(sclk_hpm_g3d, ..., EXYNOS7420_DIV_G3D, 8, 2, ...)   ← 唯一的 DIV，只喂 HPM
:2339  GATE(g3d, "aclk_g3d", "mout_g3d", EXYNOS7420_ENABLE_ACLK_G3D, 0, CLK_IGNORE_UNUSED, NULL)
```

拓扑：

```
        g3d_pll (PLL1452X, 24MHz 参考, 可编程)
              │
fin_pll(24M)──┴─► mux[ MUX_SEL_G3D.bit8 ] ─► gate[ ENABLE_ACLK_G3D.bit0 ] ─► GPU (Mali-T760 MP8)
                                                     │
                                     DIV_G3D[9:8] ───┴─► sclk_hpm_g3d（HPM 计数器，与 GPU 功能无关）
```

**没有 aclk 分频器 ⇒ GPU 频率 == PLL 频率 ⇒ 变频就是改 PLL。**

寄存器基址 `CMU_G3D = 0x14AA0000`，偏移（`clk-exynos7.c` 的宏，与 vendor `regs-clock-exynos7420.h:262-326` 一致）：

| 偏移 | 名称 | 说明 |
|---|---|---|
| 0x0000 | `G3D_PLL_LOCK` | PLL 锁时间寄存器（写 `Pdiv × 150`） |
| 0x0100 | `G3D_PLL_CON0` | M[25:16] / P[13:8] / S[2:0] / LOCK[29] / ENABLE[31] |
| 0x0200 | `MUX_SEL_G3D` | bit8 = mux：0=fin_pll，1=g3d_pll |
| 0x0300/0x0400 | `MUX_ENABLE_G3D` / `MUX_STAT_G3D` | mux 使能/状态 |
| 0x0600 | `DIV_G3D` | [9:8]=sclk_hpm_g3d，[6:4]=pclk 分支 |
| 0x0800 | `ENABLE_ACLK_G3D` | bit0 = aclk_g3d（PD 代码里用的是 bit1，见 §3.5） |
| 0x0900 | `ENABLE_PCLK_G3D` | bit0/1 = pclk_sysreg / pclk_pmu |
| 0x0a00 / 0x0b00 | `ENABLE_SCLK_G3D` / `ENABLE_IP_G3D0` | 其余 |

### 2.2 PLL1452X 公式与 vendor 全档参数

```
fout = mdiv × 24MHz / (pdiv << sdiv)
```

`clk-exynos7420.c:674-684`（`table_g3d[]`，字段序 `{rate, pdiv, mdiv, sdiv, kdiv}`）：

| 频率 | P | M | S | 验算 |
|---|---|---|---|---|
| 772 MHz | 6 | 193 | 0 | 193×24/6 = 772 ✅ |
| 700 MHz | 6 | 175 | 0 | 175×24/6 = 700 ✅ |
| 600 MHz | 3 | 75 | 0 | 75×24/3 = 600 ✅ |
| 544 MHz | 3 | 68 | 0 | 68×24/3 = 544 ✅ |
| 420 MHz | 3 | 105 | 1 | 105×24/(3×2) = 420 ✅ |
| 350 MHz | 6 | 175 | 1 | 175×24/(6×2) = 350 ✅ |
| 266 MHz | 6 | 133 | 1 | 133×24/(6×2) = 266 ✅ |

实测 `CON0 = 0xa0850621`：M=(>>16)&0x3FF=**133**，P=(>>8)&0x3F=**6**，S=&0x7=**1**，ENABLE[31]=1，LOCK[29]=1 → **266MHz**。bootloader 把 G3D PLL 留在最低档。

## 3. 为什么 700MHz 会挂 —— 完整技术分析

### 3.1 实测时间线（2026-10-22）

1. 读 `CON0 = 0xa0850621` → 266MHz（§2.2）。
2. 严格照 mainline `samsung_pll35xx_set_rate()` 的写序，把 M/P/S 改成 175/6/0：
   写 `G3D_PLL_LOCK = 6×270`，RMW 写 `CON0`，轮询 LOCK。
3. **"写入成功、立刻锁定"** —— 轮询立刻返回。
4. GPU suspended，静置 2 秒，**无异常**。
5. 发起一次 D-Bus 截图（强制 GPU 渲染）→ **SError → panic**。

关键观察：**静置不挂，一干活就挂**；而且**立刻**返回"已锁定"。

### 3.2 排除：电压不足

- vendor 的 266MHz 和 700MHz 都是 900000µV（§2.3），同为 900mV。
- 若 700mV 欠压，266MHz 同样跑不起来（同压同轨）。
- 而且 vendor 连 772MHz 都标 900mV（只是被 `GPU_MAX_CLOCK_LIMIT=700` 限制掉）。

⇒ **不是欠压**。这条一旦成立，整个"升压再升频"的思路就是错的方向。

### 3.3 排除：PLL 参数写错 / PLL 没锁

- `fout = 175×24/(6<<0) = 700MHz`，参数本身正确（§2.2 表）。
- 写完后 `LOCK[29]` 读到 1，说明 PLL 最终锁住了（否则 `samsung_pll_lock_wait()` 会 `Could not lock PLL` 打印 + 超时）。
- 如果 PLL 真的没锁，GPU 会**没有任何时钟**，那么连寄存器读写都会失败（挂起期间就能看出来），而不是"静置正常、渲染才炸"。

⇒ PLL 本身没问题。**问题在"切换过程"里**。

### 3.4 主因：PLL 重锁窗口被漏给了正在运行的 GPU

这是本方案的核心判断，三个证据链咬合：

**(a) LOCK 位轮询会立刻早退。**
mainline `clk-pll.c:248-292`：

```c
	tmp = readl_relaxed(pll->con_reg);
	...
	writel_relaxed(rate->pdiv * PLL35XX_LOCK_FACTOR, pll->lock_reg);   /* :274-276 */
	tmp &= ~(M/P/S masks); tmp |= ...;                                 /* :278-285 */
	writel_relaxed(tmp, pll->con_reg);
	/* Wait for PLL lock if the PLL is enabled */
	if (tmp & BIT(pll->enable_offs))                                   /* :287-288 */
		return samsung_pll_lock_wait(pll, BIT(pll->lock_offs));    /* :289 */
```

而 `samsung_pll_lock_wait()` → `readl_relaxed_poll_timeout_atomic(con_reg, val, val & mask, 0, 20000)`：
**写之前 `LOCK[29]` 就是 1**（`CON0 = 0xa0850621` 的 bit29 = 1）。PLL 的 LOCK 位要过几个时钟周期才会被硬件拉低，所以第一次读几乎必然还是 1 → **立刻返回 0**，内核打印"成功"。

> 换句话说：**那句 "立刻锁定" 恰恰证明这个等待是假的。** 真实的重锁要等，而内核一秒都没等。

**(b) 重锁最长要 37.5µs（有明确规格）。**
vendor `clk-pll.c:706` `PLL145XX_LOCK_FACTOR = 150`，锁时间寄存器写 `pdiv × 150`（`:767`）：

| 目标档 | Pdiv | LOCK 寄存器值 | 折合时间（24MHz 参考） |
|---|---|---|---|
| 700 MHz | 6 | 900 | **37.5 µs** |
| 544/600/420 MHz | 3 | 450 | 18.75 µs |
| 266 MHz | 6 | 900 | 37.5 µs |

mainline 用 `270×Pdiv`（`clk-pll.c:208`，P=6 → 1620 → 67.5µs 上限），这个"上限"只在**真等**的时候有意义。

**(c) 只有"真干活"才炸，符合时钟完整性故障的特征。**
SError 是 AXI 访问异常（本板对未就绪 IP 的典型表现，参见 `GPU加速-20261020.md`）。
- 静置时 GPU 内部无事务，坏时钟没人消费 → 2 秒没事；
- 一进渲染，GPU 的 job/MMU/L2 立刻开始大批量 AXI 事务，此时如果时钟在这 37.5µs 里抖动/停摆，流水线状态机被破坏 → SError；
- 而且"两次采样之间 VCO 频率瞬变"本身就会让内部 PLL-based 逻辑（如 GPU 内部的 shader core clock divider、L2 的时钟门控同步器）出现亚稳态。

⇒ **时序：写 CON0 → PLL 失锁 ≤37.5µs → GPU 在这段时间里被喂了不稳定时钟。**

### 3.5 为什么"先关 aclk_g3d 再改 PLL"不够好

父代理的直觉"先隔离 GPU 再改 PLL"是对的，**但手段要换**：

1. **关 aclk_g3d = GPU 完全停钟。** 如果此时有 job 在飞（devfreq 恰恰是在 GPU 忙的时候才升频），job 会直接卡死 → 超时 / SError。
   vendor **从不在 GPU 活动时关它**：`gpu_enable_clock()/gpu_disable_clock()`（`gpu_exynos7420.c:370-390`）只在**域上下电**时用，`gpu_set_clock()` 用的是 mux。
2. **到底哪个 bit 是真门，还没验证。**
   - vendor CMU 的 `aclk_g3d` gate = `ENABLE_ACLK_G3D.bit0`（`clk-exynos7420.c:2339`）；
   - vendor PD 下电序列里 g3d 的 local clock = `ENABLE_ACLK_G3D.bit1`（`pm_domains-exynos7420-cal.h:24-26`）。
   两个都叫 aclk_g3d。主线我们只注册了 bit0。如果真正的 GPU 时钟门是 bit1，那"关 bit0"根本没隔离 —— 白关，还给了虚假的安全感。
3. 关钟/开钟还会牵扯 genpd 的 CLKSTOP/SYS_PWR 语义（`EXYNOS_PMU_CLKSTOP_CMU_G3D_SYS_PWR_REG` 等），在 ALWAYS_ON 的域上乱动风险更大。

⇒ **mux 到 fin_pll 是"变慢但不中断"，比"停钟"安全得多，而且是 vendor 唯一验证过的路径。**

### 3.6 于是采用 vendor 的序列

```
① clk_set_parent(mux, fin_pll)   → GPU 立刻跑 24MHz（干净、常稳）
② clk_set_rate(g3d_pll, target)  → 改 PLL；此时 GPU 的时钟源不是它，看不到 glitch
③ udelay(50µs)                   → 覆盖 37.5µs 最大锁时间，比 mainline 的假轮询可靠
④ clk_set_parent(mux, g3d_pll)   → 切回；此时 PLL 已稳定
```

代价：过渡期 GPU 只跑 24MHz。50µs 的 24MHz ≈ 正常 266MHz 下 4.5µs 的等效工作量，对一帧（16.7ms）完全可忽略。

### 3.7 如果 mux 序列还是挂 —— 剩下的可能（§7 待验证）

1. **mux 切换本身不干净**：`MUX_SEL_G3D` 写入时 PLL 在跑，硬件是否做 glitch-free 握手未知（vendor `clk_set_parent` 会读 `MUX_STAT_G3D` 确认，主线 CCF 不等）。→ 备选：切 mux 前后加 `udelay`、或改用 `MUX_ENABLE_G3D` 先关 mux 输出。
2. **PLL1452X 在 700MHz 档需要 CON1 的 AFC/bypass 配置**：vendor 只写 LOCK 和 CON0（`clk-pll.c:767-781`），主线也一样，理论上不需要；但 `CON0` 里那个 bit23 是什么没人说清（实测值里有）。
3. **GPU 侧 sysreg 有频率相关配置**（vendor 的 `G3D_G3DCFG_REG0` @ `EXYNOS7420_VA_SYSREG + 0x1234`，见 `gpu_exynos7420.c:250` 附近的 dump）。vendor 是否在变频时改它，未查清。
4. **真的需要更高电压**：vendor 表是"默认表"，可能不是最终量产表（ASV 表在 `asv-exynos_cal` 里）。但 772MHz@900mV 也在表内，先排除。
5. **700MHz 档本身是坏的**（器件/批次）：那就退到 544MHz（`opp-544000000`），视频场景 544MHz 也比 266MHz 强一倍。

## 4. 实现方案（patch 形式）

### 4.1 能力 A：真正的 PLL1452X（替换 FRATE 常量）

**已在树内**（`clk-exynos7.c`，patch 0002 的主要内容）。要点：

```c
/* vendor table_g3d[] 全档 + 两档更低频（vendor 没用过，但能精确整除） */
static const struct samsung_pll_rate_table g3d_pll_rate_table[] __initconst = {
	PLL_35XX_RATE(24000000, 772000000, 193, 6, 0),
	PLL_35XX_RATE(24000000, 700000000, 175, 6, 0),
	PLL_35XX_RATE(24000000, 600000000,  75, 3, 0),
	PLL_35XX_RATE(24000000, 544000000,  68, 3, 0),
	PLL_35XX_RATE(24000000, 420000000, 105, 3, 1),
	PLL_35XX_RATE(24000000, 350000000, 175, 6, 1),
	PLL_35XX_RATE(24000000, 266000000, 133, 6, 1),
	PLL_35XX_RATE(24000000, 160000000,  80, 3, 2),	/* 新增，实验档 */
	PLL_35XX_RATE(24000000, 100000000, 100, 6, 2),	/* 新增，实验档 */
};

static const struct samsung_pll_clock g3d_pll_clks[] __initconst = {
	PLL(pll_1452x, CLK_FOUT_G3D_PLL, "fout_g3d_pll", "fin_pll",
			G3D_PLL_LOCK, G3D_PLL_CON0, g3d_pll_rate_table),
};
```

为什么这就是"真驱动"：

- `pll_1452x` 在 mainline 映射到 `samsung_pll35xx_clk_ops`（`clk-pll.c:1305-1307`），`recalc_rate` **真读 CON0**（`clk-pll.c:219-236`）：

  ```c
  pll_con = readl_relaxed(pll->con_reg);
  mdiv = (pll_con >> 16) & 0x3FF; pdiv = (pll_con >> 8) & 0x3F; sdiv = pll_con & 0x7;
  fvco = parent_rate * mdiv; do_div(fvco, pdiv << sdiv);
  ```

  ⇒ `/sys/kernel/debug/clk/fout_g3d_pll/clk_rate` 会显示 **266000000**（不再是 700M 的谎报）。
- `round_rate` 走 `samsung_pll_round_rate()`（`clk-pll.c:52-68`）：带表时**向下取整**返回表内值
  （表必须降序排列，我们的表是 772→100 降序）。⇒ 上层不可能真正设成 733.3MHz；
  而 ramp 里会用 `clk_round_rate()` 比对，取整了就直接 -EINVAL，绝不静默降档。
- `set_rate` 就是 §3.4 分析的写法 —— 我们**不改它**（它是上游代码），而是**不在它不安全的场景下调用它**（见 4.2）。

本方案额外补的一项（patch 0002 尾部）：

```c
	/* DIV_G3D bits[9:8]：vendor 唯一的真实分频器，只喂 HPM 计数器 */
	DIV_F(0, "sclk_hpm_g3d", "mout_aclk_g3d_400",
			DIV_G3D, 8, 2, 0, CLK_DIVIDER_ALLOW_ZERO),
```

`id = 0` ⇒ 不建 DT lookup（`samsung_clk_add_lookup()` 里 `if (ctx->clk_data.hws && id)`），只是让 `clk_summary` 如实显示，并留个按名字取的入口。

### 4.2 能力 B：安全升频的 DVFS 路径（patch 0001）

**改的是 panfrost 的 devfreq `target()`**，核心函数：

```c
static int panfrost_g3d_set_rate(struct panfrost_device *pfdev, unsigned long rate)
{
	struct panfrost_devfreq *pfdevfreq = &pfdev->pfdevfreq;
	struct device *dev = pfdev->dev;
	long rounded;
	unsigned long cur;
	int ret = 0;

	if (!pfdevfreq->g3d_ramp_ok)
		return -ENODEV;
	if (!rate)
		return -EINVAL;

	mutex_lock(&pfdevfreq->g3d_lock);	/* devfreq 与 debugfs 串行化 */

	/* 只接受 PLL 频率表里能精确整除出来的频点 */
	rounded = clk_round_rate(pfdevfreq->g3d_pll, rate);
	if (rounded < 0 || (unsigned long)rounded != rate) {
		ret = -EINVAL; goto out;
	}

	if (clk_get_rate(pfdevfreq->g3d_pll) == rate) {
		/* 频率没变：顺手保证 mux 还挂在 PLL 上（上次失败可自愈） */
		if (pfdevfreq->g3d_strategy == PANFROST_G3D_STRATEGY_MUX)
			clk_set_parent(pfdevfreq->g3d_mux, pfdevfreq->g3d_pll);
		goto out;
	}

	if (pfdevfreq->g3d_strategy == PANFROST_G3D_STRATEGY_MUX) {
		/* ① GPU 时钟源切到 fin_pll(24MHz)：此后改 PLL 对 GPU 不可见 */
		ret = clk_set_parent(pfdevfreq->g3d_mux, pfdevfreq->g3d_safe);
		if (ret) { dev_err(dev, "g3d: cannot mux to safe parent (%d)\n", ret); goto out; }
	} else {
		/* 实验策略（GATE）：直接关 aclk_g3d，调用者必须保证 GPU 空闲 */
		clk_disable_unprepare(pfdev->clock);
	}

	/* ② 改 PLL */
	ret = clk_set_rate(pfdevfreq->g3d_pll, rate);
	if (ret) {
		dev_err(dev, "g3d: clk_set_rate(%lu) failed (%d)\n", rate, ret);
	} else {
		/* ③ 显式等过 PLL 最大锁时间（P=6 → 37.5µs），
		 *    不依赖 mainline 那个会早退的 LOCK 轮询 */
		udelay(PANFROST_G3D_SETTLE_US);		/* 50µs */
	}

	if (pfdevfreq->g3d_strategy == PANFROST_G3D_STRATEGY_MUX) {
		/* ④ 切回 PLL */
		int mux_ret = clk_set_parent(pfdevfreq->g3d_mux, pfdevfreq->g3d_pll);

		if (mux_ret) {
			dev_err(dev, "g3d: cannot mux back to g3d_pll (%d)\n", mux_ret);
			if (!ret)
				ret = mux_ret;
		}
	} else {
		clk_prepare_enable(pfdev->clock);
	}

	/* 实测校验：CCF 说过的话不算，clk_get_rate 说才算 */
	cur = clk_get_rate(pfdev->clock);
	if (!ret && cur != rate) {
		dev_err(dev, "g3d: core clock reads %lu Hz, wanted %lu Hz\n", cur, rate);
		ret = -EIO;
	}

out:
	mutex_unlock(&pfdevfreq->g3d_lock);
	return ret;
}
```

`target()` 的接线：

```c
static int panfrost_devfreq_target(struct device *dev, unsigned long *freq, u32 flags)
{
	struct panfrost_device *pfdev = dev_get_drvdata(dev);
	...
	opp = devfreq_recommended_opp(dev, freq, flags);
	if (IS_ERR(opp)) return PTR_ERR(opp);
	dev_pm_opp_put(opp);

	if (pfdev->pfdevfreq.g3d_ramp_ok) {
		ret = panfrost_g3d_set_rate(pfdev, *freq);	/* ← 安全序列 */
		if (ret) return ret;
	}
	return dev_pm_opp_set_rate(dev, *freq);	/* 电压/记账；此时 clk_set_rate 已是 no-op */
}
```

为什么后面那句 `dev_pm_opp_set_rate()` 不会再触发一次 PLL 写（重要，别删）：

- OPP core 只用 **`clk_get(dev, NULL)` = clocks[0] = "core"（aclk_g3d 门）**，`clk_count = 1`（`drivers/opp/core.c:_update_opp_table_clk()`）。
- 我们的 ramp 结束时 `clk_set_parent(mux, pll)` 会让 CCF 重算整条链的 rate，`clk_get_rate(aclk_g3d)` 已经是目标值；`clk_set_rate()` 算出"无需变更"就直接返回，不写寄存器。
- 万一真需要写（异常路径），我们也会在 `cur != rate` 时提前 `-EIO` 报出来，不会静默。

句柄从哪来（**不猜、不按名字全局查找**）：

```c
	pfdevfreq->g3d_pll  = devm_clk_get_optional(dev, "g3d-pll");   /* fout_g3d_pll */
	pfdevfreq->g3d_mux  = devm_clk_get_optional(dev, "g3d-mux");   /* mout_aclk_g3d_400 */
	pfdevfreq->g3d_safe = devm_clk_get_optional(dev, "g3d-safe");  /* fin_pll */
	if (!三个都在) return 0;		/* 非 Exynos G3D：保持上游行为 */
	if (clk_get_rate(safe) != 24000000) { warn; return 0; }
```

三个 clock 由 DTS 提供（§4.3），`g3d_safe` 直接引用 `&fin_pll` 这个 fixed-clock 节点 —— 比 `clk_hw_get_parent_by_index()` 稳（不用猜父索引，也不依赖 `__clk_get_hw` 的导出）。

debugfs 测试口（**这是上机第一步要用的东西**）：

```
/sys/kernel/debug/panfrost-g3d/state      # ramp=on/off, strategy, pll/core/mux_parent_rate/safe
/sys/kernel/debug/panfrost-g3d/rate       # 读 = PLL 当前频率；写 = 走一遍安全序列
/sys/kernel/debug/panfrost-g3d/strategy   # 0 = mux 到 fin_pll（默认，vendor 序列）
                                          # 1 = 关 aclk_g3d（实验，GPU 必须空闲）
```

它在 `panfrost_devfreq_init()` 的**最前面**创建，所以在 OPP 表缺失、devfreq 起不来的情况下依然可用。

### 4.3 能力 C：DTS OPP 表 + devfreq + 固定 900mV 供电（patch 0003）

```dts

	/delete-property/ power-domains;	/* p211：pd_g3d ALWAYS_ON，本方案不动 */

	clocks = <&cmu_g3d CLK_ACLK_G3D>,		/* core */
		 <&cmu_g3d CLK_PCLK_SYSREG_G3D>,	/* bus  */
		 <&cmu_g3d CLK_MOUT_ACLK_G3D_400>,	/* g3d-mux */

		opp-420000000 { opp-hz = /bits/ 64 <420000000>; opp-microvolt = <900000>; };
		opp-544000000 { opp-hz = /bits/ 64 <544000000>; opp-microvolt = <900000>; };

	};

	reg_gpu_vdd: regulator-gpu-vdd {
		compatible = "regulator-fixed";
		regulator-name = "vdd_g3d";
```

几个刻意的决定：

| 决定 | 原因 |
|---|---|
| `clocks` 属性必须重写整串 | DTS 属性是整体覆盖，板级覆盖 dtsi 时不写 `core`/`bus` 会把 panfrost 的时钟弄丢 |
| 加 `mali-supply` 指向 fixed 900mV | `devm_pm_opp_set_regulators(dev, {"mali"})` 会去找它；没有也能跑（-ENODEV 被容忍），但显式写出来才能表达"恒 900mV 不可调"这个硬件事实 |
| `opp-100000000` 默认注释 | devfreq 的 `simple_ondemand` 把 `freq_table[0]` 当空闲档；一个 vendor 没验证过的低档会在**第一次空闲**时挂掉 GPU，把整个 DVFS 实验搅浑 |
| 上限只到 700MHz | vendor `GPU_MAX_CLOCK_LIMIT = 700`，772MHz 档存在但被 vendor 自己限制掉 |
| `samsung,g3d-fixed-rate-hz` 默认注释 | 这是"只验证 700MHz 能不能跑"的**最低风险开关**：probe 时一次成型，之后不再有任何运行时切换 |

### 4.5 与 vendor 的差异表（哪些故意没做）

| vendor 做的事 | 本方案 | 原因 |
|---|---|---|
| mux → fin_pll → 改 PLL → mux 回 | ✅ 一样 | 唯一验证过的序列 |
| `sclk_hpm_g3d = aclk/3 或 /2` | ⚠️ 只注册了 DIV，未在 ramp 里设 | 只影响 HPM 采样频率，panfrost 不用 HPM（性能计数器 fd 除外） |
| 电压 `regulator_set_voltage(vdd_g3d, 900mV)` | ❌ 用 fixed regulator 表达 | 全档同压，无需真调；mainline 也没有 s2mps15 驱动 |
| `GPU_PM_QOS`（MIF/INT/CPU 联动） | ❌ 没做 | 需要 exynos-bus/devfreq + PM QoS 打通，见 §7；会影响高负载下的内存带宽，视频场景值得后续做 |
| 温度 throttling（544/350/266） | ❌ 没做 | `devfreq_cooling_em_register()` 已注册 cooling device，但没有 thermal zone 绑定；本板 thermal 驱动状态未验证 |
| ABB / ASV | ❌ 没做 | `GPU_DYNAMIC_ABB = 0`，vendor 默认也不动 |
| 772MHz 档 | ❌ 不放 | vendor `MAX_LIMIT = 700` |

## 5. 验证步骤（设备恢复后按顺序做，每步都有失败判据）

> 前提：串口或 `pstore`/`last_kmsg` 能拿到 panic 现场；`boot.img` 有可回滚备份；
> `pd_g3d` 保持 ALWAYS_ON（p211），**不要**在本流程里动电源域。
> 全部命令用 root。设备名按实际替换：`/sys/class/devfreq/14ac0000.gpu`（用 `ls /sys/class/devfreq/` 确认）。

### Step 0：准备（不验证 GPU，只保证能救）

```sh
# 记录基线
cat /proc/device-tree/model
ls /sys/class/devfreq/                       # 期望：出现 14ac0000.gpu（有 OPP 表才会出现）
dmesg | grep -iE 'panfrost|g3d|opp|devfreq' | tail -40
```

期望在 dmesg 里看到（patch 0001 打印）：

```
panfrost 14ac0000.gpu: G3D safe ramp ready: pll=266000000 Hz core=266000000 Hz safe=24000000 Hz
```

- 若打印 `no G3D clock triplet` → DTS 的 `clock-names` 没生效（patch 0003 没应用 / 拼错）→ 停，先修 DTS。
- 若打印 `g3d-safe is ... Hz (expect 24000000)` → `&fin_pll` 指错了 → 停。

回滚动作：无（只读）。

### Step 1：只验证"读数是真的"（只读，不改硬件）

```sh
# 1) CCF 报的频率（应该不再是 700MHz 的谎报）
cat /sys/kernel/debug/clk/fout_g3d_pll/clk_rate        # 期望 266000000
cat /sys/kernel/debug/clk/aclk_g3d/clk_rate            # 期望 266000000
cat /sys/kernel/debug/clk/mout_aclk_g3d_400/clk_parent # 期望 fout_g3d_pll
cat /sys/kernel/debug/clk/clk_summary | grep -E 'g3d|fin_pll'

# 2) 硬件真值（不信 CCF）
dd if=/dev/mem bs=4 skip=$((0x14AA0100/4)) count=1 2>/dev/null | od -An -tx4
#   期望 0xa0850621（M=133/P=6/S=1 → 266MHz，bit29 LOCK=1，bit31 ENABLE=1）
dd if=/dev/mem bs=4 skip=$((0x14AA0200/4)) count=1 2>/dev/null | od -An -tx4
#   MUX_SEL_G3D：期望 bit8 = 1（mux 选 PLL）
dd if=/dev/mem bs=4 skip=$((0x14AA0800/4)) count=1 2>/dev/null | od -An -tx4
#   ENABLE_ACLK_G3D：记下 bit0/bit1 的值（§3.5 的疑点，顺手取证）

# 3) 驱动自己的视图
cat /sys/kernel/debug/panfrost-g3d/state
#   期望：ramp=on / strategy=0 / pll=266000000 / core=266000000 / mux_parent_rate=266000000 / safe=24000000
```

失败判据：
- `clk_rate` 仍报 700000000 → PLL 驱动没生效（检查 `fout_g3d_pll` 是不是还是 `FRATE`）。
- `CON0` 读到的和 CCF 说的不一致 → CCF 又在撒谎，**不要继续**。
- `/sys/kernel/debug/panfrost-g3d/` 不存在 → `CONFIG_DEBUG_FS` 没开或 panfrost 没 probe。

回滚动作：无。

然后一档一档往上试（**每档都要跑真实渲染**）：

```sh
for f in 420000000 544000000 700000000; do
    echo "=== -> $f ==="
    echo $f > /sys/kernel/debug/panfrost-g3d/rate || { echo "set_rate 失败，停止"; break; }
    sleep 1
    cat /sys/kernel/debug/panfrost-g3d/state
    dd if=/dev/mem bs=4 skip=$((0x14AA0100/4)) count=1 2>/dev/null | od -An -tx4  # 硬件真值
    # 真实渲染（三选一，按装了哪个）
    glmark2-es2 --benchmark 2>&1 | tail -3 || kmscube -n 60 || es2gears_x11 -n 60
    dmesg | grep -iE 'SError|panic|Unrecoverable|g3d:' | tail -5   # 必须无输出
done
```

每档的期望：

| 目标 | CON0 期望 | `state` 的 pll | 渲染 |
|---|---|---|---|
| 420M | M=105 P=3 S=1 | 420000000 | 正常，无 SError |
| 544M | M=68 P=3 S=0 | 544000000 | 正常，无 SError |
| **700M** | M=175 P=6 S=0 | 700000000 | **正常，无 SError** ← 本次的核心验证点 |

失败判据与处置：

| 现象 | 判断 | 下一步 |
|---|---|---|
| 700M 时 SError/panic | mux 序列也没救回来 | → Step 2b（换 GATE 策略）+ §7 的 1/2/3 |
| 420M 就挂 | 不是高频问题，是"改 PLL"这件事本身 | → Step 2b + 检查 `MUX_STAT_G3D` 是否真的切过去了 |
| 设置成功但 `CON0` 没变 | CCF 又在假反馈 | 停，回来查 `clk-exynos7.c` |
| 设置后 GPU 卡住但无 panic | 24MHz 过渡期把 job 卡死了 | 说明 mux 切换不可用于"活动中的 GPU"，改用"只在空闲/上电时改频"（§7 第 6 条） |

**Step 2b（仅在 Step 2 失败时）**：换策略再试同一档（GATE 策略要求 GPU 空闲，所以先停掉渲染，只测"改频后再渲染"）：

```sh
echo 1 > /sys/kernel/debug/panfrost-g3d/strategy
echo 266000000 > /sys/kernel/debug/panfrost-g3d/rate
echo 700000000 > /sys/kernel/debug/panfrost-g3d/rate
cat /sys/kernel/debug/panfrost-g3d/state
kmscube -n 30            # 或 glmark2-es2
```

- GATE 策略**能过**而 MUX 策略不能 → mux 切换本身不干净（§7 第 1 条），可用"只在 GPU 空闲时改频"的产品化方案。
- 两种都挂 → 700MHz 档或 PLL 配置有问题（§7 第 2/3/5 条），先退到 544MHz。

回滚动作：`echo 266000000 > /sys/kernel/debug/panfrost-g3d/rate`；或直接 `echo simple_ondemand > $D/governor`。

### Step 3：单点固定 700MHz（最低风险的"性能模式"）

在 DTS 里打开：

```dts
	samsung,g3d-fixed-rate-hz = <700000000>;
```

重新编译 DTS 后启动（**仍然不接 devfreq**，或把 OPP 表留着但用 `min_freq` 钉住）：

```sh
dmesg | grep -i 'G3D fixed rate'        # 期望：G3D fixed rate applied: 700000000
cat /sys/kernel/debug/panfrost-g3d/state | grep pll
glmark2-es2 --benchmark                  # 长跑 5 分钟
# 视频场景
gst-launch-1.0 playbin uri=file:///...   # 或 mpv/gnome 播放器放一段 1080p60
dmesg | grep -iE 'SError|panic'         # 必须无输出
```

这一档过了，就说明 **"700MHz 静态运行"成立** —— 用户的核心诉求（看视频 GPU 要高频）已经可以交付，
后面 Step 4 的 devfreq 只是"省电优化"，挂了也不影响性能可用性。

### Step 4：接 devfreq（升降频都工作）

```sh
D=/sys/class/devfreq/14ac0000.gpu
echo simple_ondemand > $D/governor
cat $D/available_frequencies          # 期望 266000000 420000000 544000000 700000000
cat $D/cur_freq                       # 空闲时应在 266000000

# 升频：跑负载，看它自己上去
( glmark2-es2 --benchmark & ) ; sleep 2 ; cat $D/cur_freq ; wait
# 降频：负载停了，等 2~3 个轮询周期（50ms/次）
sleep 2 ; cat $D/cur_freq             # 期望回落到 266000000
cat $D/trans_stat                     # 期望看到 4 个档位之间的迁移计数

# 钉住 700MHz 看视频（这就是用户要的"性能模式"）
echo 700000000 > $D/min_freq
mpv --fs /path/to/1080p60.mp4         # 观察是否掉帧 / dmesg 是否干净
echo 266000000 > $D/min_freq          # 恢复
```

判定：
- `trans_stat` 里 266↔420↔544↔700 都有迁移且**无 panic** → 升降频都成立，DVFS 完成。
- 频繁抖动（266↔700 反复跳）→ 调 `upthreshold`（默认 45 偏低），或直接用 `min_freq` 钉。
- 升频瞬间偶发 SError → 24MHz 过渡不够，把 `PANFROST_G3D_SETTLE_US` 从 50 加到 200 再试。

（可选）把 `opp-100000000` 打开做低档实验：先 `echo userspace > governor; echo 100000000 > userspace/set_freq` 单点验证，
确认稳了再放开给 ondemand 当空闲档。

### Step 5：回归与长跑

```sh
# 30 分钟混合负载：视频 + 偶发 3D
for i in $(seq 1 30); do glmark2-es2 --benchmark >/dev/null 2>&1; sleep 60; done
cat /sys/class/thermal/thermal_zone*/temp   # 温度（本板 thermal 是否有效见 §7）
dmesg | grep -iE 'SError|panic|Unrecoverable|g3d:'    # 必须干净
```

## 6. 风险与回滚

### 6.1 风险清单

| 风险 | 概率 | 后果 | 缓解 |
|---|---|---|---|
| 700MHz 用 mux 序列**仍然** SError | 中 | panic（可恢复，不砖） | §3.7 / §7；退 544MHz；DTS 删 700M 档 |
| 24MHz 过渡期把在飞 job 卡死 | 低 | GPU job 超时、桌面卡一下 | vendor 已验证过这个序列；如仍出现 → 只在 GPU 空闲/上电时改频 |
| `MUX_SEL_G3D` 切换不 glitch-free | 低-中 | 偶发 SError | Step 2b 的 GATE 策略对照；或在切 mux 前后加 `udelay` |
| 关 `aclk_g3d`(bit0) 其实不是真门 | 中 | GATE 策略"看起来成功"其实没隔离 | 只用它做对照实验，不当产品方案（§3.5） |
| `clk_set_rate` 设了个 PLL 表里没有的值 | 低 | 被 `clk_round_rate()` 拦截返回 -EINVAL | 已在 ramp 里显式拦截 |
| devfreq 与 debugfs 并发改频 | 已修 | mux 停在 fin_pll（GPU 24MHz） | `g3d_lock` 互斥 + "同频时自动把 mux 切回 PLL" 的自愈逻辑 |
| `simple_ondemand` 抖动 | 中 | 频繁变频（每次都过 24MHz） | 调 `upthreshold`，或 `min_freq` 钉住 |
| 低档 100MHz 不稳 | 高（没验证） | 第一次空闲就挂 | **默认关闭**，单点验证后才开 |
| 温度过高 | 未知 | 降频/降寿命 | 没接 thermal zone（§7），先靠手动观测 |
| panic 后设备起不来 | 低 | 需要进 TWRP | boot 分区备份 + `boot.img` 保留三份 |

### 6.2 回滚（按影响面从小到大）

1. **运行时**：`echo 266000000 > /sys/kernel/debug/panfrost-g3d/rate`，`echo simple_ondemand > /sys/class/devfreq/*/governor`，`echo 266000000 > .../min_freq`。
2. **不重编内核**：DTS 里注释掉 `operating-points-v2` / `mali-supply` → panfrost 无 OPP 表 → devfreq 不启动，但仍可用 debugfs（`rate` 写口）实验。
3. **只回滚 DTS 的 OPP**：删 `opp-700000000`（或全部 OPP）→ 频率表只剩低档 → 上限被限制。
4. **回滚 patch**：
   ```sh
   cd <kernel tree>
   git apply -R patches/gpu/0003-dts-zeroflte-g3d-opp-devfreq.patch
   git apply -R patches/gpu/0002-clk-exynos7-real-pll1452x-and-hpm-div.patch
   git apply -R patches/gpu/0001-panfrost-exynos-g3d-safe-ramp.patch
   ```
   （注意：0002 会连"真 PLL"一起退回到 `FRATE(700MHz)`，那时 GPU 实际还是 266MHz、CCF 又会撒谎 —— 不建议单独退 0002。）
5. **彻底回滚**：`fastboot flash boot <备份的 boot.img>`（或用 TWRP 恢复 boot 分区）。
6. **cmdline 兜底**（不改任何代码）：让 panfrost 不 probe（`modprobe.blacklist=panfrost` 或 DTS `status="disabled"`）→ 回 llvmpipe 软件渲染，桌面可用。

## 7. 待验证清单（明确没查清的事）

| # | 待验证 | 怎么验 | 影响 |
|---|---|---|---|
| 1 | `MUX_SEL_G3D` 写入是否 glitch-free（vendor 会读 `MUX_STAT_G3D`，主线不等） | Step 2 每档前后 `dd` 读 `MUX_STAT_G3D(0x14AA0400)`，看 bit8 何时翻 | 决定 mux 序列能否用于"活动中的 GPU" |
| 2 | 700MHz 是否真的能跑（本方案的核心赌注） | Step 2 / Step 3 | 决定整个方案成立与否 |
| 3 | `ENABLE_ACLK_G3D` 的 bit0 vs bit1 哪个是真的 GPU 时钟门（PD 代码用 bit1，CMU 用 bit0） | Step 1 第 2 步读 `0x14AA0800` 看两个 bit 的值；再做 GATE 策略对照实验（关 bit0 后 GPU 是否真的停） | 决定 GATE 策略是否有效；也关系将来域下电 |
| 4 | PLL CON0 里的 bit23 是什么（实测值里有） | 对照 TRM / vendor 是否有写它的地方（目前 grep 不到） | 万一 700MHz 需要它 |
| 5 | GPU sysreg 是否有频率相关配置（vendor dump 里的 `G3D_G3DCFG_REG0 @ SYSREG+0x1234`） | 看 vendor 变频前后是否改它（`gpu_exynos7420.c` 的 dump 只是取证，不是配置） | 高频档可能需要 |
| 6 | 24MHz 过渡对"在飞 job"的真实影响 | Step 2 里在 `glmark2` 运行中反复升降频 | 决定是否需要"只在空闲时改频" |
| 7 | `sclk_hpm_g3d` 分频是否影响 panfrost 的 perfcnt | 打开 perfcnt fd 后读计数，对比 vendor 的 `aclk/3` 设定 | 只影响性能计数器/可能的 GPU 内部计时 |
| 8 | MIF/INT 的 PM_QOS 联动（vendor 有：700MHz 要 `pm_qos_mif=1552000`） | 视频场景下看 `devfreq` 的 exynos-bus；对比有无联动的帧率 | **视频场景可能比 GPU 频率更关键**（内存带宽饿死） |
| 9 | thermal zone 是否可用（vendor 544/350/266 三档降频） | `ls /sys/class/thermal`；能否读到 GPU 温度 | 长时间高频的散热安全 |
| 10 | 100MHz / 160MHz 档是否可用 | Step 4 末尾的低档单点实验 | 空闲省电幅度（266→100 大约再省 ~60% 动态功耗） |

### C. CCF 读数 vs 硬件真值（怎么自查"没被骗"）

```sh
# CCF 说的
cat /sys/kernel/debug/clk/aclk_g3d/clk_rate
# 硬件真值
dd if=/dev/mem bs=4 skip=$((0x14AA0100/4)) count=1 2>/dev/null | od -An -tx4
#   解：M=((v>>16)&0x3FF), P=((v>>8)&0x3F), S=(v&0x7); fout = M*24/(P<<S) MHz
```

只要两者不一致，就是 CCF 在撒谎（本项目历史上已经踩过一次：`FRATE(700MHz)` + 编造分频器）。
**本方案的 `state` 文件两项都打印**，就是为了让这种不一致一眼看出来。

### D. 一句话给下一个人

> 想要 700MHz：先确认 `CON0` 真的变成 `M=175/P=6/S=0`，再确认改之前 mux 已经切到 24MHz、改完等过 37.5µs。
> 这三件事任何一件没做，GPU 都会在 PLL 重锁的那几十微秒里被喂坏时钟 —— 那才是 2026-10-22 那次 panic 的真相，
> 而不是"电压不够"。
